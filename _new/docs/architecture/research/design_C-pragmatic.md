# MARK XXXVI — «Прагматичный минимализм»: полная архитектура

## 0. Философия варианта

Три неторгуемых требования — независимость от LLM, единый гейт разрешений для всех путей исполнения, откат файловых операций — реализуются структурно, в коде границ, а не дисциплиной. Всё остальное подчинено двум метрикам: фоновая стоимость (RAM/CPU/диск в idle) и стоимость сопровождения одним человеком. Каждая абстракция оплачивает существование: если контракт не защищает одно из трёх требований и не экономит строки в двух и более местах — контракта нет, есть просто функция. Целевой объём ядра — 8–10 тыс. строк вместо 23 тыс., при этом бóльшая часть — переиспользованные тулы и голосовой драйвер.

## 1. Процессная топология

**Два долгоживущих процесса, ни одним больше.**

1. **jarvis-engine** — asyncio-демон: агентный цикл, гейт разрешений, шина событий, world model, память, LLM-адаптеры, голосовой драйвер. Бюджет idle: ≤150 МБ RSS, <1% CPU, ноль пробуждений чаще раза в минуту.
2. **jarvis-ui** — тонкий клиент (на первом этапе тот же tkinter), общающийся с движком по локальному WebSocket JSON-сообщениями. Движок полностью headless: падение UI ничего не ломает, замена tkinter на Tauri/веб — замена клиента, не движка.

**Эфемерные воркеры**, запускаемые лениво и убиваемые по простою: (а) индексатор/эмбеддер — включает себе `PROCESS_MODE_BACKGROUND_BEGIN` + EcoQoS (низкий CPU-, I/O- и page-приоритет, E-ядра), перезапускается движком при превышении порога RSS (известный рост памяти fastembed); (б) браузер — Playwright, вынесенный в локальный MCP-сервер по stdio: краш-изоляция самого тяжёлого и падучего компонента плюс готовая LLM-независимая форма инструмента. Отдельного процесса на каждый плагин нет — это цена, которую VS Code платит за тысячи недоверенных авторов; здесь автор один.

Между процессами не гоняются блобы: WebSocket несёт события и команды UI, воркеры получают ID строк общей SQLite. IPC-формат — зарегистрированный каталог JSON-сообщений (урок Raycast: принимаются только известные типы).

## 2. Ядро: один цикл вместо контура planner→executor

Главный цикл — компактный while-loop в стиле Claude Code nO (~200–300 строк): плоская история сообщений; модель вернула tool calls — исполняем через гейт и продолжаем; вернула текст — отдаём пользователю. Никаких конкурирующих агентских персон.

На входе — **трёхуровневый роутер** (правила + быстрый structured-вызов основной модели): уровень 0 — прямой ответ; уровень 1 — лёгкий цикл с лимитом 2–3 хода (90% трафика: «открой», «найди», «переключи»); уровень 2 — Plan-and-Execute для многошаговых сценариев. План — данные, а не рассуждение: список типизированных шагов со ссылками на выходы предыдущих (`$1`-подстановка кодом, без LLM-вызова), хранится строками в `execution_log` (намерение пишется ДО исполнения, результат — ПОСЛЕ, как WAL). Replanner вызывается только при провале шага или расхождении наблюдений с ожиданиями. Восстановление после ошибки — декларативная таблица «класс ошибки → стратегия» (retry/skip/substitute/replan/escalate); LLM-решатель — только когда правила молчат. Ошибки остаются в контексте replanner'а.

**Steering-очередь**: реплики пользователя (голосом или текстом) вклиниваются на границе итерации — «стоп, не эту папку» — штатный путь, не kill. **Бюджеты — параметры конструктора без значения «безлимитно»**: ходы, шаги плана, число replan'ов, wall-clock таймаут шага, дневной потолок стоимости; проверка ДО платного вызова; детектор стагнации по повторному вызову с идентичными аргументами. **Компактация** истории по порогу заполнения контекста с выносом фактов в память. Прежние planner, executor, task_queue и error_handler схлопываются: план — данные в цикле, очередь отложенных задач — таблица SQLite, обработка ошибок — таблица стратегий.

Субагенты — только read-only разведка (просканировать папку, собрать сводку) со свежим контекстом и компактным результатом; любая запись — главный цикл.

## 3. Хранение состояния

Единственная технология хранения — **SQLite (WAL, synchronous=NORMAL, busy_timeout, периодический PRAGMA optimize)**. Два файла:

- **jarvis.db** — вечные данные: память (+FTS5, +sqlite-vec), материализованный снапшот world model, `execution_log` (планы, шаги, pending-подтверждения), `action_journal` (undo), очередь отложенных задач, standing-grants, метрики, KV-конфиг.
- **history.db** — журнал наблюдений awareness с квотой диска, oldest-first eviction и retention по категориям; отделён, чтобы вытеснение истории не касалось вечных данных, а её бэкап был опционален.

Писатель один — движок; воркеры возвращают результаты по IPC. Все состояния задач, план, pending-подтверждения — в БД, не в RAM: рестарт процесса продолжает выполнение с последнего COMPLETE-шага (мини-DBOS без replay кода — план и так данные, достаточно интерпретатора строк). Конфиги и файл памяти самого ассистента пишутся через temp-файл + `ReplaceFile` — никогда полузаписанного состояния. Бэкап всей системы — копия двух файлов.

## 4. Реестр инструментов и система расширений

Каждый тул и awareness-модуль — **плагин**: `manifest.toml` (имя, описание, JSON Schema аргументов в «общем поднаборе» без union и глубокой вложенности, класс риска, `supports_preview`, `reversible`, триггеры активации, `api_version`) плюс pluggy-hookimpl. Манифесты читаются на старте **без импорта кода**; код тула лениво импортируется при первом вызове (вместе со своими тяжёлыми зависимостями). Из одного манифеста генерируются: tool-declarations для любой модели, секция capability-truth промпта (расширение удачного анти-дрейф-паттерна прототипа), правила гейта и превью-аннотации. Policy-таблица валидируется против манифестов на старте: невозможно добавить тул, забыв политику.

**Динамический скоуп**: в промпт попадает подмножество схем по доменам (файлы/окна/браузер/веб), активируемое контекстом; недоступные по политике тулы не удаляются из списка (инвалидация кэша, галлюцинации), а маскируются.

pluggy даёт hookspecs (`register_tools`, `on_event`, `on_startup/shutdown`), валидацию сигнатур, порядок и hookwrappers; discovery — папка `plugins/` + entry points. Выгрузка/hot-reload — Component-паттерн Obsidian: всё, что плагин зарегистрировал (подписки, таймеры, watcher'ы), трекается и снимается автоматически. Версия API — одно целое число, изменения только аддитивные. Тяжёлое/чужое — за MCP-границей (stdio, tools/list): ядро — хост, владеющий политикой; сторонние MCP-серверы подключаются адаптером, свои 25 тулов остаются in-process без сетевой прослойки.

## 5. Разрешения, подтверждения, откат

**Единственная точка исполнения** — `dispatch()` в ядре. Все пути — tool-call из live-сессии, текстовый запрос, шаг плана, плагин — сходятся в неё; мутирующие обёртки ОС принимают не строки путей, а **capability-объекты** (`ScopedRoot`: канонизация, запрет `..`, абсолютных путей и symlink-побегов на уровне типа), которые конструирует только гейт. Второго пути к действиям в системе физически нет — дыра executor-мимо-гейта закрывается конструкцией, а не проверкой.

Пайплайн фиксирован: pre-hook → deny → ask → allow → профиль сессии; deny непереопределяем. **Четыре уровня риска**: read-only → авто; обратимое → авто + журнал + toast «Перемещено 12 файлов — Отменить»; внешнее (письмо, пост) → подтверждение; необратимое → блокирующее подтверждение с точным payload, не пересказом. Поверх — немодифицируемый **circuit-breaker-пол**: операции над корнями дисков, %USERPROFILE%, каталогом самого Jarvis требуют подтверждения в любом профиле. Standing-grants привязаны к конкретному паттерну, видимы и отзываемы в UI, имеют срок.

**Подтверждение — durable interrupt**: шаг получает статус WAITING_FOR_SIGNAL в `execution_log`, payload пинается хэшем, задача не ест ресурсов и переживает рестарт; resume исполняет ровно одобренное (расхождение хэша — отказ). Одобрение плана предавторизует confirm-шаги с известными аргументами; шаги с вычисляемыми аргументами проходят гейт заново при исполнении. Ленивое «объясни, что это сделает» — LLM-вызов по запросу.

**Откат** — три слоя. Нижний: платформенные API — удаление только через `IFileOperation` с `FOFX_RECYCLEONDELETE|FOFX_ADDUNDORECORD` (корзина + Ctrl+Z в Explorer), перезапись — temp + `ReplaceFile`, staging-копии перезаписываемых файлов в каталоге ассистента с квотой. Средний: **saga-журнал** — intent-запись до операции, completion после, у каждого шага идемпотентная обратная операция; после краха координатор дочитывает журнал. Мутационные тулы обязаны check-before-act (идемпотентность закрывает окно «исполнил, но не записал»). Верхний: **undo-стек** команд с человекочитаемыми парными подписями («Верни X в Y»), batch — одна undo-единица; голосовое «отмени последнее» снимает верхний юнит. Batch-операции оформляются как changeset: превью списка src→dst с чекбоксами, применение, журнал, откат — обязательный `preview()` в контракте файловых action-хендлеров.

## 6. World model: контекст рабочего окружения

Принцип: **событийность вместо поллинга, производные вместо сырья, проекция вместо единственной копии в RAM**.

- **Файлы**: bootstrap — чтение MFT (или делегирование Everything через его IPC, если установлен, — тогда мгновенный поиск бесплатно; свой USN-ридер — фоллбек и страховка от внешней зависимости); инкременты — USN Change Journal через pywin32: durable, слепая зона после перезапуска закрывается catch-up'ом журнала, который ведёт сама NTFS. watchdog остаётся только на 1–2 «горячих» папках. Между источником и моделью — фильтр мусора, дедуп по пути, debounce с тихим окном 100 мс и жёстким потолком.
- **Окна/приложения**: `SetWinEventHook(EVENT_SYSTEM_FOREGROUND, OUTOFCONTEXT)` — событийно, без внедрения в процессы; AFK — системное «время с последнего ввода». Интервалы активности — heartbeat-слияние по ActivityWatch (pulsetime = интервал + малый запас): база растёт от переключений, не от времени.
- **Хранение**: только производные (пути, заголовки, интервалы, связи «документ—проект», извлечённый по требованию текст) в history.db; квота, retention, opt-in по категориям, индикатор наблюдения, команда «забудь X». Сырых скриншотов в v1 нет — это отдельный тяжёлый домен.
- **Механизм обновления**: текущее состояние — материализованная проекция append-only журнала диффов; редкая периодическая реконсиляция чинит дрейф. Чтение отдаёт замороженные снапшоты; изменение публикует событие с old+new. В RAM — только горячий срез с лимитом записей.
- **Доступ** — только через модуль-шлюз world_gateway (урок Recall): ни один модуль, включая плагины и LLM-контур, не читает history.db напрямую; LLM получает текстовые срезы. Это точка политики данных и одновременно точка LLM-независимости.

## 7. Память

Три уровня: контекст сессии → компактация по порогу → долговременная память в jarvis.db. Поиск гибридный: BM25 (FTS5) + вектор (sqlite-vec, 384d) со слиянием RRF; при сотнях тысяч чанков brute-force KNN хватает с запасом — отдельная векторная БД не оплачивает существование. Эмбеддинги — квантованный all-MiniLM через fastembed/ONNX в фоновом воркере. Экстракция фактов — роль `memory-extractor` в реестре моделей: локальная модель со схемным выводом (GBNF/json_schema), облако — фоллбек; извлечение из диффов world model и компактации сессий, батчами под фоновым приоритетом. Плоский JSON уходит; экспорт памяти — открытый формат (SQLite + дамп в markdown).

## 8. Шина событий

Внутрипроцессный pub/sub — один класс ~200 строк: словарь тип→подписчики, per-listener try/except с логом и continue (упавший подписчик не роняет ни шину, ни голос), счётчик ошибок с авто-отключением хронически падающего подписчика. **Каталог из ~15 замороженных dataclass-событий в прошедшем времени** (`file.changed`, `window.focus_changed`, `action.executed`, `approval.requested`, `run.step_finished`, `memory.updated`…), correlation ID через цепочку голос→план→действие→журнал. У каждого подписчика — ограниченная очередь с политикой переполнения: coalesce (файловые шквалы), latest-wins (UI), block (журнал). Жёсткое правило: **команды не летают по шине** — «сделай X» идёт только через dispatch(); шина — факты о свершившемся. UI-процесс подписан через WebSocket-мост; глубина очередей — health-метрика.

## 9. Обработка запросов: голос и текст

Оба входа сходятся в один цикл и один диспетчер тулов. Текст — из UI по WebSocket. Голос — за интерфейсом **VoiceSession**: семантические события (speech-start/stop, транскрипты входа/выхода, tool-call с id, interruption со списком отменённых вызовов, session-expiring, audio-chunk) плюс явные capability-флаги (динамика тулов, resumption, text-модальность). Драйвер GeminiLive инкапсулирует непереносимое: 4 asyncio-задачи аудио, форматы 16/24 кГц, VAD, lifecycle-менеджер (resumption-хэндлы, реакция на GoAway, sliding-window compression, реконнект с существующим circuit breaker). Tool-calls из live-сессии проходят тот же гейт — транспортов много, диспетчер один. Второй драйвер в тот же слот — **half-cascade** STT→LLM→TTS (локальный Whisper + Piper + любая batch-модель): деградационная цепочка, при которой голос хуже, но жив без Gemini. Бюджет отклика — проектное требование: простая команда ≤1.5 с от конца речи, вехи прогресса голосом (не каждый шаг), частые TTS-фразы кэшируются.

## 10. Независимость от AI-модели

Слой `llm`: **два адаптера** — google-genai (новый SDK, единственный) и openai-совместимый (разом закрывает OpenAI, Ollama /api/chat, LM Studio, OpenRouter, vLLM), позже anthropic; обёртки официальных SDK, нормализация к внутренним типам сообщений/вызовов/ошибок с сохранением `raw`-полей. **registry.yaml** — роли (`live-voice`, `chat`, `planner`, `memory-extractor`, `classifier`, `embedder`) → provider:model, параметры, fallback-цепочка, требуемые capabilities; валидация покрытия на старте; смена модели — одна строка конфига. Единая таксономия ошибок; fallback-обёртка поверх retry; cooldown нездоровых провайдеров (обобщение существующих circuit breakers). Ключи — один модуль config (DPAPI/keyring), 14 дублей загрузки и 36 хардкодов исчезают за границей слоя. Structured output — общий поднабор JSON Schema + клиентская валидация + одна repair-итерация. LiteLLM не берём: нужен не пакет со 100+ провайдерами и его цепочкой инцидентов, а его паттерны в ~500 строках своего кода.

## 11. Производительность

Бюджеты фиксируются в репозитории и проверяются самомониторингом: движок idle ≤150 МБ RSS и <1% CPU; воркеры вне бюджета, потому что эфемерны. Механика: ленивые импорты тяжёлых зависимостей внутри хендлеров (профилирование `-X importtime`, с Python 3.15 — `lazy import`); событийный сон — `await event.wait()`/`queue.get()`, TaskGroup, никаких `while True: sleep(n)`; редкая периодика с грубыми допусками под таймер-коалесцинг ОС. Индексатор — под background mode + EcoQoS. psutil-цикл раз в 30–60 с пишет RSS/CPU в метрики; воркер выше порога — рестарт (заодно лечит фрагментацию аллокатора). Никаких неограниченных кэшей: у всего — лимит и вытеснение.

## 12. Масштабируемость и эволюция

Масштаб здесь — не пользователи, а годы: рост числа тулов, объёма памяти и истории. Точки роста — стабильные маленькие контракты, вокруг которых заменяемы реализации: манифест+hookspec (новые тулы без правки ядра), MCP (чужой и тяжёлый код out-of-process), слот VoiceSession (новые голосовые конвейеры), registry.yaml (новые модели), каталог событий шины, WebSocket-каталог сообщений UI (замена tkinter без движка). Контракты версионируются одним числом и меняются только аддитивно.

**Честные жертвы линзы**: in-process плагины не изолированы от ядра крашем (компенсация — Component-очистка, hot-reload, авто-отключение по счётчику ошибок, вынос рецидивиста в MCP); нет DAG-параллелизма планов (десктоп-шаги конфликтуют по окнам/файлам — потеря мала); нет полного event sourcing (только action_journal и диффы world model); один писатель SQLite (для single-user — не ограничение); WebSocket вместо named pipe (чуть больше накладных, зато один транспорт для любых будущих UI). Это осознанная плата за систему, которую один человек способен целиком удержать в голове и сопровождать пять лет.

## Модули

- **engine.loop (агентное ядро)**: Единственный while-цикл: трёхуровневый роутер (ответ / лёгкий цикл ≤3 ходов / Plan-and-Execute), плоская история, steering-очередь, бюджеты и детектор стагнации, компактация контекста, интерпретатор плана из execution_log с replan-узлом и таблицей стратегий восстановления [Python 3.12+ asyncio, TaskGroup; собственный код ~1.5–2 тыс. строк; никакого агентного фреймворка]
- **engine.gate (гейт разрешений)**: Единственная точка dispatch() для всех путей исполнения: пайплайн hooks→deny→ask→allow→профиль, 4 уровня риска, circuit-breaker-пол, durable-interrupt подтверждения с хэш-пиннингом payload, standing-grants с TTL, конструирование ScopedRoot-capabilities [Собственный код + SQLite (execution_log); эволюция core/security.py прототипа]
- **tools.registry (реестр инструментов)**: Манифесты manifest.toml (схема, риск, preview/reversible, активация), чтение без импорта кода, ленивая загрузка хендлеров, генерация tool-declarations, capability-truth промпта и правил гейта из одного источника, динамический скоуп схем по доменам, MCP-совместимая форма записи [pluggy (hookspecs/hookimpl/hookwrapper), tomllib, pydantic для схем]
- **actions.fileops (файловый слой)**: Обёртки платформенных API: IFileOperation (корзина + undo-record Explorer) для удалений, temp+ReplaceFile для перезаписи, staging-копии с квотой, ScopedRoot вместо строк путей, обязательный preview() и check-before-act у мутационных хендлеров [pywin32/comtypes (IFileOperation, ReplaceFileW), pathlib]
- **journal (saga-журнал и undo)**: Append-only журнал операций: intent до, completion после, идемпотентная inverse-op на шаг; undo-стек Command-паттерна с человекочитаемыми парными подписями и группировкой batch; восстановление после краха; аудит «что ассистент сделал сегодня» [SQLite (таблица action_journal в jarvis.db); паттерн Nautilus + Persistasaurus]
- **llm.batch (слой моделей)**: Два адаптера над официальными SDK (google-genai, openai-совместимый), нормализация сообщений/вызовов/ошибок с raw-полями, единая таксономия исключений, fallback-поверх-retry, cooldown провайдеров, registry.yaml роль→модель с capability-валидацией, общий поднабор JSON Schema + repair-петля [google-genai SDK, openai SDK (Ollama/LM Studio/OpenRouter), pydantic; ~700–1200 строк своего кода вместо LiteLLM]
- **voice (голосовой контур)**: Интерфейс VoiceSession: семантические события сессии + RealtimeCapabilities-флаги; драйвер GeminiLive (4 asyncio-задачи, VAD, resumption-хэндлы, GoAway, sliding-window compression, реконнект); слот для half-cascade STT→LLM→TTS как резерва; маршрутизация tool-calls в общий dispatch() [websockets, pyaudio/sounddevice; позже faster-whisper + Piper для каскада]
- **worldmodel (модель окружения)**: Инжест: MFT-bootstrap/Everything-IPC + USN catch-up для файлов, SetWinEventHook для окон, last-input для AFK; фильтр/дедуп/debounce; heartbeat-слияние интервалов; материализованная проекция журнала диффов с реконсиляцией; шлюз world_gateway — единственная точка чтения с политикой; текстовые срезы для LLM [pywin32 (USN, WinEvents), опционально Everything SDK/ES.exe, watchdog только для горячих папок, frozen dataclasses]
- **memory (долговременная память)**: Гибридный поиск BM25+вектор с RRF, экстракция фактов из компактаций и диффов мира локальной моделью со схемным выводом, retention и команда «забудь», экспорт в открытый формат [SQLite FTS5 + sqlite-vec (384d), fastembed/ONNX (в воркере), роль memory-extractor из registry.yaml]
- **bus (шина событий)**: Внутрипроцессный типизированный pub/sub: каталог ~15 frozen-событий в прошедшем времени, per-listener изоляция ошибок с авто-отключением, bounded-очереди с политиками coalesce/latest-wins/block, correlation ID через всю цепочку; команды по шине запрещены [asyncio.Queue, frozen dataclasses; ~200 строк собственного кода]
- **store (хранилище)**: Схема и миграции двух SQLite-файлов: jarvis.db (память, world-снапшот, execution_log, журнал, задачи, гранты, метрики) и history.db (наблюдения с квотой, oldest-first eviction, retention); единственный писатель — движок; атомарные перезаписи конфигов [sqlite3 stdlib, WAL + synchronous=NORMAL + busy_timeout + PRAGMA optimize]
- **ui-client (интерфейс)**: Отдельный процесс: чат, очередь подтверждений с точным payload и правкой параметров, чеклист плана из событий прогресса, тосты с Undo, индикатор наблюдения, управление грантами; движок работает и без него [tkinter на первом этапе, WebSocket (websockets/aiohttp) с каталогом зарегистрированных JSON-сообщений; позже заменяем на Tauri/веб без правки движка]
- **workers (эфемерные воркеры)**: Индексатор/эмбеддер под фоновым приоритетом с самопонижением (background mode + EcoQoS) и перезапуском по порогу RSS; запуск лениво, остановка по простою; обмен с движком ссылками на строки БД, не блобами [multiprocessing/subprocess, pywin32/ctypes (SetPriorityClass, ProcessPowerThrottling), psutil, fastembed]
- **mcp-adapter (граница внешних расширений)**: Хост локальных MCP-серверов по stdio: запуск процесса, tools/list-обнаружение, маппинг в реестр с риск-метаданными, прохождение вызовов через общий гейт; первый клиент — Playwright-браузер [MCP Python SDK, JSON-RPC/stdio]
- **config (конфигурация и секреты)**: Единственная точка загрузки ключей и настроек, registry.yaml моделей, бюджеты ресурсов и лимиты агентного контура как обязательные поля; шифрование секретов [pydantic-settings, keyring/DPAPI, YAML/TOML]

## Ключевые решения

- Два долгоживущих процесса (движок + UI) плюс эфемерные воркеры; никакого процесса-на-плагин и никаких брокеров — Изоляция процессов у VS Code существует ради тысяч недоверенных авторов; здесь автор один. Два конкретных источника нестабильности (UI, Playwright) выносятся адресно; всё остальное in-process дёшево и отлаживаемо. Минимальный фоновый footprint — прямая цель линзы (ценой: Жертвуем краш-изоляцией in-process плагинов: баг тула может уронить движок. Компенсация — Component-очистка, авто-отключение падающего подписчика, вынос рецидивиста в MCP; но риск ненулевой)
- Собственный агентный цикл (~2 тыс. строк) вместо LangGraph/CrewAI/AutoGen; контур planner→executor→task_queue упраздняется — Индустрия сошлась на «простой цикл + инфраструктура вокруг» (Claude Code, Anthropic, 12-Factor); отказы от LangChain задокументированы; SK удалил планировщики с цифрами 1869 vs 755 токенов. План-как-данные в SQLite даёт durable-исполнение без Temporal-подобного replay (ценой: Жертвуем готовыми фичами фреймворков (визуализация графов, экосистема интеграций, коммьюнити-рецепты) и берём на себя сопровождение всей обвязки цикла)
- Единственная точка dispatch() + capability-объекты ScopedRoot; политика — только в коде гейта, никогда в промпте — «Rules are enforced by the harness, not the model» — любой второй путь исполнения со временем дрейфует (что уже случилось с executor в прототипе). Тип вместо проверки закрывает класс ошибок «забыл про safe-roots» навсегда (ценой: Жертвуем гибкостью: каждый новый вид действия обязан оформляться типизированным тулом с манифестом — быстрые хаки «просто вызови функцию» и code-as-action запрещены конструкцией)
- SQLite (WAL + FTS5 + sqlite-vec) — единственная технология хранения; два файла: вечный jarvis.db и вытесняемый history.db — 100k+ SELECT/с, миллисекундный полнотекст, brute-force KNN с запасом для сотен тысяч чанков; транзакции, бэкап копированием, ноль эксплуатации. Разделение файлов даёт квоту и eviction истории, не трогая вечные данные (ценой: Жертвуем специализированными возможностями (ANN-индексы, распределённость, graph-запросы); при росте векторов до миллионов высокоразмерных придётся пересматривать. Один писатель — осознанное ограничение)
- Откат через компенсации: saga-журнал + staging + платформенные API (IFileOperation с корзиной, ReplaceFile); никаких снапшот-rollback и TxF — Компенсация корректна в живой среде, где файлы параллельно меняют другие программы; TxF деприкейтнут самим Microsoft; корзина и undo-record Explorer дают пользователю привычный путь отмены даже без Jarvis (ценой: Жертвуем «идеальным» откатом: компенсация возвращает объект, а не мир в точности; для перезаписей глубина undo ограничена квотой staging-каталога)
- Подтверждение — durable interrupt в execution_log с хэш-пиннингом payload, 4 уровня риска, «обратимое → авто + toast Undo» — Развязывает такт агента и латентность человека, переживает рестарт, даёт очередь подтверждений в UI; перевод обратимых операций в авто+Undo — главное лекарство от confirm-усталости, возможное только потому, что есть журнал и undo-стек (ценой: Жертвуем простотой блокирующего диалога: нужны идемпотентность шагов до interrupt, TTL брошенных подтверждений и дисциплина «показываем точный payload, не пересказ»)
- Свой LLM-слой из двух адаптеров над официальными SDK + registry.yaml роль→модель; LiteLLM не берём — Нужно 3–5 провайдеров, а не 100+; официальные SDK сопровождает провайдер; openai-совместимый адаптер разом покрывает все локальные рантаймы. Реестр ролей убивает 36 хардкодов и 14 загрузок ключа одной точкой конфигурации (ценой: Жертвуем готовой поддержкой экзотических провайдеров и фич (кэш-роутинг, спенд-трекинг из коробки) — новый провайдер = свой адаптер (~200–500 строк))
- Голос — за интерфейсом VoiceSession с capability-флагами; Gemini Live — драйвер, а не ось системы; каскад STT→LLM→TTS — резервный слот — Опыт LiveKit/Pipecat доказал: realtime не абстрагируется полностью, но семантические события сессии — абстрагируются; tool-calls из live-сессии обязаны идти через общий гейт. Каскад с локальными Whisper/Piper — настоящая провайдер-независимость голоса (ценой: Жертвуем частью возможностей конкретного провайдера (нюансы нативного S2S, проактивное аудио) и платим двойной сложностью: у сессии два принципиально разных lifecycle-механизма под одним контрактом)
- World model на событийных механизмах ОС: MFT/USN (или Everything), SetWinEventHook, heartbeat-слияние; хранить только производные, доступ через шлюз — Журнал ФС ведёт сама NTFS — durable и бесплатно; watchdog-подход прототипа теряет историю между запусками. Производные на 2–3 порядка дешевле сырья и закрывают 95% запросов; шлюз — перенос удачного паттерна единой точки (Recall-редизайн) на самые чувствительные данные (ценой: Жертвуем кроссплатформенностью (глубокая привязка к Win32) и полнотой: без записи экрана ассистент не ответит «что было на экране час назад» — только окна, файлы, интервалы)
- UI — отдельный процесс по WebSocket с каталогом зарегистрированных JSON-сообщений; движок headless — GIL/GC движка не фризят интерфейс, падение UI не убивает ассистента, замена tkinter на любой стек — замена клиента; WebSocket один покрывает tkinter, веб и Tauri, в отличие от named pipe (ценой: Жертвуем простотой одного процесса (сериализация, версионирование каталога сообщений) и микролатентностью named pipe — для чат-темпа несущественно)

## Миграция
Стратегия — strangler: новое ядро растёт рядом с работающим прототипом, куски переключаются по одному, прототип в фичефризе с этапа 0.

**Этап 0 — конфигурация (переиспользуется всё).** Единый модуль config + registry.yaml ролей моделей; все 14 загрузок ключа и 36 хардкодов имён заменяются обращением к нему прямо в старом коде. Готовность: grep не находит имён моделей и чтения ключа вне config/; прототип работает без изменений поведения.

**Этап 1 — фундамент: store, bus, реестр.** Пакет core2: SQLite-схема (jarvis.db, history.db), шина событий, ToolRegistry с manifest.toml для всех 25 тулов; policy-таблица core/security.py конвертируется в риск-поля манифестов, генерация capability-truth сохраняется (паттерн переиспользуется). Готовность: манифесты покрывают 100% тулов, генерируемая секция промпта байт-в-байт эквивалентна старой, тесты гейта зелёные.

**Этап 2 — гейт (закрытие главной дыры).** dispatch() с пайплайном deny→ask→allow и durable-interrupt; все вызовы тулов старого main.py и agent/executor переводятся на dispatch(); прямые импорты action-модулей из executor удаляются. Готовность: автотест «агентный путь получает confirm на опасной операции»; grep-тест: вне dispatch() нет вызовов action-хендлеров.

**Этап 3 — файловый слой и откат.** actions.fileops (IFileOperation, ReplaceFile, ScopedRoot, staging), saga-журнал, undo-стек; мёртвые ~30% actions/ и сирота searxng удаляются, copy_file получает ScopedRoot. Готовность: сценарные тесты «переименуй 20 файлов → отмени», «краш посреди batch → докат/откат по журналу»; в кодовой базе нет os.remove/shutil.move для пользовательских файлов.

**Этап 4 — новый цикл.** Роутер + лёгкий цикл + Plan-and-Execute на execution_log; planner/executor/task_queue/error_handler прототипа удаляются, task_queue мигрирует в таблицу; main.py сжимается до запуска engine. Переиспользуются: circuit breakers (в llm-слой), тулы (уже за манифестами). Готовность: рестарт посреди плана продолжает с последнего шага; main.py < 200 строк.

**Этап 5 — голос за интерфейсом.** Существующий Gemini Live-код (4 задачи, реконнект) оборачивается в драйвер VoiceSession; tool-calls из live-сессии идут в dispatch(); steering-очередь; старый SDK google.generativeai удаляется. Готовность: смена модели в registry.yaml не требует правок вне драйвера; в requirements один SDK Gemini.

**Этап 6 — отделение UI.** WebSocket-каталог сообщений, tkinter становится клиентом; движок headless. Готовность: kill UI-процесса не прерывает выполняющуюся задачу; запуск движка без UI работает.

**Этап 7 — world model v2.** USN catch-up + MFT bootstrap (или Everything-адаптер), SetWinEventHook, heartbeat-журнал в history.db с квотой, world_gateway; watchdog остаётся на горячих папках. Переиспользуются эвристики awareness прототипа как правила экстракции. Готовность: изменения, сделанные при выключенном Jarvis, видны после старта; idle-бюджет (≤150 МБ, <1% CPU) выдержан неделю по метрикам.

**Этап 8 — память v2 и финальная чистка.** FTS5+sqlite-vec, миграция плоского JSON (архив сохраняется), экстракция локальной моделью; удаление остатков core/ прототипа. Готовность: гибридный поиск отвечает на запросы по старым воспоминаниям; строк кода ≤ ~12 тыс.; ARCHITECTURE.md генерируется из манифестов.

Порядок жёсткий: 0→1→2 обязательны до всего остального (гейт — приоритет №1), 3–4 — ядро ценности, 5–8 допускают перестановку. Каждый этап заканчивается работающей системой — точки невозврата нет до этапа 4.

## Риски

- Низкоуровневая Windows-специфика (USN Journal, SetWinEventHook, IFileOperation через pywin32/comtypes) окажется дороже в отладке, чем ожидается, и станет болотом для соло-разработчика → Изолировать весь Win32-код в два тонких модуля (worldmodel.ingest, actions.fileops) с чистыми интерфейсами; на каждый — фоллбек попроще (watchdog, send2trash) за тем же интерфейсом; интеграционные тесты на чистой VM; вариант «делегировать Everything» как готовый обход самой сложной части (MFT/USN)
- In-process плагин или awareness-модуль роняет или подвешивает движок (нет краш-изоляции — осознанная жертва линзы) → Per-listener try/except на шине со счётчиком и авто-отключением; Component-паттерн авто-очистки при выгрузке; таймауты на вызовы хендлеров; supervisor-скрипт с авто-рестартом движка (состояние в SQLite делает рестарт дешёвым); хронически падающий модуль выносится в MCP-процесс
- Абстракция VoiceSession протечёт: второй realtime-провайдер или каскад не ляжет на интерфейс, спроектированный по одному Gemini Live → Capability-флаги с первого дня; интерфейс валидируется вторым драйвером (half-cascade на локальных Whisper/Piper) до того, как на него завяжется остальная система; непереносимое (VAD, форматы, lifecycle) — явно внутри драйвера, а не в контракте
- Усталость от подтверждений или, наоборот, слишком агрессивное «авто с Undo» приведёт к потере данных и подрыву доверия к ассистенту → Reversible-операции идут в авто только при работающем журнале+staging (проверка на старте); circuit-breaker-пол не отключаем; метрика доли подтверждений и отмен в metrics; первые недели — консервативный профиль с постепенным переводом классов операций в авто по накопленной статистике безошибочности
- Миграция затянется: два ядра параллельно, мотивация падает, прототип продолжает жить «ещё чуть-чуть» и strangler превращается в вечный гибрид (сценарий Siri) → Жёсткий фичефриз прототипа с этапа 0; этапы 0–2 короткие и дают видимую ценность (конфиг, гейт); каждый этап заканчивается работающей системой с критерием готовности; запрет на новые фичи до этапа 4; календарная ревизия прогресса раз в месяц
- SQLite-писатель станет узким местом при шквалах awareness-событий (копирование дерева = тысячи USN-записей) и начнёт душить латентность голосового контура → Debounce/coalescing до записи (шквал → батч-транзакция), history.db отделена от jarvis.db, запись истории — низкоприоритетная задача с bounded-очередью, метрика глубины очередей как health-сигнал; при деградации — вынос ingest в отдельный процесс-писатель history.db (архитектурный шов уже есть)
- Динамический скоуп инструментов (подмножество схем по контексту) заставит модель галлюцинировать недоступные тулы или терять нужные → Домены включаются консервативно (базовый набор всегда в промпте), недоступные по политике тулы маскируются, а не удаляются (стабильность KV-кэша); метрика «вызов несуществующего/замаскированного тула»; при проблемах — откат к статичному набору с ленивой подгрузкой только редких доменов
