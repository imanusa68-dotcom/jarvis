# MARK XL: эволюционная архитектура персонального ассистента

## 1. Философия варианта «Эволюция»

Прототип MARK XXXV (~25,8k строк, из них main.py 1784, ui.py 1195, core/security.py 976) — работающая система с двумя подтверждённо удачными паттернами: центральная policy-таблица с генерацией «capability truth» из неё же, и живой голосовой контур на 4 asyncio-задачах. Эволюционная линза означает: мы не строим второе ядро рядом, а последовательно пересаживаем систему на новые «органы», причём каждый шаг самоценен и ассистент работает каждый день миграции. Целевая форма — та же, что у революционного варианта (компактный однопоточный agent loop + серьёзная обвязка), но путь к ней — серия строго упорядоченных рефакторингов, где новый механизм сначала оборачивает старый код, а потом старый код удаляется.

Честная оценка выживаемости кода: до целевой архитектуры доживёт примерно **45–55% строк**. Подробно: голосовой контур (send/listen/recv/play, реконнект, circuit breakers) — ~80%, он переупаковывается в драйвер; хендлеры действий в actions/ — ~60% (логика открытия приложений, окон, поиска, погоды переносится, обвязка и файловые мутации переписываются на IFileOperation/ReplaceFile, ~30% мёртвого кода удаляется сразу); core/security.py — переживает как данные: таблица становится частью реестра действий, генератор capability truth сохраняется; awareness — ~40% (логика окон и приложений остаётся, watchdog-слежение за деревом заменяется USN/Everything); memory — ~30% (промпты LLM-экстракции живут, хранилище переписывается на SQLite); ui.py — ~50% (виджеты остаются, связь с движком переезжает на IPC); main.py — ~10%; agent/ (planner/executor/task_queue/error_handler) — ~10–15% (промпты планировщика и классификация ошибок переносятся, сами контуры схлопываются в цикл). Это нормальная цена: выбрасывается в основном оркестрационный клей, а не доменная логика.

## 2. Карта модулей

Целевая система — 3–4 процесса: **движок** (asyncio-ядро), **UI-процесс**, **индексатор** (фоновый, под low-priority), **эфемерные воркеры** (эмбеддинги, Playwright/MCP). Внутри движка модули:

- **kernel** — главный agent loop (~200–300 строк): плоская история, steering-очередь, бюджеты, компактация контекста.
- **registry** — ActionRegistry: декларации всех действий (схема, риск, preview, inverse, activation-триггеры); из него генерируются tool-declarations, capability truth и правила гейта.
- **gate** — единственный диспетчер вызова действий: pipeline deny→ask→allow, circuit-breaker-пол, подтверждения как персистентный interrupt, пиннинг payload хэшем.
- **journal** — саговый журнал операций + undo-стек + staging-каталог.
- **bus** — внутрипроцессный типизированный pub/sub (~150–200 строк).
- **worldmodel** — снапшот окружения + журнал диффов в SQLite; шлюз доступа к истории.
- **memory** — долговременная память: SQLite (FTS5 + sqlite-vec), LLM-экстракция.
- **llm** — batch-адаптеры + реестр «роль→модель» + fallback/retry/cooldown.
- **voice** — realtime-драйверы за событийным интерфейсом (GeminiLiveDriver первый).
- **planner** — трёхуровневый роутер + Plan-and-Execute с execution_log.
- **plugins** — pluggy-хост, манифесты, MCP-адаптер.
- **supervisor** — самомониторинг psutil, перезапуск воркеров, бюджеты ресурсов.

## 3. Ядро: один цикл вместо оркестратора

main.py схлопывается в цикл формы «модель вернула tool calls → гейт → исполнение → результат в историю → продолжить; вернула текст → отдать пользователю». Контур planner→executor→task_queue упраздняется как отдельные сущности: план — это инструмент (`update_plan`), живущий в контексте; task_queue вырождается в хранилище отложенных задач в SQLite (напоминания уже так работают). Существующая steering-механика достраивается: между `listen`-задачей аудиоконтура и циклом появляется asyncio-очередь, проверяемая на границе каждой итерации, — «стоп, не эту папку» становится штатным путём, а не kill.

Бюджеты — свойство конструктора цикла, без значения «безлимитно»: лимит ходов лёгкого цикла (2–3), шагов плана, перепланирований (1–2), wall-clock таймаут шага, дневной потолок стоимости (существующие квоты модели переезжают сюда), детектор стагнации по повторному вызову с идентичными аргументами.

## 4. Обработка запросов: голос и текст

Оба входа сходятся в одну точку — kernel. Текстовый путь: UI-процесс шлёт сообщение по IPC → steering-очередь → цикл (batch-адаптер LLM). Голосовой путь: GeminiLiveDriver держит realtime-сессию (существующие 4 задачи + реконнект + resumption-хэндлы + реакция на GoAway оформляются как session-lifecycle-manager внутри драйвера) и эмитит семантические события: транскрипты, tool-call с id, interruption со списком отменённых вызовов, session-expiring. Критично: **tool-вызовы из live-сессии идут через тот же гейт**, что и все остальные — драйвер лишь доставляет вызов и результат. Интерфейс драйвера снабжается capability-флагами (per-response tool_choice, динамика тулов, resumption), чтобы будущий каскадный драйвер STT→LLM→TTS (провайдер-независимый резерв голоса) встал в тот же слот. Роутер запросов трёхуровневый: правила + быстрый structured-вызов модели делят трафик на «прямой ответ», «лёгкий цикл 1–2 тула» (90% случаев) и «Plan-and-Execute» (многошаговые сценарии: план как typed-список шагов с плейсхолдерами $1/$2, replan только при провале).

## 5. Разрешения, подтверждения, откат

Это сердце эволюции и первый этап миграции, потому что закрывает главную дыру прототипа (executor мимо гейта) без переписывания чего-либо ещё.

**Гейт.** Вводится одна функция `dispatch(action, args, ctx)` — физически единственная точка, где возможен вызов хендлера действия. Через неё проходят все три пути: tool call из live-сессии, шаг плана, вызов плагина. Внутри — фиксированный pipeline: circuit-breaker-пол (немодифицируемый список катастрофического: корни дисков, %USERPROFILE%, каталог самого Jarvis — confirm всегда, любым режимом) → deny-правила → allow/standing-grants → ask → режим сессии. Существующая policy-таблица core/security.py остаётся источником правды, но шкала уточняется до 4 уровней: read-only → авто; обратимое → авто + журнал + toast «Отменить»; внешнее (письмо, пост) → ask; необратимое → блокирующее подтверждение с точным payload. Гейт проверяет **фактические** аргументы в момент исполнения (аргументы шага плана вычисляются в рантайме), а не «обещанные» при планировании. Дыра cmd_control с сырым полем `command` закрывается типизацией: свободная строка команды перестаёт существовать как вход, действия — только зарегистрированные.

**Подтверждение как персистентный interrupt.** Confirm-шаг не блокирует диалог: состояние задачи и pending-операция пишутся в SQLite (status=WAITING_FOR_SIGNAL), пользователь отвечает голосом/кнопкой когда угодно, resume продолжает с того же шага; всё переживает рестарт. Одобренный payload пинуется хэшем — executor отказывает при расхождении (защита от перегенерации вызова моделью). У подтверждений есть TTL. Одобрение плана предавторизует confirm-шаги с конкретными аргументами; шаги с рантайм-аргументами проходят гейт заново.

**Откат.** Саговый журнал в SQLite: intent-запись ДО операции → операция → completion-запись; у каждого мутационного действия — идемпотентная обратная операция и ссылки на staging-копии (копия файла в каталог ассистента перед перезаписью). Поверх журнала — undo-стек Command-паттерна (по образцу Nautilus): batch-переименование — одна undo-единица с человекочитаемой подписью, голосовое «отмени» снимает верхний unit. Нижний слой файловых мутаций: удаление — только IFileOperation с FOFX_RECYCLEONDELETE|FOFX_ADDUNDORECORD (корзина + Ctrl+Z в Explorer как подстраховка), перезапись — temp-файл + ReplaceFile (атомарно, сохраняет ACL). Мутационные хендлеры обязаны реализовать `preview()` → typed diff («будет перемещено 12 файлов, список») и check-before-act идемпотентность — это контракт интерфейса Action, а не пожелание. Файловые пути модулям выдаются не строками, а объектом ScopedRoot (канонизация, запрет «..» и выхода за корень на уровне типа) — класс ошибок «забыл проверить путь» (copy_file без safe-roots) исчезает конструктивно.

## 6. Шина событий и взаимодействие модулей

Разделение по образцу Home Assistant: **события — факты** (прошедшее время), **команды — через реестр действий** с валидацией; никакого request/response по шине. Шина — один класс на ~150 строк: диспетчеризация по типу события, per-listener try/except с логированием (упавший подписчик не роняет соседей), счётчик ошибок подписчика с авто-отключением хронически падающего (связка с существующими circuit breakers). Каталог событий фиксированный и маленький (~15 типов, frozen dataclasses): file.changed, window.focus_changed, app.installed, action.executed, action.confirm_requested, memory.updated, run.step_started/finished, session.expiring и т.п. Через всю цепочку голос→план→действие→журнал проходит correlation ID. Каждая подписка имеет ограниченную очередь с политикой переполнения: coalesce для файловых штормов, latest-wins для UI, block для журнала. Контракт сообщений шины сериализуем с первого дня — это позволяет позже прозрачно пробросить события в UI-процесс и воркеры без смены API (урок OVOS: контракт шины — единственное, что нельзя менять часто).

## 7. World model: модель рабочего окружения

Принцип: **текущее состояние — восстановимая производная от журнала событий**, а не единственная копия истины в RAM.

- **Файлы.** Watchdog-слежение за деревьями заменяется двухступенчато: сначала интеграция с Everything через IPC (named pipe / ES.exe) — мгновенный поиск и всегда актуальный индекс за ~50 МБ чужой RAM; затем собственный USN-ридер (pywin32) как fallback и как источник событий file.changed с catch-up после простоя (журнал ведёт NTFS, изменения не теряются, пока ассистент выключен). Watchdog остаётся только на 1–2 «горячих» папках (Downloads, рабочий проект) для мгновенной реакции.
- **Окна/приложения.** Поллинг заменяется на SetWinEventHook(EVENT_SYSTEM_FOREGROUND, OUTOFCONTEXT) в потоке с message loop; журнал активности пишется с heartbeat-слиянием (pulsetime = интервал + запас): «окно X активно 47 минут» — одна строка, а не 2820. AFK — по системному «времени с последнего ввода».
- **Хранение.** SQLite: append-only журнал диффов (события с old+new) + материализованный текущий снапшот (frozen dataclasses в памяти — только горячий срез с лимитом записей). «История изменений», «недавние действия» и материал для undo — запросы к одному журналу. Квота диска и retention задаются с первого дня: сырых снимков экрана в v1 нет вообще, только производные (пути, заголовки, интервалы, извлечённый текст); UIA-чтение экрана — по требованию, с CacheRequest и узким TreeScope.
- **Доступ.** История активности — самые чувствительные данные; читаются только через модуль-шлюз worldmodel с policy-проверкой (включая LLM-контур и плагины), файл БД шифруется DPAPI, в UI — индикатор наблюдения, пауза и «забудь X». В облачную модель уходит только производный текст релевантных срезов — это одновременно граница приватности и точка LLM-независимости.

## 8. Память

Плоский JSON заменяется тем же единым SQLite-файлом (WAL, synchronous=NORMAL, busy_timeout, PRAGMA optimize): таблица фактов + FTS5 (гибридный поиск BM25) + sqlite-vec (384d, all-MiniLM через fastembed/ONNX в эфемерном воркере с рестартом по порогу RSS — известная утечка fastembed нейтрализуется дизайном). LLM-экстракция памяти сохраняется (промпты переносятся), но получает роль memory-extractor в реестре моделей — кандидат на локальную модель с GBNF-гарантией структуры. Компактация контекста цикла по порогу (~90%) выносит важное в память. Запись памяти и конфигов — только через temp+ReplaceFile.

## 9. Независимость от LLM

Двухуровневая граница. **Batch-слой** абстрагируется полностью: внутренние типы сообщений/вызовов/ошибок, два адаптера над официальными SDK — google-genai (новый SDK, старый google.generativeai удаляется) и openai-совместимый (покрывает OpenAI, Ollama /api/chat, LM Studio, OpenRouter, llama.cpp). Никакого LiteLLM как зависимости — его паттерны (fallback-поверх-retry, три класса fallback по таксономии ошибок, CooldownCache) копируются в ~200–500 строк; существующие circuit breakers провайдеров переезжают сюда. Рядом с нормализованными полями всегда хранится сырое native_*. **Реестр «роль→модель»** (registry.yaml): live-voice, planner, memory-extractor, cheap-classifier, embedder; каждая роль — provider:model, параметры, fallback-цепочка, требуемые capabilities с валидацией на старте. Это одним махом убивает 14 загрузок ключа и 36 хардкодов. **Realtime-слой** честно не абстрагируется до конца: интерфейс — семантические события сессии + capability-флаги, wire-протокол и lifecycle остаются в драйверах. Structured output — общий поднабор JSON Schema (плоско, без union), клиентская валидация + одна repair-итерация.

## 10. Расширяемость

Каждый тул и awareness-модуль — плагин: manifest.toml (имя, схема аргументов pydantic, риск-уровень, activation-триггеры, требуемые capability-группы) + pluggy-hookimpl (hookspecs: register_actions, on_event, on_startup/shutdown). Манифесты читаются на старте без импорта кода — capability truth и валидация policy-таблицы генерируются из них, код тула импортируется лениво при первом вызове (прямое лекарство от «25 тулов тянут всё при старте»). Гейт реализован как hookwrapper вокруг вызова действия — у плагина физически нет другого пути к побочным эффектам; файлы — только через выданный ScopedRoot. Версионирование — одно целое api_version + правило аддитивных изменений схем (LLM кеширует схемы тулов). Тяжёлое/нестабильное — out-of-process: Playwright-браузер выносится в локальный MCP-сервер (stdio, tools/list) — краш-изоляция плюс бесплатная совместимость с любым LLM-клиентом; внешние MCP-серверы подключаются адаптером к тому же реестру и гейту. Сетевые плагины получают lifecycle «не готово → retry с backoff / сломано → терминально» (машина загрузилась раньше роутера — типовой кейс).

## 11. Производительность

Бюджеты явные: движок в idle — 80–150 МБ RSS, <1% CPU, ноль пробуждений чаще раза в минуту; UI — отдельный процесс; индексатор — отдельный процесс под PROCESS_MODE_BACKGROUND_BEGIN + EcoQoS; Playwright/эмбеддер — 0 МБ, пока не запрошены. Механика: ленивые импорты тяжёлых библиотек внутри хендлеров (профилирование -X importtime), событийная модель вместо поллинга (await event.wait(), TaskGroup), debounce файловых событий (тихое окно 50 мс–1 с + потолок + дедуп по пути), heartbeat-слияние журнала активности, между процессами — ID строк SQLite, не блобы. Supervisor раз в 30–60 с снимает RSS/CPU процессов через psutil, пишет метрики в SQLite, перезапускает stateless-воркеры по порогу — «Jarvis съел 2 ГБ за неделю» становится невозможным состоянием. Латентность: целевой бюджет «конец реплики → действие» ≤ 500 мс на лёгком пути; ленивый скоуп тулов (подмножество схем по контексту awareness, не все 25+) сокращает токены и ускоряет каждый ход.

## 12. Масштабируемость и горизонт 5 лет

Масштабирование здесь — рост числа тулов, объёма памяти и истории, а не пользователей. Швы заложены так: контракт шины сериализуем → любой модуль выносится в процесс без смены API; реестр действий MCP-совместим по форме → сторонние серверы подключаются адаптером; драйверный слот голоса → смена Gemini Live на каскад или другого realtime-провайдера не трогает ядро; SQLite-схемы версионируются миграциями; для каждой облачной зависимости существует local-first альтернатива (Whisper/Piper/локальная LLM через тот же openai-адаптер) — система деградирует, но живёт при отключении любого провайдера. PyO3/Rust — только по профилировщику, скорость приходит через нативно-backed библиотеки (SQLite, ONNX, orjson). ARCHITECTURE.md и capability-описания генерируются из реестров — страховка от эрозии знаний соло-мейнтейнера.

## 13. Компромиссы линзы

Эволюция медленнее революции: ~10–15% написанного в ходе миграции кода — временные мостики (shim-обёртки старых вызовов под новый гейт, двойная запись JSON+SQLite на переходный период), которые будут выброшены. Часть легаси (tkinter, отдельные кривые хендлеры) проживёт дольше, чем хотелось бы. Зато нет периода «ассистент не работает», каждый этап приносит пользу немедленно (этап 1 сам по себе закрывает главную дыру), и риск «переписали всё и не взлетело» исключён конструктивно.

## Модули

- **kernel (agent loop)**: Главный однопоточный цикл: плоская история, tool calls → гейт → результат, steering-очередь для инъекции реплик, бюджеты (ходы/шаги/стоимость/таймауты), детектор стагнации, компактация контекста по порогу. Заменяет оркестрацию main.py и контур planner→executor→task_queue. [Python asyncio, TaskGroup; ~200–300 строк собственного кода, без агентных фреймворков]
- **registry (ActionRegistry)**: Единый источник правды о действиях: схема аргументов, класс риска (4 уровня), supports_preview/reversible, activation-триггеры. Генерирует tool-declarations для LLM, capability-truth секцию промпта и правила гейта. Эволюция policy-таблицы core/security.py. [pydantic-схемы, manifest.toml на плагин, MCP-совместимая форма записи]
- **gate (диспетчер + разрешения)**: Единственная точка исполнения действий для всех путей (live-сессия, план, плагины): pipeline circuit-breaker-пол → deny → allow/standing-grants → ask → режим; подтверждение как персистентный interrupt в SQLite с пиннингом payload хэшем и TTL. [Собственный код поверх реестра; pluggy hookwrapper как механизм обёртки; SQLite для pending-подтверждений]
- **journal (журнал операций + undo)**: Саговый журнал: intent до операции, completion после, идемпотентные обратные операции, staging-копии; undo-стек Command-паттерна с человекочитаемыми подписями и группировкой batch-операций; файловые мутации через корзину и атомарную замену. [SQLite (append-only), IFileOperation (FOFX_RECYCLEONDELETE|FOFX_ADDUNDORECORD) и ReplaceFile через pywin32; ScopedRoot-класс поверх pathlib]
- **bus (шина событий)**: Внутрипроцессный типизированный pub/sub: факты в прошедшем времени (~15 типов, frozen dataclasses), per-listener изоляция ошибок, bounded-очереди с политиками coalesce/latest-wins/block, correlation ID через цепочку голос→план→действие→журнал. Сериализуемый контракт для будущего IPC. [Python asyncio.Queue, ~150–200 строк собственного кода; без брокера]
- **worldmodel (модель окружения)**: Актуальная модель: файлы, окна, приложения, активность, связи; текущее состояние — производная от журнала диффов; heartbeat-слияние интервалов активности; шлюз доступа к истории с policy-проверкой, шифрование, retention и квоты. [SQLite (журнал + снапшот), SetWinEventHook через pywin32/comtypes, GetLastInputInfo, DPAPI-шифрование, UIA с CacheRequest по требованию]
- **fileindex (файловый индекс)**: Мгновенный поиск файлов и durable-поток file.changed: интеграция с Everything через IPC как основной путь, собственный USN-ридер как fallback и catch-up после простоя; watchdog только на 1–2 горячих папках с debounce. [Everything IPC (named pipe / ES.exe), pywin32 (USN Change Journal, MFT), watchdog для горячих папок]
- **memory (долговременная память)**: Факты о пользователе и мире: гибридный поиск (полнотекст + вектор), LLM-экстракция из диалогов и событий (промпты переносятся из прототипа), приём выноса при компактации контекста. [SQLite WAL + FTS5 + sqlite-vec (384d), fastembed/ONNX (all-MiniLM-L6-v2) в эфемерном воркере]
- **llm (batch-адаптеры + реестр моделей)**: Полная абстракция request/response: единые типы сообщений/тулов/ошибок, retry→fallback по классам ошибок, cooldown провайдеров; registry.yaml «роль→модель» (live-voice, planner, memory-extractor, cheap-classifier, embedder) с capability-валидацией на старте; поле raw рядом с нормализованным. [google-genai (новый SDK), openai (совместимый эндпоинт: Ollama/LM Studio/OpenRouter/llama.cpp), собственный роутер ~500–1000 строк по паттернам LiteLLM]
- **voice (realtime-драйверы)**: Голосовой контур за событийным интерфейсом (транскрипты, tool-call, interruption, session-expiring) с capability-флагами; GeminiLiveDriver — существующие 4 asyncio-задачи + session-lifecycle-manager (resumption-хэндлы, GoAway, реконнект); слот для будущего каскада STT→LLM→TTS. [google-genai Live API (WebSocket, PCM 16/24 кГц); интерфейс RealtimeDriver + RealtimeCapabilities (по образцу LiveKit)]
- **planner (роутер + планирование)**: Трёхуровневый роутер (прямой ответ / лёгкий цикл 1–2 тула / Plan-and-Execute); план как typed-список шагов с плейсхолдерами результатов; execution_log (intent до, результат после, WAITING_FOR_SIGNAL для подтверждений); replan и таксономия восстановления retry/skip/replan/substitute/escalate. [Structured output основной модели (общий поднабор JSON Schema), SQLite execution_log по образцу Persistasaurus/DBOS]
- **ui (отдельный процесс)**: Интерфейс: чат, чеклист плана из событий прогресса, очередь подтверждений с точным payload и preview-диффами, undo-toast, индикатор наблюдения; недоверенный потребитель — данные только через шлюзы движка. [Существующий tkinter-код, пересаженный на IPC: локальный WebSocket/named pipe, JSON-сообщения; позже заменим на Tauri/веб без правки ядра]
- **plugins (плагин-хост)**: Загрузка манифестов без импорта кода, ленивая активация, hookspecs (register_actions, on_event, lifecycle), Component-паттерн авто-очистки регистраций, lifecycle сетевых плагинов с backoff; MCP-адаптер для внешних серверов; Playwright как локальный MCP-сервер. [pluggy, importlib.metadata entry points, MCP SDK (stdio-транспорт)]
- **supervisor (ресурсы и здоровье)**: Самомониторинг RSS/CPU движка и воркеров, перезапуск stateless-воркеров по порогу, метрики в SQLite, фоновые приоритеты индексатора, единый модуль circuit breakers и бюджетов. [psutil, pywin32/ctypes (PROCESS_MODE_BACKGROUND_BEGIN, EcoQoS/ProcessPowerThrottling)]

## Ключевые решения

- Собственный компактный agent loop вместо агентного фреймворка (LangChain/CrewAI/OpenManus не берём; LiteLLM — только как источник паттернов) — Индустрия сошлась на «простой цикл + инфраструктура вокруг» (Claude Code, Anthropic, 12-Factor); production-кейсы документируют отказ от фреймворков из-за отладки через слои абстракций; для соло-мейнтейнера на 5+ лет зависимость от мутирующей экосистемы — отдельный риск, а supply-chain-история LiteLLM неприемлема для программы с полным доступом к личным файлам. (ценой: Пишем и сопровождаем свою обвязку (~2–3k строк: цикл, гейт, шина, роутер fallback'ов) вместо готовой; отказываемся от бесплатных обновлений экосистемы и готовых интеграций.)
- Первым этапом миграции — единый диспетчер-гейт для всех путей исполнения, до любых других перестроек — Закрывает главную известную дыру (agent/executor и cmd_control мимо policy-таблицы) структурно, а не дисциплиной; все последующие этапы автоматически наследуют гейт; этап самоценен — прототип становится безопаснее для данных немедленно, ещё до появления новой архитектуры. (ценой: Ранний churn: нужно тронуть все ~25 вызовов тулов и агентный путь сразу, часть правок — временные shim'ы, которые позже будут выброшены вместе со старым executor'ом.)
- Единый SQLite-файл (WAL + FTS5 + sqlite-vec) как хранилище памяти, world model, журнала операций, execution_log и pending-подтверждений — Подтверждённая производительность (100k+ SELECT/с, FTS5 миллионы строк, sqlite-vec с запасом для сотен тысяч чанков 384d); транзакции, бэкап одним файлом, ноль эксплуатации; персистентность подтверждений и плана переживает рестарт — плоский JSON и in-memory состояние этого не дают. (ценой: Дисциплина одного писателя и миграции схем на годы; переходный период двойной записи JSON+SQLite; отказ от «настоящей» векторной БД (при росте до миллионов векторов высокой размерности понадобится пересмотр).)
- Голосовой контур не переписываем, а переупаковываем: Gemini Live остаётся первым драйвером за событийным интерфейсом с capability-флагами; realtime честно не абстрагируется до wire-уровня — Голос — самая живая и отлаженная часть прототипа (~80% переиспользования); опыт LiveKit/Pipecat доказывает, что полная абстракция realtime протекает, а честная граница «семантические события + флаги» дешевле; batch-путь при этом абстрагируется полностью и сразу. (ценой: Vendor-специфичный код остаётся в ядре голосового пути до появления каскадного драйвера; часть логики (VAD, lifecycle сессий) принципиально непереносима между провайдерами.)
- Откат через саговый журнал компенсаций + staging + корзина/ReplaceFile, а не снапшоты, TxF или System Restore — Компенсация корректна в живой среде, где файлы параллельно меняют другие программы; TxF деприкейтнут, Restore Points не покрывают документы; IFileOperation даёт пользователю привычную корзину и Ctrl+Z в Explorer как подстраховку независимо от Jarvis. (ценой: Каждое мутационное действие требует ручной реализации inverse-операции и preview — это налог на каждый новый тул; staging-каталог ест диск и требует своей retention-политики.)
- Файловый awareness делегируем Everything (IPC) с собственным USN-ридером как fallback, вместо развития watchdog-слежения — MFT+USN — эталон durable-индексации с копеечными ресурсами (1 млн файлов ≈ 100 МБ RAM); изменения не теряются, пока ассистент выключен; целый домен закрывается зрелым чужим кодом — критично для одного сопровождающего. (ценой: Внешняя зависимость от проприетарного (хоть и 15+ лет стабильного) продукта; собственный USN-fallback всё равно придётся написать и поддерживать; NTFS-специфика (не работает на FAT/сетевых дисках).)
- Плагины in-process на pluggy + декларативные манифесты с ленивой активацией; out-of-process — только UI и Playwright (как MCP-сервер) — Процесс-на-плагин существует у VS Code ради тысяч недоверенных авторов, которых здесь нет; Obsidian доказывает жизнеспособность in-process на годы; ленивые манифесты дают capability truth без загрузки кода и режут RSS; MCP для браузера — краш-изоляция самого падучего компонента + LLM-независимая форма тулов. (ценой: Нет краш-изоляции in-process плагинов (лечится Component-паттерном и авто-отключением падающих подписчиков, но баг в плагине может уронить движок); для стороннего кода границу доверия придётся усиливать позже.)
- Планирование: роутер + план-в-контексте + execution_log, без отдельного LLM-планировщика и без параллельной мультиагентности; субагенты — только read-only — Semantic Kernel удалил планировщики с числами (двойные вызовы, 1869 vs 755 токенов); 90% запросов десктоп-ассистента — 1–2 tool call, латентность голоса критична; Cognition документирует, что работают только однопоточные записи. (ценой: Сложные многошаговые сценарии выполняются последовательно (без DAG-параллелизма LLMCompiler); отказ от «эффектной» автономии — агент никогда не работает без бюджета и внешнего запроса.)
- Линза «Эволюция»: строгая последовательность инкрементальных этапов, ассистент работает каждый день; целевой архитектуры достигаем через shim-слои — Прототип — ежедневный рабочий инструмент, «выключить на полгода» означает потерю привычки и обратной связи; каждый этап самоценен (гейт, шина, SQLite приносят пользу немедленно); исключается риск «переписали и не взлетело» (урок Siri: гибрид на legacy — тупик, но и big-bang стоил Apple года). (ценой: Суммарно медленнее и ~10–15% временного кода-мостиков; легаси (tkinter, кривые хендлеры) живёт дольше; нужна дисциплина не останавливаться на «уже достаточно хорошо» посреди пути.)

## Миграция
**Этап 0. Страховочная сетка + конфиг (1–2 недели).** Golden-сценарии (20–30 типовых голосовых/текстовых запросов) как смоук-тесты; unified config: один загрузчик ключей, registry.yaml «роль→модель», удаление 14 дублей и 36 хардкодов, вынос live-ключа из config. Переиспользуется: всё, правки точечные. Готовность: grep не находит имён моделей вне registry.yaml; смоук-прогон зелёный.

**Этап 1. Единый гейт (2–3 недели).** Функция dispatch() поверх core/security.py; все вызовы тулов из main.py и agent/executor переводятся на неё; сырое поле command в cmd_control упраздняется; circuit-breaker-пол; логирование каждого вызова с вердиктом. Переиспользуется: policy-таблица и capability truth целиком. Готовность: в логе 100% tool-вызовов с вердиктом гейта; тест «executor не может вызвать хендлер напрямую» (хендлеры недоступны вне диспетчера).

**Этап 2. Шина + журнал операций (3–4 недели).** EventBus (~200 строк), каталог из ~15 событий; awareness публикует, память/UI подписываются; SQLite вводится: журнал операций с intent/completion, staging, undo-стек; файловые мутации actions/ переводятся на IFileOperation/ReplaceFile/ScopedRoot; мёртвые ~30% actions/ удаляются. Готовность: «отмени последнее» работает голосом для move/rename/delete; прямые вызовы между awareness и движком удалены.

**Этап 3. Персистентные подтверждения + память на SQLite (3–4 недели).** Confirm как interrupt (WAITING_FOR_SIGNAL, пиннинг хэшем, TTL); 4-уровневая шкала риска; миграция memory.json → SQLite FTS5 (двойная запись 2 недели, потом отключение JSON); sqlite-vec + воркер эмбеддингов. Готовность: подтверждение переживает рестарт; поиск по памяти отвечает <50 мс; JSON-путь удалён.

**Этап 4. Kernel-цикл (4–6 недель, самый рискованный).** main.py схлопывается в agent loop со steering-очередью и бюджетами; planner/executor/task_queue упраздняются (промпты и классификация ошибок переносятся); трёхуровневый роутер; execution_log для многошаговых планов. Голосовой контур подключается к циклу как есть. Готовность: main.py < 300 строк; golden-сценарии зелёные; многошаговый сценарий переживает рестарт посреди плана.

**Этап 5. LLM-слой (2–3 недели).** Batch-адаптеры (google-genai, openai-compatible), удаление старого SDK; retry→fallback→cooldown; голосовой контур оформляется как GeminiLiveDriver за событийным интерфейсом. Готовность: текстовый путь работает на локальной модели через Ollama переключением одной строки registry.yaml; в requirements нет google.generativeai.

**Этап 6. Процессы и производительность (3–4 недели).** UI на IPC (WebSocket/named pipe) — tkinter-код переезжает в отдельный процесс; индексатор (Everything/USN) под background-priority + EcoQoS; ленивые импорты; supervisor с psutil. Готовность: kill UI не роняет движок; idle RSS движка ≤ 150 МБ; file.changed доезжают после простоя (catch-up по USN).

**Этап 7. Плагины (3–4 недели).** Манифесты + pluggy для всех тулов; ленивая активация; Playwright → MCP-сервер; MCP-адаптер для внешних серверов. Готовность: новый тул добавляется одним каталогом с манифестом без правки ядра; крах браузера не трогает движок.

Итого ~5–7 месяцев календарно при соло-темпе. Каждый этап мержится в рабочую систему; порядок жёсткий: гейт до шины (безопасность важнее развязки), SQLite до kernel (циклу нужна персистентность), kernel до LLM-слоя (адаптеры вставляются в новый цикл, не в main.py).

## Риски

- Этап 4 (схлопывание main.py в kernel-цикл) окажется «маленькой революцией» внутри эволюции: скрытые связи оркестратора с голосовым контуром и UI всплывут в рантайме, и система будет полурабочей дольше плана → Golden-сценарии этапа 0 как обязательный гейт мержа; kernel вводится параллельно старому пути за feature-флагом (роутер сначала отправляет в новый цикл только текстовые запросы, голос переключается последним); правило «в любой момент один git checkout возвращает рабочую систему»
- Двойные механизмы переходного периода (JSON+SQLite, старый executor+новый гейт) задержатся навсегда — «временные» мостики имеют свойство костенеть у соло-мейнтейнера → Каждый этап в определении готовности содержит пункт «старый путь удалён» (не «выключен»); календарный лимит двойной записи (2 недели); чек-лист удаления shim'ов ведётся в ARCHITECTURE.md и проверяется перед стартом следующего этапа
- Реализация inverse-операций и preview для каждого мутационного действия — постоянный налог; часть хендлеров получит их формально или не получит вовсе, и undo станет дырявым → preview()/inverse — обязательные поля интерфейса Action: реестр не регистрирует мутационное действие без них (честное supports_preview=False переводит действие в tier «блокирующее подтверждение»); генерический fallback для файловых операций — staging-копия + компенсация «вернуть на место» покрывает 90% случаев одним кодом
- USN/Everything-интеграция и WinEvents на Python (pywin32, message loop, catch-up логика) сложнее, чем выглядит: краевые случаи NTFS, переполнение журнала, не-NTFS тома → Начать с Everything IPC (чужой отлаженный код) и держать watchdog на горячих папках как временный параллельный источник; собственный USN-ридер вводить вторым шагом с fallback-полной переиндексацией при переполнении журнала; событие file.changed нормализуется шиной — потребители не знают, какой источник его породил
- Gemini Live как единственный realtime-провайдер: изменение условий API или деградация качества оставит голос — основной интерфейс — без альтернативы до готовности каскадного драйвера → Событийный интерфейс драйвера с capability-флагами проектируется на этапе 5, а не «потом»; текстовый путь через batch-адаптеры — всегда рабочий второй интерфейс; каскад STT→LLM→TTS (Whisper+Piper+любая batch-модель) заложен как следующий драйвер в том же слоте — прототипировать его минимально (пусть с худшей латентностью) сразу после этапа 5
- Соло-темп: 5–7 месяцев миграции параллельно с ежедневным использованием системы; усталость и соблазн новых фич посреди рефакторинга размоют фокус → Жёсткое правило «новые фичи — только как плагины нового каркаса» (мотивация закончить каркас); этапы нарезаны на самоценные куски по 2–4 недели с видимой пользой каждого (гейт → безопасность, журнал → undo, SQLite → поиск памяти); допустимо остановиться после любого этапа — система в каждой точке лучше предыдущей
- Производительность SQLite-центричной архитектуры: единый файл БД как шина состояния между процессами может стать точкой конкуренции (busy_timeout, блокировки при тяжёлой индексации) → WAL-режим (читатели не блокируются писателем); единственный писатель — движок, индексатор пишет в отдельный файл БД (attach по需 требованию); тяжёлые данные — в файловой системе, в БД только ссылки; метрики latency запросов в supervisor с алертом при деградации
- Регрессия поведения при переносе промптов и логики planner/error_handler в новый контур: старый код содержит неявные знания (обработанные краевые случаи), которые потеряются при «переносе 10–15%» → Промпты и таблицы классификации ошибок переносить как данные без переписывания; вести журнал расхождений (старый путь логирует решения ещё 2 недели после переключения — сравнение оффлайн); краевые случаи из старого кода оформлять тестами до удаления кода
