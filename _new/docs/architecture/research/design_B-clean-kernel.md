# MARK L «Чистое ядро»: целевая архитектура персонального ассистента на 5+ лет

## 1. Философия линзы

Вариант B строится от идеальной формы, а не от существующего кода. Центральный принцип: **микроядро, которое почти ничего не умеет** — оно лишь владеет контрактами (события, действия, разрешения, состояние) и жизненным циклом. Вся функциональность, включая «родные» 25 инструментов, голос и даже awareness, — плагины, подчиняющиеся тем же контрактам, что и будущий сторонний код. Второй принцип — «простой цикл + серьёзная обвязка» (Claude Code, 12-Factor Agents): агентный контур — это один while-loop на ~200 строк, а инженерия живёт в гейте разрешений, журнале, шине и реестрах. Третий — **контракты переживают реализации** (урок Mycroft→OVOS и Wyoming): единственное, что нельзя менять часто, — это схемы событий, действий и манифестов; всё остальное сменяемо.

## 2. Процессная топология

Система — 4 постоянных процесса + эфемерные воркеры:

1. **Engine (ядро)** — один asyncio-процесс: микроядро, шина, реестр действий, гейт, агентный цикл, in-process плагины, драйверы LLM/голоса.
2. **Observer (индексатор-наблюдатель)** — отдельный процесс под `PROCESS_MODE_BACKGROUND_BEGIN` + EcoQoS: USN-журнал NTFS, WinEvents (фокус окон), процессы/приложения. Пишет производные в свой SQLite, публикует события в Engine через локальный сокет.
3. **UI** — отдельный процесс (сначала перенесённый tkinter, позже что угодно), тонкий клиент шины по WebSocket на localhost: рендерит проекции событий, очередь подтверждений, undo-тосты. Падение UI не трогает движок.
4. **MCP-хост(ы)** — Playwright-браузер и прочие тяжёлые/падучие инструменты как локальные MCP-серверы (stdio): краш-изоляция + LLM-независимый формат инструмента.
5. **Эфемерные воркеры** — эмбеддинги (fastembed/ONNX), пакетный OCR и т.п.: запускаются лениво, убиваются по простою или порогу RSS (документированная утечка fastembed #222 лечится дизайном «перезапускаемый stateless-воркер»).

## 3. Микроядро и его контракты

Микроядро (`kernel/`) — цель: менее 2000 строк, стабильных годами. Оно содержит четыре вещи:

**EventBus** — типизированный async pub/sub (~200 строк, по образцу Home Assistant core.py): диспетчеризация O(1) по типу события, per-listener try/except (упавший подписчик не роняет шину), счётчик ошибок с авто-отключением хронически падающего подписчика (связка с circuit breaker). Каждая подписка имеет ограниченную очередь с политикой переполнения: `coalesce` (файловые шквалы), `latest-wins` (UI), `block` (журнал). Каталог событий — фиксированный, ~15–20 frozen-датаклассов pydantic в прошедшем времени: `file.changed`, `window.focus_changed`, `app.installed`, `action.executed`, `action.confirm_requested`, `memory.updated`, `run.step_finished`… Каждое событие несёт `correlation_id`, протянутый через цепочку голос→план→действие→журнал. Строго: **события = факты; команды по шине не летают** — команды идут только через ActionRegistry. Шина имеет WebSocket-мост наружу (UI, Observer, отладочная консоль) с тем же контрактом сообщений — это позволяет выносить модули из процесса без смены API (паттерн OVOS messagebus).

**ActionRegistry** — единственный источник правды о действиях. Каждое действие декларируется одной записью: имя, описание, pydantic-схема аргументов (в «общем поднаборе» JSON Schema — плоско, без union, вложенность ≤2), класс риска (`read / reversible / external / irreversible`), флаги `supports_preview`, `reversible`, обратная операция, activation-триггеры. Из этой записи генерируются: (а) tool-declarations для любого LLM-адаптера, (б) секция «capability truth» системного промпта, (в) правила гейта, (г) preview-аннотации UI. Это прямое масштабирование удачного паттерна core/security.py: невозможно добавить инструмент, забыв про политику. Форма записи MCP-совместима, поэтому внешние MCP-серверы подключаются адаптером «MCP-тул → запись реестра» автоматически.

**PolicyGate (исполнитель)** — единственная точка, где действие может быть исполнено. Реализован как pluggy-hookwrapper вокруг вызова хендлера: другого пути вызвать мутирующую операцию ОС в системе физически нет — модули не импортируют `os`/`shutil` напрямую (см. ScopedRoot ниже). Подробности в §7.

**Supervisor** — запуск/останов процессов, health-мониторинг через psutil (раз в 30–60 с RSS/CPU себя и детей), политика рестарта воркеров по порогу памяти, деградационные состояния плагинов (`loaded / not_ready(retry+backoff, кап 1 час) / auth_required / error` — паттерн ConfigEntry из Home Assistant).

## 4. Хранение состояния

Всё персистентное — SQLite (WAL, `synchronous=NORMAL`, `busy_timeout`, периодический `PRAGMA optimize`), по одному файлу на домен, единственный писатель — владелец домена:

- `state.db` (Engine): execution_log планов, pending-подтверждения, конфиг-снапшоты, метрики.
- `journal.db` (Engine): saga-журнал действий с undo-метаданными + staging-каталог копий.
- `world.db` (Observer): файловый индекс, журнал активности (heartbeat-слитые интервалы), окна/приложения. FTS5 по именам/путям.
- `memory.db` (Engine, через Memory-шлюз): факты, эпизоды, FTS5 + sqlite-vec (384d, brute-force KNN — при сотнях тысяч чанков запас огромный).

Плоские JSON исчезают полностью; собственные конфиги пишутся паттерном temp-файл + `ReplaceFile` (атомарность). Правило IPC: между процессами ходят ID строк и события, не блобы. Доступ к чувствительным доменам (`world.db`, `memory.db`) — только через модуль-шлюз с политикой (урок Recall: «каждый модуль читает SQLite сам» — тот же дрейф, что executor мимо гейта); файлы БД шифруются DPAPI.

## 5. World model: актуальная модель окружения

World model — производная от журнала событий, восстановимая после любого сбоя (как индекс Everything из USN), а не единственная копия истины в RAM.

**Файлы**: bootstrap — интеграция с Everything через named pipe IPC (весь домен «мгновенный поиск + актуальный индекс» за ~50 МБ чужого отлаженного RAM); фоллбек и стратегический путь — собственный ридер MFT+USN на pywin32. USN durable: Observer догоняет изменения, случившиеся пока он не работал. Watchdog остаётся максимум на 1–2 «горячие» папки. **Окна/приложения**: `SetWinEventHook(EVENT_SYSTEM_FOREGROUND, OUTOFCONTEXT)` + message loop в потоке — событийно, без поллинга; AFK — по «времени с последнего ввода». **Компактирование**: heartbeat-слияние (ActivityWatch): часы одинаковой активности — одна строка; pulsetime = интервал + малый запас (ловушка сна машины). **Дебаунс**: тихое окно 50 мс–1 с с потолком ожидания, дедуп по пути. **Хранение двухуровневое**: только производные (пути, заголовки окон, интервалы, извлечённый текст) — вечные и дешёвые; сырых снимков экрана в v1 нет вообще. Квоты диска и retention по типам данных заданы в конфиге с первого дня, eviction oldest-first. **Чтение экрана** — по требованию: UIA с CacheRequest и узким TreeScope, OCR — только fallback. Наблюдение — opt-in по категориям, с индикатором в UI и командой «забудь X».

Текущий срез мира (активное окно, текущий проект, недавние файлы) Engine держит как иммутабельные снапшоты (frozen dataclass): изменение = новый объект + событие `*_changed(old, new)` — вход для памяти и подсказок контекста без гонок.

## 6. Обработка запросов: голос и текст

Оба входа сходятся в один **агентный цикл** — плоская история сообщений, один поток записи (Cognition: однопоточная запись, никаких параллельных агентов с правом записи).

**Роутер на входе** (правила + быстрый структурный вызов основной модели): уровень 0 — прямой ответ; уровень 1 — «лёгкий цикл» function-calling с лимитом 2–3 хода (90% трафика: «открой блокнот», «где документ про X»); уровень 2 — Plan-and-Execute: планировщик выдаёт типизированный план (список action-вызовов из реестра, с плейсхолдерами `$1` для подстановки результатов кодом), план сохраняется строками в `execution_log` (намерение ДО исполнения, результат ПОСЛЕ — WAL-паттерн Persistasaurus/DBOS), replanner вызывается только при провале шага. Рестарт процесса посреди задачи — штатная ситуация: интерпретатор пропускает COMPLETE-шаги.

**Бюджеты в ядре**: лимиты ходов/шагов/перепланирований, wall-clock таймаут шага, дневной потолок стоимости, детектор стагнации (повторный вызов с идентичными аргументами); проверка ДО платного вызова. **Steering-очередь**: реплики пользователя вклиниваются на границе итерации цикла — «стоп, не эту папку» — штатный путь, не kill. **Ошибки шага**: декларативный маппинг класс→стратегия (retry / substitute / skip / replan / escalate), ошибки остаются в контексте. **Субагенты** — только read-only разведка (сканировать папку, собрать сводку) со свежим контекстом, возвращают компактный результат; запись — всегда главный цикл.

**Голос** — драйвер, не ось. Интерфейс `VoiceSession` — семантические события (`user_speech_started/ended`, транскрипты, `tool_call(id)`, `interruption(cancelled_ids)`, `session_expiring`, аудио-чанки) + структура capability-флагов (LiveKit RealtimeCapabilities). Реализация №1 — Gemini Live драйвер: внутри — resumption-хэндлы, GoAway/timeLeft, реконнект, sliding-window compression (существующий код реюзается). Реализация №2 (позже) — half-cascade STT→LLM→TTS (локальный Whisper/Piper): голос деградирует, но не умирает при смене/отказе провайдера. Ключевое: tool-вызовы из live-сессии идут в **тот же диспетчер ActionRegistry→PolicyGate**, что и текстовые, — транспортов много, гейт один.

## 7. Разрешения, подтверждения, откат

**Пайплайн гейта** (фиксированный, для всех путей): pre-hooks → deny-правила → circuit-breaker-«пол» (операции над корнями дисков, %USERPROFILE%, каталогом самого ассистента — always-confirm, не отключается никаким режимом) → allow → ask → активный профиль сессии (`observe / normal / trusted`). Deny непереопределяем. Политика — в коде гейта; промпт лишь информирует модель (capability truth).

**4 уровня риска**: read → авто; reversible → авто + запись в журнал + тост «Перемещено 12 файлов — Отменить»; external (письмо, пост) → ask; irreversible → блокирующее подтверждение с точным payload (не пересказом). **Подтверждение — durable interrupt**: шаг получает `status=WAITING_FOR_SIGNAL` в execution_log, задача замораживается (не ест ресурсов, переживает рестарт), UI/голос показывают очередь pending; ответ — resume. Одобренный payload пиннится хэшем: `confirm_token = hash(action, args)`; расхождение при исполнении = отказ (класс багов «показали одно, исполнили другое»). Standing-grants привязаны к конкретному паттерну, видны и отзываемы в UI, имеют expiry. Для планов — preview-чеклист с risk-аннотацией каждого шага из той же таблицы; шаги с рантайм-аргументами проходят гейт повторно при исполнении.

**Откат**: `journal.db` — саговый журнал: intent-запись → операция → completion; у каждого шага идемпотентная компенсация; поверх — undo-стек Command-паттерна (батч = одна undo-единица, парные человекочитаемые подписи — «отмени последнее» голосом). Нижний слой файловых мутаций: удаление — только IFileOperation с `FOFX_RECYCLEONDELETE|FOFX_ADDUNDORECORD` (корзина + Ctrl+Z Explorer как подстраховка), перезапись — temp+ReplaceFile, перед перезаписью — staging-копия в каталог ассистента. Мутационные хендлеры обязаны: реализовать `preview() → typed diff` (контракт, не опция) и check-before-act идемпотентность. **ScopedRoot**: файловые хендлеры и плагины получают не строки путей, а capability-объект разрешённого корня (канонизация, отказ на `..`/абсолютные пути/symlink-побеги на уровне API); конструирует его только policy-слой — класс ошибок «забыл проверить путь» исчезает типом.

## 8. Память

Память — шлюз-модуль над `memory.db`: факты (subject-predicate-object с источником и временем), эпизоды (суммаризации сессий), предпочтения. Поиск гибридный: FTS5 (BM25) + sqlite-vec, слияние результатов. Экстракция — роль `memory-extractor` на **локальной модели** (llama.cpp/LM Studio через openai-совместимый адаптер, JSON Schema→GBNF гарантирует структуру даже на 4–8B): экстракция перестаёт стоить денег и уходить в облако. Эмбеддер — all-MiniLM-L6-v2 квантованный ONNX в эфемерном воркере. Компактация контекста по порогу (~90%): суммаризация в эпизод + вынос фактов. В облачную LLM уходит только производный текст релевантных срезов — сырые данные не покидают машину (граница Rewind).

## 9. Независимость от модели

Двухуровневая граница: **batch абстрагируется полностью** — 2–3 адаптера над официальными SDK (google-genai; openai-совместимый — закрывает OpenAI/Ollama/LM Studio/OpenRouter/llama.cpp; опц. anthropic), единая таксономия ошибок, нормализованные поля + сырое `native_*` рядом, fallback-обёртка поверх retry с классами ошибок и CooldownCache (~500–1000 строк своих, LiteLLM — источник паттернов, не зависимость: supply-chain история и вес неприемлемы для программы с доступом ко всем файлам). **Realtime абстрагируется только на уровне событий сессии** + capability-флаги; wire-протокол, VAD, аудиоформаты — в драйверах. **Реестр роль→модель** (`models.yaml`): `live-voice`, `planner`, `light-loop`, `memory-extractor`, `cheap-classifier`, `embedder` — provider:model, параметры, fallback-цепочка, требуемые capabilities, валидация на старте. Смена модели = одна строка конфига; 36 хардкодов и 14 загрузок ключа умирают по построению. Для каждой облачной роли — local-first альтернатива в цепочке деградации (урок OVOS/Selene).

## 10. Система расширений

Плагин = пакет с `manifest.toml` (имя, api_version, декларации действий со схемами и риском, подписки, activation-триггеры, требуемые capability: какие ScopedRoot, сеть, MCP) + pluggy-hookimpl (`register_actions`, `on_event`, `on_startup/shutdown`). Ядро читает манифесты **без импорта кода**; capability truth и policy-валидация строятся из манифестов; код грузится при первом вызове (ленивая активация VS Code — неиспользуемые плагины не стоят ни байта RAM). Базовый класс `Plugin` с авто-очисткой регистраций (Obsidian Component): подписки/таймеры/watchers снимаются при выгрузке — горячая перезагрузка при разработке. Discovery: локальная папка + entry points. Версионирование: одно целое `api_version` + правило «только аддитивные изменения» (новые поля optional — MCP-клиенты кешируют схемы). Тяжёлое/чужое — out-of-process как MCP-серверы. In-process плагины пишет один человек — процессной изоляции на каждый плагин нет сознательно (цена VS Code-модели не окупается без экосистемы недоверенных авторов).

## 11. Производительность: бюджеты как требования

Idle-бюджет Engine: **80–150 МБ RSS, <1% CPU, ноль пробуждений чаще 1/мин**; Observer: ~50–100 МБ (с Everything); UI: отдельно; тяжёлое: 0 МБ пока не вызвано. Механика: ленивые импорты тяжёлых библиотек внутри хендлеров (до `lazy import` в 3.15), профилирование `-X importtime`; событийная модель вместо поллинга (`await event.wait()`, TaskGroup, грубые допуски таймеров для коалесцинга); фоновая индексация под background-mode+EcoQoS; ленивый скоуп инструментов — в промпт попадает подмножество схем по контексту задачи (порог деградации 10–15 тулов, −85% токенов); кэш TTS-фраз; целевой бюджет отклика «конец речи → действие ≤500 мс» для лёгкого пути. Самонаблюдение: psutil-метрики в state.db, рестарт воркеров по порогу — «Jarvis съел 2 ГБ» становится невозможным состоянием.

## 12. Масштабируемость и эволюция

Масштабирование здесь — рост функций и лет, не пользователей. Швы заложены контрактами: (а) шина с WebSocket-мостом — любой in-process модуль выносится в процесс без смены API; (б) MCP-граница — инструменты переносимы в любой LLM-клиент; (в) реестр моделей — смена провайдера без кода; (г) UI — любой клиент шины (tkinter → Tauri/web); (д) event-sourced журнал действий — только один модуль, без общесистемного ES-налога. ARCHITECTURE.md и capability-описания генерируются из реестров (анти-эрозия знаний соло-проекта).

## 13. Честная цена линзы

«Чистое ядро» — это 4 процесса, ~10 контрактов и дисциплина, которую придётся соблюдать одному человеку годами. Оценка объёма: микроядро+шина+реестры ~2–3 тыс. строк, гейт+журнал+undo ~2–3 тыс., LLM-слой ~1–1,5 тыс., Observer ~2 тыс., портирование 17–18 живых тулов ~3–4 тыс. — суммарно 6–12 месяцев вечерами до паритета с прототипом. Главные риски линзы: second-system effect (соблазн строить каркас вместо фич) и «долина смерти» миграции, когда старая система уже не развивается, а новая ещё не полезна. Лекарство — строгий strangler-подход (§миграция), запрет на функциональность вне паритета до конца этапа 4 и правило: каждый этап заканчивается работающим ассистентом, которым пользуешься ежедневно. Плата принимается осознанно: за неё покупается система, где добавление инструмента — 1 файл с манифестом, смена LLM — 1 строка конфига, а «случайно повредить данные» — не свойство поведения модели, а конструктивно невозможное состояние.

## Модули

- **kernel/EventBus**: Типизированный async pub/sub: каталог ~15-20 frozen-событий (факты в прошедшем времени), per-listener изоляция ошибок, bounded-очереди с политиками coalesce/latest-wins/block, correlation_id через всю цепочку, WebSocket-мост для внепроцессных клиентов (UI, Observer) [asyncio, pydantic v2 (frozen models), websockets; ~200-300 строк своих по образцу Home Assistant core.py]
- **kernel/ActionRegistry**: Единый источник правды о действиях: схема аргументов, класс риска, preview/reversible-флаги, обратная операция. Генерирует tool-declarations для LLM, capability-truth секцию промпта, правила гейта, preview-аннотации. MCP-совместимая форма записи + адаптер внешних MCP-серверов [pydantic v2 (схемы в общем поднаборе JSON Schema), собственный код; MCP SDK для адаптера]
- **kernel/PolicyGate**: Единственная точка исполнения действий: pipeline pre-hooks→deny→circuit-breaker-пол→allow→ask→профиль; 4 уровня риска; durable-подтверждения (WAITING_FOR_SIGNAL в SQLite) с пиннингом payload хэшем; standing-grants с expiry; исполнение только через него для всех транспортов (голос, текст, план, плагин) [pluggy hookwrapper вокруг вызова хендлера, SQLite (state.db); эволюция policy-таблицы core/security.py]
- **kernel/Supervisor**: Жизненный цикл процессов и воркеров: запуск/останов, health-мониторинг RSS/CPU, рестарт stateless-воркеров по порогу памяти, состояния плагинов loaded/not_ready(backoff)/auth_required/error, фоновые приоритеты для Observer [psutil, asyncio.TaskGroup, pywin32/ctypes (PROCESS_MODE_BACKGROUND_BEGIN, EcoQoS)]
- **Journal/Undo**: Саговый журнал действий: intent-запись до, completion после; идемпотентные компенсации; staging-копии перед перезаписью; undo-стек Command-паттерна с батч-группировкой и человекочитаемыми подписями; нижний слой мутаций через IFileOperation (корзина+undo-record) и ReplaceFile [SQLite (journal.db, WAL), pywin32 (IFileOperation, ReplaceFile), staging-каталог]
- **ScopedRoot**: Capability-объекты доступа к ФС: хендлеры и плагины получают дескриптор разрешённого корня вместо строк путей; канонизация, отказ на .., абсолютные пути, symlink-побеги на уровне API; конструирует только policy-слой [собственный класс поверх pathlib, ~150 строк; идея WASI preopens]
- **Observer (world model writer)**: Отдельный процесс наблюдения: файловый индекс (Everything IPC либо свой MFT+USN ридер с durable catch-up), фокус окон через SetWinEventHook, AFK по последнему вводу, heartbeat-слияние интервалов, дебаунс с тихим окном, квоты/retention/eviction, только производные данные [pywin32 (USN Journal, SetWinEventHook), Everything named-pipe IPC, SQLite (world.db, FTS5), background-priority + EcoQoS]
- **WorldModel gateway**: Единственная точка чтения world.db для Engine, LLM-контура и плагинов: текстовые срезы мира по запросу, иммутабельные снапшоты текущего состояния (frozen dataclass, события *_changed(old,new)), policy-проверка доступа, opt-in категории наблюдения, команда «забудь X» [собственный модуль, DPAPI-шифрование файла БД, frozen dataclasses]
- **Memory**: Долговременная память за шлюзом: факты/эпизоды/предпочтения в SQLite, гибридный поиск BM25+вектор, LLM-экстракция на локальной модели со structured output, компактация контекста по порогу с выносом в эпизоды; в облако — только производный текст [SQLite (memory.db) + FTS5 + sqlite-vec (384d), fastembed/ONNX (all-MiniLM-L6-v2) в эфемерном воркере, llama.cpp/LM Studio (GBNF) для экстракции]
- **LLM layer (batch)**: Полная абстракция request/response: 2-3 адаптера над официальными SDK, единая таксономия ошибок, native_* поля рядом с нормализованными, fallback-поверх-retry по классам ошибок, CooldownCache, реестр роль→модель с capability-валидацией на старте [google-genai (новый SDK), openai (совместимый эндпоинт — Ollama/LM Studio/OpenRouter/llama.cpp), models.yaml; свой слой ~700-1200 строк, паттерны LiteLLM без зависимости]
- **Voice drivers (realtime)**: Драйверы за событийным интерфейсом VoiceSession + capability-флаги: Gemini Live (resumption-хэндлы, GoAway, реконнект, компрессия контекста) как реализация №1; half-cascade STT→LLM→TTS (Whisper/Piper) как провайдер-независимый резерв; tool-вызовы — в общий диспетчер [google-genai Live API, websockets; позже faster-whisper + Piper; интерфейс по образцу LiveKit RealtimeModel/RealtimeCapabilities]
- **Agent loop**: Однониточный цикл с плоской историей: роутер (прямой ответ / лёгкий цикл ≤3 ходов / Plan-and-Execute), план как данные в execution_log (intent до, результат после), replan по провалу, steering-очередь, бюджеты и детектор стагнации в ядре, read-only субагенты, recitation для длинных планов [asyncio, SQLite (execution_log в state.db); ~200 строк ядро цикла + обвязка]
- **Plugin host**: In-process плагины: manifest.toml читается без импорта кода, ленивая активация по триггерам, hookspecs (register_actions/on_event/on_startup), Component-автоочистка регистраций, hot reload, api_version с правилом аддитивности; out-of-process — MCP-серверы (Playwright) [pluggy, tomllib, importlib.metadata entry points; MCP SDK (stdio) для внешних]
- **UI process**: Отдельный процесс — тонкий клиент шины: чат, план-чеклист (STEP_STARTED/FINISHED проекции), очередь pending-подтверждений с точным payload и кнопкой «объясни», undo-тосты, индикатор наблюдения, управление standing-grants [сначала перенесённый tkinter поверх WebSocket-клиента; контракт позволяет заменить на Tauri/web без правки движка]

## Ключевые решения

- Микроядро <2000 строк: ядро владеет только контрактами (события, действия, разрешения, супервизия), вся функциональность — плагины, включая родные тулы и голос — Контракты переживают реализации (Mycroft→OVOS, Wyoming); соло-мейнтейнер может удержать в голове маленькое ядро; добавление функций не трогает ядро годами (ценой: Каждая фича проходит через церемонию манифест+схема+риск — писать «по-быстрому» больше нельзя; стартовая скорость разработки ниже, чем при доработке монолита)
- Свой агентный цикл и свой LLM-слой вместо LangChain/LiteLLM/CrewAI; чужое берём точечно: pluggy, MCP SDK, fastembed, sqlite-vec — Production-опыт (Octomind, Zup, депрекация планировщиков SK) показывает: цепочечные фреймворки не ложатся на stateful-цикл, а LiteLLM — неприемлемый вес и supply-chain история для программы с доступом ко всем личным файлам; нужные паттерны копируются в сотни строк (ценой: Отказ от бесплатных обновлений экосистемы: новые провайдеры и фичи адаптируем руками; свой код надо самому тестировать и документировать)
- PolicyGate как pluggy-hookwrapper — единственная точка исполнения; модули не имеют прямого доступа к os/shutil, файлы — только через ScopedRoot; deny и circuit-breaker-пол непереопределяемы — Закрывает дыру executor-мимо-гейта конструктивно, а не дисциплиной: у альтернативных путей исполнения физически нет API; политика в коде, промпт только информирует (Claude Code: enforced by harness, not by model) (ценой: Все 25 тулов придётся переписать под реестр и ScopedRoot — портирование дороже, чем «обернуть как есть»; редкие легитимные сценарии произвольных команд становятся неудобными)
- Подтверждение = durable interrupt в SQLite с пиннингом payload хэшем, 4 уровня риска, reversible-операции идут авто с тостом Undo — Развязывает такт агента и латентность человека, переживает рестарт, убирает усталость от подтверждений (confirm — дефицитный ресурс для необратимого); хэш закрывает класс багов «показали одно, исполнили другое» (ценой: Код до точки interrupt обязан быть идемпотентным — дополнительное требование к каждому мутационному хендлеру; UX-сложность очереди pending вместо простого модального диалога)
- World model на USN Journal + WinEvents в отдельном фоновом процессе; интеграция с Everything как основной путь файлового индекса; только производные данные, без записи экрана в v1 — USN durable (догоняет пропущенное), Everything закрывает целый домен за ~50 МБ чужого отлаженного кода; событийность вместо поллинга — фоновая нагрузка стремится к нулю; опыт screenpipe показывает, что медиазахват — отдельный тяжёлый домен, убивающий бюджеты (ценой: Зависимость от проприетарного Everything (митигируется своим MFT/USN-фоллбеком — за ним открытый механизм); отказ от скриншотной истории означает, что «что было на экране час назад» система не ответит)
- Двухуровневая LLM-граница: batch абстрагирован полностью (адаптеры+models.yaml), realtime — только семантические события сессии + capability-флаги, Gemini Live остаётся драйвером — Оба боевых голосовых фреймворка (LiveKit, Pipecat) пришли к этой границе через боль: полная унификация realtime протекает (issue #6002); честная граница дешевле ложной универсальности; смена batch-модели = строка конфига (ценой: Голосовой путь остаётся частично vendor-специфичным до появления half-cascade драйвера; поддержка двух режимов голоса (S2S и каскад) — двойная работа в перспективе)
- SQLite (WAL+FTS5+sqlite-vec) как единая технология хранения, по файлу на домен, доступ к чувствительным БД только через модули-шлюзы — 100k+ SELECT/с и миллисекундный FTS на десктопе с нулевой эксплуатацией; шлюзы переносят анти-дрейф паттерн на данные (урок редизайна Recall); бэкап = копия файлов; один формат для памяти, мира, журнала, планов (ценой: Никакой «настоящей» векторной БД и распределённости — при росте эмбеддингов до миллионов высокоразмерных векторов упрёмся (для single-user практически недостижимо); шлюзы добавляют слой кода там, где можно было бы просто сделать SELECT)
- UI и тяжёлые инструменты — вне процесса ядра (WebSocket-мост шины и MCP stdio), но in-process плагины без изоляции на каждый плагин — Изоляция нужна там, где реальная нестабильность (Playwright, UI-фреймворк) — Raycast/VS Code прецеденты; процессы на каждый плагин — цена без выгоды при одном авторе (Obsidian доказывает жизнеспособность in-process годами) (ценой: Баг в in-process плагине всё же может уронить движок (митигируется per-listener изоляцией и Component-очисткой); IPC добавляет латентность и сериализацию для браузерных сценариев)
- Бюджеты ресурсов и стоимости — свойства конструкторов, а не опции: idle 80-150 МБ/<1% CPU, лимиты шагов/replan/стоимости без значения «безлимитно», рестарт воркеров по порогу RSS — История AutoGPT/BabyAGI ($80 за ночь) и screenpipe (OOM 25 ГБ) показывает: опциональные лимиты не включают; на Windows нет rlimit — polling+restart единственный механизм; бюджет, заданный конструкцией, не зависит от благоразумия модели (ценой: Легитимные длинные задачи будут иногда упираться в потолки и требовать явного расширения бюджета пользователем; самомониторинг — постоянный небольшой фоновый расход)

## Миграция
Стратегия — strangler: новое ядро растёт рядом, старый MARK XXXV остаётся рабочим ассистентом до паритета. Каждый этап заканчивается системой, которой пользуешься ежедневно.

**Этап 0 — Инвентаризация и заморозка (1–2 недели).** Удалить ~30% мёртвого кода в actions/ и сироту searxng; вынести live-ключ из config; зафиксировать список из ~17–18 живых тулов и их фактические схемы. Готовность: старый код проходит smoke-тесты, список тулов и policy-таблица выгружены в декларативный формат (прото-манифесты).

**Этап 1 — Ядро контрактов (3–4 недели).** Новый пакет `kernel/`: EventBus, ActionRegistry, PolicyGate (pipeline + 4 уровня риска + пол), схемы событий. Переиспользуется: policy-таблица core/security.py (как данные), генератор capability truth. Готовность: юнит-тесты гейта (deny непереопределяем, пиннинг хэшем), шина гоняет события с correlation_id, старый main.py публикует в шину параллельно старой логике.

**Этап 2 — Действия через гейт + журнал (4–6 недель).** Портировать файловые/оконные/приложенческие тулы в реестр с манифестами и ScopedRoot; журнал+staging+undo; IFileOperation/ReplaceFile вместо os.remove/shutil. Закрываются дыры cmd_control (типизированные действия вместо сырого command) и copy_file. Переиспользуется: логика хендлеров как «карьер». Готовность: все мутации идут только через гейт (грепом по кодовой базе нет прямых os/shutil в тулах), «отмени последнее» работает.

**Этап 3 — LLM-слой (2–3 недели).** models.yaml, адаптер google-genai (только новый SDK), openai-совместимый адаптер, fallback/retry/cooldown (переиспользуются существующие circuit breakers). Удаляются 14 загрузок ключа, 36 хардкодов, старый google.generativeai. Готовность: текстовый путь работает через реестр ролей; смена planner-модели — правка одной строки.

**Этап 4 — Агентный цикл (3–4 недели).** Роутер + лёгкий цикл + Plan-and-Execute на execution_log; planner/executor/task_queue/error_handler старого контура удаляются; подтверждения — durable interrupt. Готовность: рестарт процесса посреди многошаговой задачи продолжает её; паритет функций со старым ассистентом — с этого момента старый main.py выводится из эксплуатации.

**Этап 5 — Observer и world model (4–6 недель).** Отдельный процесс: Everything IPC (или USN-ридер), SetWinEventHook, heartbeat-журнал в world.db, шлюз доступа. Переиспользуется: знания awareness-слоя о том, «что важно наблюдать»; watchdog остаётся на 1–2 горячие папки. Готовность: после суток выключения индекс догоняет изменения без рескана; idle-бюджет процесса соблюдён.

**Этап 6 — Память (2–3 недели).** Миграция JSON→memory.db скриптом, гибридный поиск, локальный экстрактор. Готовность: старые воспоминания ищутся; экстракция работает офлайн.

**Этап 7 — UI и MCP (3–4 недели).** tkinter — в отдельный процесс-клиент шины; Playwright — в MCP-сервер. Готовность: kill UI не роняет движок; краш браузера не роняет ассистента.

Суммарно 6–9 месяцев вечерами. Порядок этапов 1→4 намеренно даёт быстрый выигрыш в безопасности данных (гейт+журнал) до дорогих подсистем.

## Риски

- Second-system effect: соло-разработчик год строит «идеальные» контракты и шину, а функционального прогресса нет — мотивация умирает до паритета со старым прототипом → Жёсткий strangler-план с правилом «каждый этап завершается ежедневно используемым ассистентом»; запрет на новую функциональность до этапа 4; микроядро ограничено бюджетом строк (~2000) как явным критерием
- Долина смерти миграции: старый MARK XXXV уже заморожен, новый ещё не умеет главного (голос), пользователь возвращается к старому и новое ядро остаётся вечным side-проектом → Голосовой драйвер Gemini Live переносится как есть (код реюзается) на этапе 4, а не переписывается в конце; этапы 1-3 работают параллельно со старым main.py, публикуя в ту же шину
- Церемония контрактов душит скорость: каждый новый тул требует манифест+схему+риск+preview — «быстрые хаки» невозможны, и часть идей просто не будет реализована → Генераторы-скаффолды (создать тул из шаблона одной командой); уровень риска read освобождён от preview/undo-требований; экспериментальные тулы допускаются с пометкой experimental в личном профиле observe
- Everything как проприетарная зависимость файлового индекса: смена лицензии/смерть продукта ломает основной путь world model (прецедент Rewind→Meta) → За Everything стоит открытый механизм MFT+USN; интерфейс файлового индекса — адаптер с двумя реализациями, собственный USN-ридер пишется на этапе 5 как fallback и проверяется в CI-сценарии «Everything отсутствует»
- Реальный idle-бюджет не сходится: Python-процессы с импортами SDK, шиной и Observer суммарно превышают 150 МБ / 1% CPU, и ассистент становится заметным фоновым жильцом (судьба screenpipe) → Бюджеты — тестируемые артефакты: perf-тест на CI меряет RSS/пробуждения idle-состояния; ленивые импорты с профилированием importtime; тяжёлое — только в эфемерных воркерах; самомониторинг psutil с рестартом по порогу с первого дня
- Gemini Live остаётся фактической осью голоса: half-cascade так и не будет написан, и смена условий API (лимиты, цена, закрытие) оставляет систему без основного интерфейса на недели → Интерфейс VoiceSession с capability-флагами фиксируется на этапе 4 (драйвер обязан жить за ним); текстовый путь полностью провайдер-независим сразу; минимальный каскадный драйвер (faster-whisper + любой batch + Windows TTS) — запланированный этап 8, дешёвая деградация «хуже, но живой»
- Идемпотентность и компенсации на практике неполны: краш между исполнением шага и записью completion, либо параллельное изменение файлов другими программами, приводит к некорректному undo и подрыву доверия к «безопасности по построению» → Контракт check-before-act для всех мутационных хендлеров + интеграционные тесты с kill -9 посреди сценариев; компенсации вместо снапшот-отката (учёт чужих изменений); корзина Windows и staging-копии как двойная страховка; журнал всегда показывает фактическое состояние для ручного разбора
- Дрейф семантики событий: через два года каталог событий оброс полудокументированными полями, подписчики зависят от неявных инвариантов, отладка шины превращается в археологию («coupling without a call stack») → Каталог событий — типизированные frozen-модели в одном модуле с правилом аддитивности и api_version; correlation_id обязателен; отладочная консоль-подписчик шины с записью трейсов; генерируемый EVENTS.md как часть анти-дрейф документации
- Соло-фактор: болезнь/выгорание/смена приоритетов на 6-9-месячном горизонте миграции оставляет систему в полусобранном состоянии из двух архитектур → Каждый этап атомарно полезен и завершается тегом с работающей системой; ARCHITECTURE.md и манифесты генерируются из кода (система самоописываема для возвращения после паузы); порядок этапов ставит наибольшую ценность (гейт+журнал+undo) в первую треть пути
