Исследование закрывает пробел «жизненный цикл самой системы»: упаковка, автозапуск, self-update с откатом, миграции SQLite и бэкап/восстановление для always-on Python-демона на Windows 11 при соло-мейнтейнере.

Упаковка. Консенсус источников: для машины, которой вы владеете, замороженный бинарь (PyInstaller/Briefcase) — лишний слой. PyInstaller для долгоживущих фоновых процессов имеет два документированных капкана: onefile распаковывается во временную папку Windows, которую ОС периодически чистит, что «ломает любой нетривиальный сервис, работающий долго» (обход — --runtime-tmpdir), и hidden imports (win32timezone и весь ONNX/ctranslate2-стек) подбираются методом проб и ошибок — сборка проходит, падение в рантайме. Урок Leon подтверждён их блогом (beta.8): компиляция TCP-сервера и Python-моста под 5 платформ дала 5-кратное ускорение скиллов, но потребовала отдельного репозитория leon-binaries и постоянной кросс-платформенной сборки — это цена, оправданная только при распространении тысячам пользователей. Для одного ПК правильный стек: git-checkout по тегу + uv.lock (универсальный лок-файл с хэшами) + управляемый uv Python (пин в .python-version); `uv sync` детерминированно восстанавливает окружение за секунды. Важный нюанс uv: venv содержит симлинк на managed-интерпретатор в ~/.local/share/uv/python, поэтому venv не переносим — но при схеме «всё на одном хосте» это не мешает.

Автозапуск. Ключевое архитектурное решение: Jarvis — это НЕ Windows-служба. Служба живёт в session 0 и не имеет доступа к окнам пользователя, аудио и desktop — а awareness-слой на pywin32 и голосовой ввод этого требуют. Правильный механизм — задача Task Scheduler с триггером «At log on» (или Run whether user is logged on для headless-частей), NSSM — только если понадобится настоящий сервис-компонент. Single-instance — именованный мьютекс Win32 (CreateMutex + ERROR_ALREADY_EXISTS): ОС освобождает его при падении процесса, в отличие от PID-файлов. Graceful shutdown на Windows нетривиален: SIGTERM не существует, taskkill шлёт WM_CLOSE, а логофф — WM_ENDSESSION; библиотеки win_graceful_shutdown / graceful-shutdown закрывают эти случаи, причём консольные события не доходят до pythonw.exe — демону нужен скрытый консольный процесс или обработка оконных сообщений.

Self-update. Все изученные системы сходятся на одном паттерне: новая версия ставится РЯДОМ со старой, а не поверх. Squirrel.Windows (Slack, Discord) держит в %LocalAppData% папки app-1.0.0/app-1.0.1 + иммутабельную packages/ с полными и дельта-пакетами; переключение — атомарная смена «указателя». Tauri v2 не имеет встроенного отката: подпись minisign обязательна, а откат реализуется сервер-сайд (сервер говорит клиенту, какую версию ставить, version_comparator разрешает даунгрейд) — т.е. откат это ваша логика, не фреймворка. Home Assistant Supervisor даёт готовую транзакцию: флаг --backup делает частичный бэкап перед обновлением Core, watchdog проверяет здоровье API после старта и при провале «reanimation» должен откатить версию (issue #4590 показывает, что и у них это иногда не срабатывает — значит, откат нужно тестировать). tufup (наследник PyUpdater на python-tuf) — если захочется подписанных обновлений с патчами и защитой от rollback-атак метаданных; для личного проекта скорее избыточен, но архитектура «архив + бинарный патч + подписанные метаданные» показательна. Синтез для проекта: каталог releases/<git-tag> с собственным venv, скрипт-супервизор обновления: (1) VACUUM INTO-снапшот jarvis.db, (2) uv sync нового каталога, (3) миграции, (4) запуск нового кода в режиме golden-смоука (self-test: открыть БД, поднять шину, прогнать «capability truth» — у вас уже есть эта таблица), (5) при успехе — переключить junction/указатель «current» и перерегистрировать задачу планировщика; при провале — вернуть указатель и восстановить снапшот. Хранить N-1 (двух слотов достаточно). Важно: AWS Builders' Library формулирует критерий безопасного отката для standalone-софта — новая версия обязана читать данные, записанные старой, И НАОБОРОТ; раз это дорого гарантировать вечно, вводится явная политика даунгрейда (см. миграции).

Миграции. Для соло-проекта консенсус SQLite-форума и практиков: цикл на PRAGMA user_version по нумерованным SQL-файлам (~30 строк кода), отдельный счётчик на каждый файл БД (jarvis.db и history.db мигрируют независимо — это плюс слабой связности). Правила: каждая миграция в транзакции; выпущенную миграцию никогда не редактировать — только добавлять новую; бэкап перед миграцией обязателен; свободного места нужно не меньше размера БД (HA документирует это явно). Alembic оправдан только при SQLAlchemy и команде; caribou/yoyo — компромисс ради CLI, но ценности для одного человека мало. Home Assistant recorder — эталон линейной пошаговой схемы: константа SCHEMA_VERSION, апгрейд по одному шагу, с версии 48 миграции live (в фоне при работающей системе). Урок Syncthing: «database version 7 is too old to be upgraded directly; step via v1.27.0» — либо вечно хранить всю цепочку миграций (для SQL-файлов это дёшево), либо документировать минимальную базовую версию. Политика даунгрейда — как у Syncthing: старый код обязан отказаться стартовать, если user_version БД больше известного ему (с явным сообщением), а откат кода на N-1 после миграции версией N означает восстановление пре-миграционного снапшота (Syncthing архивирует config.xml.v31 рядом — тот же приём). Для append-only журналов и типизированных событий шины индустриальное правило (Marten, event-driven.io, эмпирическое исследование 19 продакшн-систем arXiv:2104.01146): строгая аддитивность — новые поля только опциональные, никогда не переименовывать/удалять/менять тип; версия — в имени типа события и только при действительно ломающем изменении; чтение старых событий — через upcasting-цепочку. Формализация в CI: зафиксировать реальные исторические события как fixture-файлы и гонять текущие парсеры/проекции по ним в каждом прогоне — это дешёвый и честный контракт-тест.

Бэкап. Копирование живой WAL-базы файловой операцией — подтверждённый источник тихой потери данных (свежие изменения в -wal-файле). Правильные механизмы: sqlite3 backup API (в Python встроен как Connection.backup, инкрементальный, не блокирует писателей) для регулярных снапшотов и VACUUM INTO для компактного снапшота перед миграцией. Litestream для десктопа — оверкилл: отдельный always-on процесс, который надо мониторить, Windows — второстепенная платформа, и в v0.5.6/0.5.7 была молчаливая полная потеря репликации — сами авторы экосистемы говорят, что при малой БД достаточно периодических снапшотов. Консистентность двух БД: документация WAL прямо говорит, что транзакции через ATTACH НЕ атомарны между файлами в WAL-режиме, и backup API снимает по одному файлу — общего атомарного снапшота нескольких SQLite-файлов не существует. Значит, слабая связность должна быть спроектирована: jarvis.db — единственный источник правды, бэкапится строго и часто; history.db — вытесняемый и восстановимый, бэкап best-effort или вовсе не нужен; любые ссылки из jarvis.db в history.db обязаны переживать отсутствие строки. Восстановление проверяется автоматически: еженедельная задача восстанавливает последний бэкап во временный файл, PRAGMA integrity_check, sanity-запросы, открытие текущим кодом схемы — история с dev.to («бэкапил битые файлы неделями, потому что ни разу не восстанавливал») — типовой провал.

Лицензии. Стек чист для личного многолетнего проекта: pluggy — MIT, watchdog — Apache-2.0, pywin32 — PSF-подобная, comtypes — MIT, fastembed — Apache-2.0, ONNX Runtime — MIT, sqlite-vec (именно asg017/sqlite-vec, MIT OR Apache-2.0 — не путать с sqliteai/sqlite-vector под Elastic License 2.0), faster-whisper и CTranslate2 — MIT, MCP python-sdk — MIT. Единственная жёлтая зона — Piper TTS: старый rhasspy/piper заархивирован, актуальная ветка OHF-Voice/piper1-gpl — GPL-3.0 (espeak-ng встроен). Для неразглашаемого личного использования GPL не создаёт обязательств, но чтобы плагинная экосистема осталась чистой, TTS стоит изолировать отдельным процессом за IPC-границей — что и так совпадает с целевой многопроцессной архитектурой. Slack/Discord живут на этой схеме годами. | Почему: Обновление и откат становятся O(1)-операцией смены указателя, никогда не бывает полусостояния «наполовину обновлён»; старый код физически цел до подтверждения здоровья нового. | Применимость: high — лаунчер-скрипт (batch/py) читает current и запускает releases/<tag>/.venv; на Windows вместо симлинка — directory junction или txt-указатель, что снимает вопрос привилегий на symlink.

Независим от способа упаковки. | Почему: Референс продуманного update-канала: раздельные роли ключей, защита метаданных от подмены и отката, патчи вместо полных архивов — образец, как выглядит зрелый механизм доставки. | Применимость: low — для single-user установки из собственного git-репозитория избыточен; становится актуален, только если проект начнёт распространяться другим людям. Из него стоит взять идею иммутабельного локального архива версий.
- **Изоляция GPL-компонента (Piper) за процессной границей** [github.com/rhasspy/piper issue #93 и discussion #582, OHF-Voice/piper1-gpl, k2-fsa/sherpa-onnx issue #3731]: Актуальный Piper — GPL-3.0 (espeak-ng встроен в wheel); остальной стек MIT/Apache/PSF. TTS выносится в отдельный процесс с узким IPC-интерфейсом, ядро и плагины остаются пермиссивными. | Почему: Для личного использования GPL не создаёт обязательств, но процессная изоляция сохраняет свободу замены TTS-движка (sherpa-onnx уже выпилил espeak-ng ради Apache-2.0) и совпадает с целевой многопроцессной архитектурой — лицензия просто подтверждает уже правильную границу. | Применимость: medium — на этапе выделения voice-процесса; параллельно закрепить в зависимостях именно asg017/sqlite-vec (MIT OR Apache-2.0), не sqliteai/sqlite-vector (Elastic License 2.0).

## Анти-паттерны

- **PyInstaller onefile для always-on фонового процесса** [PyInstaller mailing list / metallapan.se / гайды по pywin32-службам]: Onefile распаковывается в %TEMP%, которую Windows периодически чистит — долгоживущий процесс однажды теряет собственные файлы; hidden imports для pywin32/ONNX/ctranslate2 подбираются трwatai-and-error, сборка «зелёная», падение в рантайме. Для машины, которой владеешь, заморозка не решает ни одной реальной задачи, но добавляет постоянный сборочный налог (урок Leon: бинарная компиляция потребовала отдельного репозитория и кросс-сборок и оправдана только массовой дистрибуцией).
- **Бэкап живой WAL-базы файловым копированием** [sqlite.org forum «Hot backup database in WAL mode by copying», dev.to «I Thought My Backups Were Safe»]: Свежие транзакции лежат в -wal; копия одного .db-файла молча теряет их или несогласована с активным checkpoint. Автор из dev.to неделями «бэкапил» битые файлы и узнал об этом при первом восстановлении — судьи проекта уже ловили ровно эту ошибку.
- **Windows-служба (session 0) для user-desktop ассистента** [CodeProject «Windows Service or Schedule Task», NSSM-гайды]: Служба изолирована от пользовательской сессии: нет доступа к окнам (pywin32-awareness ослепнет), аудиоустройствам и desktop; выглядит «правильно и по-взрослому», но архитектурно противоречит назначению системы. Плюс сложность SCM-цикла и деплоя ради нулевой выгоды для single-user машины.
- **Обновление поверх единственного каталога установки (in-place, без слотов)** [контраст с Squirrel.Windows / HA Supervisor / Deployer atomic swap; AWS Builders' Library]: При падении обновления на середине нет ни работающей старой версии, ни целой новой — откат превращается в ручную археологию. Отдельная ловушка «на глаз атомарных» переключений: rm+ln или ln -sf имеют окно неатомарности; на Windows нужен junction-swap/rename, а не пересоздание ссылки.
- **Молчаливый запуск старого кода на новой схеме БД (отсутствие downgrade-политики)** [Syncthing (brick при откате: «config file version newer than supported»), SSRS «Database downgrade detected»]: Если версионирование кода и данных не связано явно, откат кода после миграции даёт либо крэш в случайном месте, либо тихую порчу данных. Долгоживущие системы решают одинаково: refuse-to-start с внятным сообщением + архивная пре-миграционная копия (config.xml.v31 у Syncthing); отсутствие этого — бомба замедленного действия в 5-летнем проекте.
- **Litestream / непрерывная репликация для десктопной БД** [litestream.io, issue #1083 (silent replication failure v0.5.6–0.5.7), oldmoe.blog]: Ещё один always-on процесс, который сам требует мониторинга, держит долгую читающую транзакцию (перехватывает checkpointing) и на Windows — второстепенная платформа; v0.5.6/0.5.7 молча теряли репликацию без единой ошибки. Для локальной БД в единицы ГБ периодический backup API покрывает риск за долю стоимости — экосистема сама называет Litestream оверкиллом для этого случая.
- **Alembic/SQLAlchemy-каркас миграций для пары SQLite-файлов соло-проекта** [SQLite-форум (консенсус-тред о migration-инструментах), levlaz.org]: Тянет ORM-зависимость и конвенции команды ради задачи, которая решается 30 строками на PRAGMA user_version; каждый лишний каркас в 5-летнем однопользовательском проекте — будущий налог на обновления и отладку. Сообщество SQLite прямо советует встраивать управление схемой в собственный код, когда БД несколько.
- **Ретроактивное редактирование выпущенных миграций и «умные» правки журнала событий** [sqliteforum.com «Versioning and Migration Strategies», event-driven.io, Marten docs]: Изменённая задним числом миграция делает состояние БД зависящим от того, КОГДА она применялась — воспроизводимость исчезает. Аналогично для append-only журнала: переименование/удаление полей или смена их типа ломает replay старых событий; единственные безопасные операции — добавление опциональных полей и новый тип события с upcaster-ом (подтверждено эмпирикой 19 продакшн-систем, arXiv:2104.01146).
- **Самообновляющийся апдейтер без пиновки (обновлятор обновляет сам себя)** [HA Supervisor (auto-update, откат — «dirty workaround» по признанию форума), issue #4590]: Когда компонент, отвечающий за откат, сам обновляется автоматически и не имеет собственного слота отката, его сбой лишает систему последней линии обороны — у HA это регулярный источник инцидентов. Апдейтер должен быть маленьким, скучным, версионируемым отдельно и меняться реже всего остального.
