Изучены первоисточники по девяти системам (LangGraph, AutoGen v0.4, CrewAI, Semantic Kernel, smolagents, Open Interpreter, OpenManus, Claude Code / Claude Agent SDK, MCP) и три опорных инженерных текста: Anthropic «Building Effective Agents», HumanLayer «12-Factor Agents» и Cognition «Don't Build Multi-Agents», плюс production-разборы отказа от LangChain (Octomind, Zup).

Главный вывод: индустрия сошлась на формуле «простой однониточный цикл + серьёзная инфраструктура вокруг него». Claude Code — самый показательный пример: главный цикл (внутреннее имя nO) — это буквально while-loop с плоской историей сообщений и ~14 инструментами, который крутится, пока модель возвращает tool calls. Вся инженерия живёт вокруг: пайплайн разрешений с фиксированным порядком проверки (hooks → deny-правила → allow → ask → permission mode → callback, причём deny побеждает всегда, даже в bypass-режиме), компактация контекста при ~92% заполнения с выносом важного в markdown-память, очередь h2A для инъекции пользовательских команд в работающего агента без рестарта, субагенты как свежие циклы с изолированным контекстом для scoped-задач, append-only хранение сессий. Тот же тезис независимо формулируют Anthropic («самые успешные реализации не используют сложные фреймворки, а строятся из простых композируемых паттернов») и 12-Factor Agents (Factor 8: «own your control flow» — владей своим while-loop, потому что пауза между выбором инструмента и его вызовом — то самое место, где живёт подтверждение пользователя).

Для вашего проекта это прямо означает: не брать тяжёлый фреймворк как каркас, а рефакторить main.py в собственный компактный цикл. Опыт отказов это подтверждает: Octomind и Zup ушли с LangChain именно потому, что цепочечная модель не ложится на циклический stateful-агентный паттерн, а отладка через 5 слоёв абстракций хуже, чем свой код; LangChain в v1.0 сам признал критику и переориентировался на «голый» agent loop.

Самая ценная механика для ваших подтверждений — у LangGraph. Checkpointer сохраняет снапшот состояния графа на каждом супер-шаге в SQLite/Postgres, thread_id работает курсором, interrupt() приостанавливает выполнение с персистентным состоянием на неограниченное время, Command(resume=...) подаёт ответ человека в ожидающий узел. Это превращает «подтверждение опасной операции» из блокирующего диалога в данные: pending-операция переживает рестарт процесса, её можно показать в UI, отредактировать параметры, отклонить. Важный документированный нюанс — идемпотентность: при resume узел перевыполняется с начала, поэтому побочные эффекты до interrupt должны быть идемпотентны. Сам LangGraph можно взять как библиотеку (он работает без LangChain, SQLite-чекпоинтер — отдельный пакет, тянет только langgraph-checkpoint и langchain-core транзитивно), но, по моей оценке, для одного пользователя нужный паттерн — «сериализуемое состояние задачи + interrupt как объект + журнал» — достаточно мал, чтобы реализовать его самому поверх вашей policy-таблицы и не принимать зависимость от экосистемы LangChain на 5 лет.

Второй важный урок — судьба планировщиков. Semantic Kernel официально депрецировал и удалил Stepwise/Handlebars-планировщики: отдельный LLM-шаг «сгенерируй план, потом исполняй» удваивал число вызовов и поверхность ошибок (в их бенчмарке 1869 токенов у Stepwise против 755 у нативного function calling), а ReAct теперь «вшит» в сами модели. OpenManus с его цепочкой наследования ReActAgent → ToolCallAgent → PlanningAgent → Manus и PlanningFlow — как раз архитектура вчерашнего дня. Claude Code решает планирование иначе: TODO-список — это просто инструмент (TodoWrite), план живёт в контексте той же беседы и пересматривается по ходу. Ваш контур planner→executor→task_queue стоит схлопнуть в один цикл с planом-в-контексте; заодно это закрывает архитектурную дыру executor-мимо-гейта: в Claude Agent SDK любой путь исполнения, включая субагентов, проходит через один и тот же фиксированный пайплайн разрешений — это ровно обобщение вашего удачного паттерна «policy-таблица + capability truth» на все пути исполнения.

Мультиагентность: Cognition (Devin) аргументирует, что параллельные агенты с правом записи — «заманчивая идея, плохая на практике» из-за потери контекста при передаче (принцип: share full traces, not messages); их апдейт 2026 допускает только паттерны, где несколько агентов дают интеллект, но записи однопоточны. Критика CrewAI из Towards Data Science подтверждает: иерархический manager-worker не работает как задокументировано — менеджер не координирует, задачи всё равно идут последовательно, растут латентность и лишние tool calls. Для single-user desktop-ассистента вывод однозначен: один главный цикл, субагенты — только read-only (поиск по файлам, анализ), запись — всегда через главный цикл и гейт.

AutoGen v0.4 полезен не своим distributed actor-рантаймом (для одного ПК это оверинжиниринг), а двумя вещами: мотивацией редизайна (пользователи требовали observability и контроля — Microsoft перестроила всё вокруг событий и OpenTelemetry) и слоистостью Core / AgentChat / Extensions с чётким разделением ответственности. Ваш недостающий event bus — это внутрипроцессный async pub/sub на пару сотен строк: awareness публикует события мира, движок и UI подписываются, модули перестают дёргать друг друга напрямую, а UI выносится в отдельный процесс (прецедент — Claude Code как тонкий CLI поверх Agent SDK).

MCP стоит принять как форму контракта, но дозированно. Архитектура host-client-server с тремя примитивами (tools / resources / prompts), JSON-RPC, stdio-транспорт для локальных серверов и principle «безопасность принадлежит хосту, не протоколу» — зрелый дизайн для границы расширения: внутренний реестр инструментов делаете MCP-совместимым по форме (name, description, JSON Schema входов + ваша колонка риска), тогда сторонние MCP-серверы подключаются адаптером, а свои 25 инструментов остаются in-process без сетевой прослойки. Документированная обратная сторона MCP — токенная цена: GitHub-сервер съедает 17,6k токенов схем на запрос, практический потолок — 10–15 активных инструментов, дальше модель начинает путать похожие тулы; лечится ленивой подгрузкой схем (Anthropic Tool Search сообщает −85% токенов). Для вас это аргумент за динамический скоуп: не все 25+ схем в каждом промпте, а подмножество по контексту задачи.

smolagents и Open Interpreter — источники идей и предостережений. smolagents доказывает, что ядро агента умещается в ~1000 строк (MultiStepAgent), и что code-as-action выразительнее JSON-вызовов — но требует песочницы (E2B/Docker); для ассистента, чья ценность — сохранность данных пользователя, генерация произвольного Python как способ действия неприемлема: policy-гейт не может статически оценить риск произвольного кода, аудит и откат разваливаются. Открытая правда Open Interpreter: их главный барьер — confirm-перед-каждым-исполнением плюс «выравнивание модели» как механизм защиты — это то, чего надо избегать (защита должна быть структурной, в коде гейта, а не в благоразумии модели). Зато его ставка на LiteLLM как провайдер-независимый слой — проверенный путь к LLM-независимости; для Gemini Live придётся абстрагировать выше — на уровне «сессии» (streaming-аудио-канал + текстовый tool-calling канал как две реализации одного интерфейса), это моя оценка, не первоисточник.

Итоговая рекомендация по «библиотека vs идеи»: как библиотеки — LiteLLM (адаптер моделей), MCP SDK (граница плагинов), возможно langgraph-checkpoint как референс формата снапшотов; как источники идей — Claude Code (цикл, пайплайн разрешений, компактация, steering), LangGraph (interrupt/checkpoint-паттерн), AutoGen (слои, события), 12-factor (управление состоянием); не брать вовсе — CrewAI, OpenManus, полный LangChain, планировщики SK.

## Идеи

- **Однониточный главный цикл с плоской историей** [Claude Code (nO loop) — PromptLayer, ZenML, arXiv 2604.14228]: Один while-loop: модель отвечает tool calls — исполняем и продолжаем; отвечает текстом — возвращаем управление пользователю. Одна плоская история сообщений, без конкурирующих агентских персон. | Почему: Максимальная предсказуемость и отлаживаемость; вся сложность выносится в обвязку (разрешения, компактация, хуки), которая тестируется отдельно от LLM. Подтверждено как осознанный выбор Anthropic для production-агента. | Применимость: high — это готовая целевая форма рефакторинга main.py: ~200-строчное ядро цикла вместо 1800-строчного оркестратора; planner/executor/task_queue схлопываются в этот цикл.
- **Фиксированный пайплайн разрешений для всех путей исполнения** [Claude Agent SDK permissions (code.claude.com/docs/en/agent-sdk/permissions)]: Каждый tool call проходит строгую последовательность: pre-hook → deny-правила → allow → ask → режим → callback; deny побеждает всегда, субагенты наследуют режим и не могут его ослабить. | Почему: Один enforcement point без обходных путей; документированные gotchas SDK (allow-правило молча пропускает callback) показывают, чего избегать. Это прямое обобщение вашей policy-таблицы из core/security.py. | Применимость: high — закрывает главную дыру прототипа (executor мимо гейта): диспетчер инструментов становится единственной точкой вызова, агентный путь физически не может её обойти.
- **Подтверждение как персистентный interrupt + resume** [LangGraph interrupts (docs.langchain.com/oss/python/langgraph/interrupts)]: Опасная операция не блокирует диалог, а сохраняет снапшот состояния задачи и создаёт pending-объект; ответ пользователя подаётся через resume-команду; состояние переживает рестарт процесса. | Почему: Развязывает такт агента и латентность человека; даёт бесплатно: очередь подтверждений в UI, правку параметров операции перед одобрением, аудит отклонённых действий. Документированное требование — идемпотентность кода до точки interrupt. | Применимость: high — реализовать самостоятельно поверх SQLite (паттерн мал), не принимая зависимость от LangChain; ложится на голосовой сценарий: «переименовать 40 файлов? — да» как отдельная реплика.
- **План как инструмент в контексте, а не отдельный planner-LLM** [Claude Code TodoWrite; Semantic Kernel — депрекация планировщиков (devblogs.microsoft.com/semantic-kernel/the-future-of-planners-in-semantic-kernel)]: Агент ведёт TODO-список вызовом обычного инструмента; план лежит в той же истории и пересматривается по ходу. Отдельный шаг «LLM генерирует план → исполнитель выполняет» упразднён. | Почему: SK удалил планировщики с числами: двойная поверхность ошибок и 1869 токенов против 755 у нативного function calling; ReAct уже встроен в современные модели. | Применимость: high — прямое указание, что делать с контуром planner→executor→task_queue: удалить как отдельные сущности, оставить TODO-tool и очередь отложенных задач как хранилище.
- **Реестр инструментов как единый источник правды** [MCP tool primitives + ваш паттерн capability truth; 12-Factor Agents (Factor 4: tools are just structured outputs)]: Каждый инструмент декларирует в одном месте: имя, описание, JSON Schema входов, класс риска, необходимость подтверждения, побочные эффекты/откатываемость. Из этой декларации генерируются схемы для LLM, правила гейта и секция промпта. | Почему: Расширяет ваш удачный анти-дрейф-паттерн: невозможно добавить инструмент, забыв про политику; tool call — это просто валидируемый structured output, а не магия фреймворка. | Применимость: high — эволюция существующей policy-таблицы; MCP-совместимая форма записи даёт бесплатную интеграцию сторонних MCP-серверов через адаптер.
- **MCP как граница плагинов (stdio, out-of-process)** [modelcontextprotocol.io/docs/learn/architecture]: Сторонние и тяжёлые расширения подключаются как локальные MCP-серверы по stdio с capability negotiation; ядро остаётся хостом, который владеет политикой разрешений. | Почему: Стандарт с экосистемой готовых серверов; изоляция по процессам (упавший плагин не роняет ассистента); принцип «безопасность у хоста» совпадает с вашей архитектурой центрального гейта. | Применимость: medium — не переводить свои 25 инструментов на MCP (лишняя прослойка), но сделать реестр MCP-совместимым и держать адаптер для внешних серверов; это и есть план расширяемости без переписывания ядра.
- **Ленивый скоуп инструментов вместо «всё в каждый промпт»** [Anthropic MCP Tool Search / code-execution-with-mcp; критика tool bloat (thenewstack.io)]: В промпт попадает подмножество схем инструментов, релевантное текущему контексту/задаче; остальные подгружаются по запросу или через поиск по каталогу. | Почему: Документированные цифры: схемы съедают до 40-50% контекста, порог деградации выбора — 10-15 инструментов, ленивая подгрузка даёт −85% токенов. Меньше токенов — быстрее отклик и дешевле, что критично для realtime-голоса. | Применимость: high — у вас уже 25 инструментов и будет больше; группировка по доменам (файлы/окна/браузер/веб) с активацией по контексту awareness-слоя.
- **Внутрипроцессная шина событий (actor-паттерн в миниатюре)** [AutoGen v0.4 event-driven core (microsoft.com/en-us/research/blog/autogen-v0-4...)]: Модули общаются асинхронными сообщениями через pub/sub-шину вместо прямых вызовов: awareness публикует события мира, движок, память и UI подписываются. | Почему: Microsoft перестроила AutoGen именно ради observability и развязки модулей; для одного ПК достаточно asyncio-шины на ~200 строк — все выгоды развязки без распределённого рантайма. | Применимость: high — закрывает заявленную боль «нет шины, модули дёргают друг друга»; заодно готовит вынос tkinter UI в отдельный процесс (события сериализуемы).
- **Субагент как свежий контекст для read-only подзадач** [Claude Code Task tool; Cognition «Don't Build Multi-Agents» / «Multi-Agents: What's Actually Working»]: Для объёмных изолированных подзадач (просканировать папку, собрать сводку) порождается отдельный цикл со своим контекстом, возвращающий компактный результат; запись в мир — только через главный цикл. | Почему: Решает загрязнение контекста без рисков мультиагентности: Cognition документирует, что работают только схемы с однопоточной записью; полная параллельная автономия ломается на потере контекста. | Применимость: medium — полезно для «наведи порядок в Downloads» (разведка субагентом, план и исполнение — главным циклом); вводить после стабилизации ядра.
- **Steering-очередь: инъекция команд в работающего агента** [Claude Code h2A queue (PromptLayer)]: Асинхронная очередь между вводом пользователя и циклом агента: новые реплики вклиниваются на границе итерации, позволяя скорректировать или отменить задачу без рестарта. | Почему: Для голосового интерфейса это разница между «ассистентом» и «скриптом»: пользователь говорит «стоп, не эту папку» посреди выполнения — и это штатный путь, а не kill. | Применимость: high — у вас уже есть 4 asyncio-задачи аудиоконтура; добавить очередь между listen и главным циклом с проверкой на каждой итерации.
- **Провайдер-независимость через LiteLLM-подобный адаптер + абстракция сессии** [Open Interpreter (LiteLLM как фундамент); smolagents (model-agnostic дизайн)]: Единый интерфейс модели (completion + tool calling + streaming) с реализациями под облачные и локальные модели; realtime-аудио Gemini Live оформляется как отдельная реализация интерфейса «сессии», а не как ядро системы. | Почему: Проверено двумя model-agnostic проектами; убирает 36 хардкодов имён моделей и два параллельных SDK в одну точку конфигурации. | Применимость: high —条件 выхода из vendor lock-in; text-путь переводится на адаптер сразу, voice-путь остаётся Gemini-специфичной реализацией интерфейса до появления альтернатив.
- **Компактация контекста по порогу с выносом в долгую память** [Claude Code wU2 compressor (PromptLayer)]: При заполнении контекста (~92%) история суммаризуется, важные факты выносятся в простой персистентный документ/хранилище, доступный следующим сессиям. | Почему: Простое решение проблемы длинных сессий без векторных БД на старте; Claude Code демонстрирует, что markdown + grep достаточно для production-агента. | Применимость: medium — для длинных голосовых сессий; сочетается с планами заменить плоский JSON памяти на SQLite с FTS-поиском.

## Анти-паттерны

- **Фреймворк-каркас с глубокими абстракциями поверх цикла** [Octomind «Why we no longer use LangChain», кейс Zup (arXiv 2604.09805), HN-обсуждение]: Абстракции прячут промпты и control flow; любое нестандартное требование (динамическая смена инструментов mid-run, свой критерий останова) превращается в борьбу с фреймворком и отладку его внутренностей через 5 слоёв. Octomind и Zup документированно выбросили LangChain и «просто стали писать код»; LangChain в v1.0 признал критику. Для проекта на 5+ лет с одним сопровождающим зависимость от быстро мутирующей экосистемы — отдельный риск.
- **Отдельный LLM-планировщик (plan-then-execute как два LLM-шага)** [Semantic Kernel — депрекация и удаление Stepwise/Handlebars planners; OpenManus PlanningFlow]: Удваивает вызовы модели и поверхность ошибок (план может быть неверен, исполнение может разойтись с планом), жжёт токены (1869 против 755 в бенчмарке SK) и повышает латентность — смертельно для голосового отклика. Microsoft удалила планировщики из пакета целиком: ReAct теперь встроен в модели. Ваш контур planner→executor — эта же архитектура.
- **Иерархический менеджер-агент, делегирующий работникам (CrewAI-стиль)** [Towards Data Science «Why CrewAI's Manager-Worker Architecture Fails»]: По разбору Towards Data Science, менеджер в CrewAI не координирует реально: задачи выполняются последовательно, добавляются лишние tool calls, некорректные рассуждения и высокая латентность. Ролевая «корпоративная» метафора — оверинжиниринг для single-user ассистента, где нет независимых рабочих потоков.
- **Параллельные автономные агенты с правом записи** [Cognition «Don't Build Multi-Agents» + апдейт «Multi-Agents: What's Actually Working»]: Передача задачи субагенту без полного трейса — игра в испорченный телефон: нюансы многоходового диалога теряются, агенты принимают конфликтующие решения. Cognition (Devin) публично прошла путь «не стройте мультиагентов» → «работают только схемы, где записи однопоточны». Для ассистента, трогающего реальные файлы пользователя, конфликтующие записи — прямой путь к повреждению данных.
- **Code-as-action на живой машине пользователя** [smolagents CodeAgent, Open Interpreter]: Генерация произвольного Python выразительна, но центральный policy-гейт не может классифицировать риск произвольного кода — рушатся подтверждения по классам операций, аудит и откат. Сами smolagents требуют песочницу (E2B/Docker), а Open Interpreter честно признаёт, что частично полагается на «выравнивание модели» как защиту. Это ровно та дыра обхода allowlist через `command`, что уже найдена в вашем cmd_control: действия должны быть типизированными инструментами, а не кодом.
- **Все схемы инструментов в каждом промпте** [Критика MCP tool bloat (The New Stack, SEP-1576, lunar.dev)]: Схемы съедают до 40-50% контекста (GitHub MCP — 17,6k токенов на запрос); свыше 10-15 инструментов модель начинает путать похожие тулы, зависать на выборе и галлюцинировать несуществующие вызовы. Растут стоимость и латентность каждого хода — для realtime-голоса это заметно на слух.
- **Распределённый actor-рантайм и event-sourcing-платформа для одного ПК** [AutoGen v0.4 Core, LangGraph Platform]: Кросс-процессные рантаймы, gRPC-доставка, оркестрация на Kubernetes решают проблемы масштабирования на множество пользователей и машин, которых у single-user desktop-приложения нет. Плата — фоновые ресурсы, сложность деплоя и отладки, которые противоречат целям «минимальный фоновый CPU/RAM» и «сопровождает один человек». Брать идею (события, развязка), не платформу.
- **Обходные пути вокруг пайплайна разрешений** [Задокументированные gotchas Claude Agent SDK (allow-правило молча пропускает canUseTool; bypassPermissions наследуется всеми субагентами)]: Любой второй путь исполнения (агентный executor, «доверенный» режим, прямые вызовы между модулями) со временем расходится с центральной политикой — это уже случилось в вашем прототипе (executor мимо гейта). Уроки SDK: порядок проверок фиксирован и одинаков для всех путей, deny вычисляется первым и не переопределяется, субагенты не могут получить больше прав, чем родитель.
- **Память диалога только в оперативке процесса** [OpenManus (in-memory PlanningTool), прототип MARK XXXV]: Состояние задачи, план и pending-подтверждения, живущие только в памяти процесса, умирают при краше/рестарте — длинные задачи нельзя ни возобновить, ни разобрать постфактум. LangGraph демонстрирует альтернативу: чекпоинт каждого шага в SQLite как норма, а не как фича «для энтерпрайза».
