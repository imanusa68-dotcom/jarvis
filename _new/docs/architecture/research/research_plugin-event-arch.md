Изучены четыре зрелые системы расширений (VS Code, Home Assistant, Obsidian, pluggy/pytest) плюс MCP как «плагин для LLM-эпохи», и отдельно — событийные архитектуры: pub/sub внутри процесса, backpressure, event sourcing и типовые провалы EDA. Главный вывод: для системы, которую сопровождает один человек, правильная комбинация — in-process плагины на хук-контрактах + один типизированный асинхронный event bus + декларативные манифесты с ленивой активацией; отдельный процесс — только там, где есть реальная нестабильность (Playwright-браузер, UI), и лучше всего в форме MCP.

Что подтверждено первоисточниками. VS Code выносит расширения в отдельный extension host process по явно названной причине: тысячи недоверенных сторонних расширений не должны влиять на старт и отзывчивость редактора; коммуникация — двунаправленный RPC с полной JSON-сериализацией (объекты по ссылке передать нельзя), DOM для расширений закрыт. Это дорогое решение: анализ Mozilla по process isolation даёт ~7–10 МБ приватной памяти на минимальный процесс плюс IPC-латентность. Ключевая же переносимая идея VS Code — не процесс, а декларативность: манифест package.json с activation events и contribution points читается при старте БЕЗ исполнения кода расширения; команды, меню и языки появляются в UI до загрузки JS, а код грузится при первом реальном использовании (onCommand, onLanguage, workspaceContains). Расширения, не использованные в сессии, вообще не потребляют память. Второй урок VS Code — политика API: «We DO NOT want to break API», новые API живут как proposed (только Insiders, публиковать нельзя), финализируются после итераций; совместимость — через minAppVersion/engines.

Home Assistant — лучший образец событийного ядра. Core = четыре части: event bus («бьющееся сердце»), state machine (иммутабельные снапшоты состояний, каждое изменение — событие state_changed), service registry (слушает call_service) и timer. Критичные детали реализации из core.py: диспетчеризация O(1) по словарю тип→слушатели; каждый вызов слушателя и каждого event filter обёрнут в try/except с _LOGGER.exception и continue — упавший слушатель не роняет ни шину, ни соседей. Отказоустойчивость интеграций оформлена как state machine конфиг-записей: ConfigEntryNotReady → автоматический retry с экспоненциальным backoff (кап 1 час), ConfigEntryAuthFailed → reauth-flow, ConfigEntryError → терминальная ошибка; интеграциям запрещено самим логировать retry. Важно: HA разделяет события (факты: state_changed) и сервисы (команды: call_service с registry) — это готовый ответ на вопрос «как не сделать шину ради шины»: команды идут через реестр сервисов с валидацией, события — только уведомления о свершившемся.

Obsidian доказывает, что in-process плагины жизнеспособны годами, если ядро даёт дисциплину жизненного цикла: Plugin extends Component; всё, что зарегистрировано через registerEvent/registerDomEvent/registerInterval/addCommand в onload(), автоматически отписывается при onunload(); дочерние компоненты выгружаются каскадом. Это даёт горячую перезагрузку плагина без утечек — при одном авторе это ценнее краш-изоляции. Версионирование простое: minAppVersion в manifest.json + requireApiVersion() в рантайме.

pluggy (экстрагирован из pytest) — эталон механизма in-process хуков: хост объявляет hookspec (контракт), плагины дают hookimpl; вызов хука по умолчанию собирает список результатов всех реализаций (LIFO), firstresult=True останавливается на первом не-None, tryfirst/trylast управляют порядком, hookwrapper позволяет обернуть исполнение остальных (идеально для гейта разрешений и журналирования!). Discovery — через стандартные Python entry points (importlib.metadata, [project.entry-points."jarvis.plugins"] в pyproject.toml) — это официальный механизм из Python Packaging Guide, работает для pip-установленных плагинов; для локальной папки плагинов достаточно pm.register(). Кейс-стади Эли Бендерски честно отмечает: pluggy — «shallow API», и большинство проектов всё равно катают своё; но валидация сигнатур, порядок вызова и wrappers — то, что скучно писать самому.

MCP решает смежную задачу: stdio-транспорт + JSON-RPC, динамическое обнаружение возможностей через tools/list, resources/list, версия протокола согласуется при initialize. Для проекта это двойной выигрыш: тяжёлые/нестабильные инструменты (Playwright!) выносятся из ядра с краш-изоляцией, и одновременно инструменты становятся доступны любому LLM-клиенту — прямое попадание в цель LLM-независимости. Подтверждённая ловушка: LLM-клиенты кешируют схемы тулов, поэтому изменение схемы должно быть аддитивным (новые поля — optional).

По событийной части. Консенсус источников (Fowler, event-driven.io): event sourcing — паттерн хранения на уровне МОДУЛЯ, не всей системы; применять там, где нужны аудит, replay и «состояние на момент T». Для Jarvis это ровно один модуль — журнал действий (action journal) для отката файловых операций; world model и память событийно-сорсить не нужно. Для шины в asyncio подтверждённые практики: bounded queue как естественный backpressure (безлимитная очередь при медленном потребителе = рост памяти), политика latest-wins/coalescing для бурстовых источников (watchdog даёт шквалы файловых событий), Python 3.13 Queue.shutdown для корректного завершения. Разбор провалов EDA (Wix, Temporal, CodeOpinion) единодушен: «loose coupling» шины — иллюзия наполовину, связность переезжает в схемы и семантику событий («coupling without a call stack»); события «обо всём» не значат ничего; без correlation ID и каталога событий отладка превращается в архео��огию логов. Лекарство — маленький фиксированный каталог типизированных событий (дата-классы со схемой), имена в прошедшем времени, correlation ID через всю цепочку голос→план→действие→журнал.

Применение к проекту (моя экспертная сборка). 1) Ядро остаётся одним asyncio-процессом; выделяются два внешних: UI (tkinter и так надо отделять от движка) и MCP-хост для браузера/тяжёлых тулов. Отдельный процесс на каждый плагин — оверинжиниринг: он у VS Code существует ради недоверенной экосистемы тысяч авторов, которой здесь нет. 2) Каждый из 25 тулов и каждый awareness-модуль становится плагином: манифест (имя, риск-уровень, activation triggers, схема аргументов) + hookimpl. Секция «capability truth» промпта генерируется из манифестов не загружая код — расширение уже удачного паттерна с policy-таблицей; сама policy-таблица валидируется против манифестов на старте. 3) Все вызовы действий — только через service registry, где единственный pluggy-hookwrapper реализует гейт разрешений и журналирование; это конструктивно закрывает дыру executor-в-обход-гейта: у executor физически нет другого пути вызвать действие. 4) Шина событий развязывает слои так: awareness публикует факты (file.changed, window.focus_changed, app.installed), память и world model — подписчики, UI — подписчик с latest-wins очередью, память публикует memory.updated, реестр действий публикует action.executed/action.confirmed — итого каталог из ~15 событий покрывает всё; шина — один класс на ~150 строк с per-listener try/except по образцу HA, никакого брокера. 5) Плагин-API версионируется одним целым api_version в манифесте + правило «только аддитивные изменения» (VS Code-стиль); semver-церемония одному мейнтейнеру не нужна. Такой каркас — манифесты, хуки, шина, реестр сервисов — суммарно меньше тысячи строк, но задаёт швы, по которым система сможет расти 5+ лет без переписывания ядра.

## Идеи

- **Декларативный манифест плагина + ленивая активация** [VS Code (activation events, contribution points)]: Плагин описывает свои команды/тулы/триггеры в статическом манифесте; ядро читает манифесты при старте без импорта кода и загружает модуль только при первом реальном использовании (аналог onCommand/onLanguage). | Почему: VS Code подтверждает: неиспользованные расширения не потребляют память вообще; UI и промпт можно построить из манифестов до загрузки кода. Прямо бьёт в цель «минимальный фоновый CPU/RAM». | Применимость: high — 25 тулов Jarvis получают manifest.toml (имя, риск, схема аргументов, activation); секция capability truth промпта и policy-валидация генерируются из манифестов; код тула импортируется при первом вызове.
- **События = факты, сервисы = команды (две разные подсистемы)** [Home Assistant (event bus + service registry)]: HA разделяет event bus (уведомления о свершившемся: state_changed) и service registry (вызов действий: call_service с регистрацией и валидацией). Запросы «сделай X» не летают по шине как события. | Почему: Убирает главный источник «шины ради шины» — request/response через pub/sub, который делает трассировку невозможной. Команды остаются синхронными вызовами с точкой контроля. | Применимость: high — action-слой Jarvis оформляется как service registry; awareness/память/UI общаются событиями. Это структурный ответ на вопрос «какие события должны существовать»: только факты в прошедшем времени.
- **Per-listener изоляция ошибок в диспетчере шины** [Home Assistant core.py]: Каждый вызов слушателя и каждого фильтра события обёрнут в try/except с логированием (_LOGGER.exception) и continue — упавший подписчик не влияет ни на публикатора, ни на других подписчиков. | Почему: Дешёвая (десяток строк) устойчивость: баг в одном awareness-модуле не роняет голосовой контур. Проверено на системе с 2000+ интеграций. | Применимость: high — обязательное свойство самописной шины Jarvis; плюс счётчик ошибок на подписчика для авто-отключения хронически падающего плагина (связка с существующими circuit breakers).
- **Hookspec/hookimpl-контракты через pluggy** [pluggy / pytest; кейс-стади Eli Bendersky]: Хост объявляет спецификации хуков, плагины — реализации; библиотека даёт валидацию сигнатур, порядок (tryfirst/trylast), firstresult и hookwrappers, плюс discovery через entry points. | Почему: Production-proven ядро плагинности в ~1 модуль без процессов и RPC; контракт заставляет продумать, что именно доступно плагинам, вместо «импортируй что хочешь» (текущая болезнь прототипа). | Применимость: high — pluggy как готовая зависимость (крошечная, стабильная); hookspecs: register_tools, on_event, on_startup/shutdown. Альтернатива — своя реализация на 200 строк, но wrappers и валидацию сигнатур скучно писать самому.
- **Гейт разрешений как hookwrapper вокруг вызова действия** [pluggy hookwrapper + HA service registry (синтез, моя оценка)]: Единственный путь исполнить действие — вызов через реестр, где wrapper-хук выполняет проверку policy-таблицы, подтверждение и журналирование до/после. | Почему: Закрывает архитектурно (а не дисциплиной) незакрытую дыру agent/executor в обход core/security.py: другого пути вызвать действие в системе не существует. | Применимость: high — главное структурное исправление прототипа; policy-таблица остаётся единственным источником правды и валидируется против манифестов на старте.
- **Component-паттерн авто-очистки регистраций** [Obsidian Plugin API (registerEvent/registerInterval, onload/onunload)]: Всё, что плагин регистрирует (подписки, таймеры, watchers), трекается его Component-объектом и автоматически снимается при выгрузке; дочерние компоненты выгружаются каскадом. | Почему: Делает выгрузку/горячую перезагрузку плагина безопасной без ручного bookkeeping — для in-process системы это замена краш-изоляции: плагин можно просто перезагрузить. | Применимость: high — базовый класс JarvisPlugin с bus.listen()/add_watcher()/add_interval(), возвращающими авто-трекаемые регистрации; hot reload плагина при разработке в одиночку экономит часы.
- **Config-entry lifecycle с NotReady-retry и backoff** [Home Assistant (ConfigEntryNotReady / ConfigEntryAuthFailed / ConfigEntryError)]: Setup интеграции различает три исхода: «пока не готово» → авто-retry с экспоненциальным backoff (кап 1 ч), «нужна реавторизация» → отдельный flow, «сломано» → терминальная ошибка; сам плагин про retry не логирует. | Почему: Система стартует всегда, деградируя по частям; недоступный сервис (нет сети после ребута) сам восстановится без рестарта — типовая боль desktop-ассистента. | Применимость: medium — нужно для плагинов с внешними зависимостями (поиск, погода, LLM-провайдер, browser); для чисто локальных тулов достаточно loaded/error.
- **MCP-сервер как out-of-process форма плагина** [Model Context Protocol (stdio transport, tools/list, версия при initialize)]: Тяжёлый или нестабильный инструмент оформляется как локальный MCP-сервер (stdio, JSON-RPC): ядро запускает процесс, обнаруживает тулы через tools/list, версия протокола согласуется при initialize. | Почему: Даёт краш-изоляцию именно там, где она нужна (Playwright-браузер — самый тяжёлый и падучий компонент), и одновременно стандартный, LLM-независимый интерфейс тулов: тот же сервер подключается к Claude/любому клиенту. | Применимость: medium-high — вынести browser-автоматизацию (и при желании web-поиск) в MCP; остальные 20+ тулов оставить in-process. Двойное попадание: изоляция + LLM-независимость.
- **Event sourcing только для журнала действий** [Martin Fowler (Event Sourcing); event-driven.io (When not to use ES)]: Append-only журнал исполненных действий (что, чем, над какими файлами, обратная операция) как единственный event-sourced модуль; остальное состояние — обычные снапшоты. | Почему: Источники сходятся: ES — модульный паттерн, не системный; журнал действий даёт ровно то, что в целях проекта — откат, аудит, «что ассистент сделал за сегодня», — без стоимости полного ES (replay, эволюция схем). | Применимость: high — journal.sqlite: action.executed события с undo-метаданными (переименование → обратное переименование, удаление → корзина/staging); UI «отменить последнее».
- **Bounded queues + coalescing для awareness-потока** [asyncio best practices (bounded Queue, high/low water marks); HA keyed dispatch]: Каждый подписчик шины получает свою ограниченную очередь с политикой переполнения: coalesce (склеить всплеск файловых событий в одно), latest-wins (для UI), block (для журнала). | Почему: Безлимитная очередь при медленном потребителе = неограниченный рост памяти; watchdog даёт сотни событий на одну операцию копирования — coalescing превращает шквал в одно осмысленное событие для LLM-памяти. | Применимость: high — оформить политику переполнения как поле подписки (subscribe(..., overflow='coalesce')); метрики глубины очередей — готовый health-сигнал.
- **Иммутабельные снапшоты состояния world model** [Home Assistant state machine (frozen State objects, state_changed со старым и новым состоянием)]: Чтение состояния возвращает замороженный снапшот; изменение создаёт новый объект и публикует событие с old+new. Подписчики никогда не видят частично изменённое состояние. | Почему: Убирает целый класс гонок в asyncio-системе с 4+ конкурентными задачами; событие с diff (old, new) — готовый вход для LLM-экстракции памяти. | Применимость: medium — world model Jarvis: frozen dataclasses для окон/файлов/приложений; события window.focus_changed(old, new).
- **Один api_version + правило аддитивных изменений** [VS Code (proposed API, engines/minAppVersion); Obsidian (minAppVersion, requireApiVersion)]: Плагин-API версионируется одним целым числом в манифесте; изменения только аддитивные (новые опциональные параметры, новые хуки); нестабильные хуки помечаются experimental и не документируются как стабильные. | Почему: VS Code («We DO NOT want to break API») показывает цену стабильности, Obsidian — что одному числу достаточно; полный semver для внутреннего API одного мейнтейнера — лишняя церемония. | Применимость: medium — api_version=1 в манифесте, проверка при загрузке; то же правило аддитивности для схем тулов (MCP-ловушка: LLM кеширует схемы, новые поля обязаны быть optional).

## Анти-паттерны

- **Отдельный процесс на каждый плагин в single-author системе** [VS Code extension host; Mozilla process isolation analysis]: Изоляция процессов у VS Code существует ради тысяч недоверенных сторонних расширений; цена — RPC с полной JSON-сериализацией, ~7–10 МБ на минимальный процесс (замер Mozilla), рост cold start и «chatty IPC» (то, что было быстрым в общей памяти, становится мучительно медленным). Для системы, где все плагины пишет один человек, это чистый оверинжиниринг — Obsidian доказывает жизнеспособность in-process на годы. Изолировать стоит два конкретных компонента: UI и Playwright.
- **Команды и request/response через event bus** [Wix Engineering «5 Pitfalls», CodeOpinion, Temporal blog]: «Сделай X» как событие превращает поток управления в невидимый лабиринт: нет стека вызовов, некому вернуть ошибку, гейт разрешений негде поставить. Связность не исчезает — переезжает в семантику событий («coupling without a call stack»). HA решает это архитектурно: команды идут через service registry, шина — только для фактов.
- **Event sourcing как общесистемное хранилище состояния** [event-driven.io «When not to use Event Sourcing», Fowler]: Тянет за собой эволюцию схем событий, replay-инфраструктуру, компенсации — постоянный налог на каждый чих. Источники прямо говорят: ES — паттерн уровня модуля. Для Jarvis событийно-сорсить world model или память бессмысленно; нужен только журнал действий.
- **Жадная активация всех плагинов на старте (аналог activationEvents: "*")** [VS Code activation events docs]: VS Code явно предписывает «*» только когда ничто другое невозможно: каждый жадно грузящийся плагин платит памятью и временем старта постоянно, хотя используется эпизодически. В прототипе Jarvis все 25 тулов и awareness-модули грузятся сразу — при цели «минимальный фоновый footprint» это первое, что ломает бюджет.
- **Безлимитные очереди и подписчики на все события (MATCH_ALL)** [asyncio Queue документация/практика; HA best practices]: Unbounded queue при медленном потребителе — тихий рост памяти до OOM («concurrency without backpressure is just a DoS you launched at yourself»); подписка на все события заставляет диспетчер создавать job на каждый чих (HA рекомендует фильтры и конкретные типы). Watchdog-шквалы при копировании папки добьют такую шину за минуты.
- **Событие-«обо всём» без схемы и каталога** [Software Architecture Guild, Three Dots Labs, Forbes Tech Council («event sprawl», «ghost events»)]: «Events that mean everything mean nothing»: generic-события с dict-пейлоадом создают скрытые контракты, которые видны только в проде; отладка без correlation ID — «фонарик и молитва». Лекарство — маленький фиксированный каталог типизированных событий (frozen dataclass на каждый тип) и correlation ID через цепочку голос→план→действие.
- **Терминальный отказ интеграции при временной недоступности зависимости** [Home Assistant issue #153956 (Cloud терминально падает без интернета после ребута)]: Классика desktop-среды: машина загрузилась быстрее роутера, сервис недоступен 30 секунд — и интеграция мертва до рестарта. HA-паттерн различения «не готово, ретрай с backoff» vs «сломано навсегда» обязателен для всех сетевых плагинов Jarvis (LLM-провайдер, поиск, погода).
- **Ломающие изменения схем тулов при кеширующем клиенте** [MCP practice notes (LLM-клиенты кешируют tool definitions)]: LLM-клиент продолжает слать аргументы по старой схеме до перечитывания tools/list — переименованное обязательное поле даёт тихие отказы вызовов. Правило: изменения схем тулов только аддитивные (новые поля optional) либо новое версионированное имя тула.
