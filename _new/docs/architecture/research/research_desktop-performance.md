Изучен вопрос производительности always-on desktop-демонов на Python по первоисточникам: PEP 810/690, доки Microsoft по приоритетам процессов и EcoQoS, блог Алекса Гарсии (sqlite-vec), гайд phiresky по тюнингу SQLite, FAQ voidtools (Everything), доки psutil и fastembed, дизайн-доки Chromium/VS Code по IPC, обсуждения pydantic-core. Ниже — что подтверждено источниками и что из этого следует для Jarvis.

**Бюджет ресурсов.** Реалистичный ориентир для idle-состояния движка задаёт Everything (voidtools): индекс на 1 млн файлов — ~100 MB RAM и 45 MB диска, свежая Windows 11 (~250 тыс. файлов) — ~35 MB RAM, полная индексация за секунды за счёт чтения MFT напрямую и подписки на NTFS USN Journal вместо обхода каталогов (подтверждено FAQ voidtools). Для Python-движка моя экспертная оценка бюджета: 80–150 MB RSS в idle, <1% CPU, ноль периодических пробуждений чаще раза в минуту; тяжёлые подсистемы (браузер, эмбеддинги) — 0 MB, пока не нужны, потому что живут в отдельных процессах, запускаемых лениво.

**Импорты — главный налог на RAM.** Подтверждено: базовый интерпретатор мал, но каскад импортов при старте раздувает базовую память (pandas ~44 MB, boto3 ~25 MB только на импорт); в одном кейсе вынос долгоживущих импортов в подпроцессы снизил RSS демона с 708 MB до 22 MB (32x). PEP 690 (Meta) показывал до 70% ускорения старта и до 40% экономии памяти; принятый PEP 810 вводит явный синтаксис `lazy import` в Python 3.15 (октябрь 2026) с наблюдаемой экономией памяти 30–40%. До 3.15 работает дисциплина: тяжёлые библиотеки (cv2, numpy, playwright, google-sdk) импортируются только внутри функций-обработчиков соответствующих тулов; профилировать `python -X importtime` + tuna. Для Jarvis это прямое лекарство от «25 тулов тянут всё при старте».

**Спящий демон.** Подтверждено: правильный asyncio-паттерн — «спать до события», а не «спать N секунд и проверять»: `await event.wait()` / `await queue.get()` вместо poll-циклов; для жизненного цикла задач — `asyncio.TaskGroup` (3.11+), иначе осиротевшие таски держат ссылки на большие объекты (документированный источник утечек). Периодику согласовывать с OS: Windows поддерживает timer coalescing (tolerable delay), у Apple таймер-коалесцинг снижал CPU-активность на 72% — цифра из их whitepaper, иллюстрирует цену частых пробуждений. Исторический факт: ProactorEventLoop на Windows имел утечку в WSASend (исправлено), т.е. для realtime-аудио контура стоит следить за версией CPython.

**Фоновая индексация на Windows.** Подтверждено доками Microsoft: понижение только CPU-приоритета недостаточно — даже idle-поток убивает отзывчивость системы диском; `PROCESS_MODE_BACKGROUND_BEGIN` (SetPriorityClass) снижает сразу CPU-, page- и I/O-приоритет, применяется только к самому себе — идеально для отдельного процесса-индексатора. EcoQoS (SetProcessInformation/ProcessPowerThrottling) — ортогональный механизм энергоэффективности: планирование на E-ядра и низкие частоты; сам индексатор Windows 11 работает под EcoQoS. Efficiency Mode в Task Manager = low priority + EcoQoS; воркеру-индексатору Jarvis нужно включать оба через pywin32/ctypes.

**События ФС.** Подтверждено: один «сейв» в редакторе — это 3–4 события (temp-файл, rename, write); дефолтная очередь watchdog — 1024, всплески >500 соб./с её переполняют с потерей событий. Рабочая схема: фильтрация мусора на входе, дедупликация по пути внутри батча, debounce по «тихому окну» (50 мс–1 с) с потолком максимального ожидания (иначе git checkout никогда не даст батчу сработать). Паттерн Everything — журнал изменений: система догоняет пропущенное после простоя по USN Journal, не перечитывая диск; для Python доступ к USN есть через pywin32 — это выход из ловушки «watchdog работает только пока процесс жив».

**SQLite как хранилище.** Подтверждено (phiresky и др.): WAL + `synchronous=NORMAL` (безопасно в WAL) + `busy_timeout` + периодический `PRAGMA optimize` дают 100k+ SELECT/с и 500–1000 записей/с на десктопном железе; единственный писатель — не ограничение для single-user приложения. FTS5 — инвертированный индекс уровня Lucene, миллионы строк с миллисекундной задержкой (используется в Firefox history). sqlite-vec (Алекс Гарсия): brute-force KNN, 1 млн векторов 128d — ~17–35 мс/запрос; на 3072d деградирует до секунд на миллионе. Для памяти ассистента (моя оценка: десятки-сотни тысяч чанков, 384d) brute-force в sqlite-vec достаточен с запасом — отдельная векторная БД не нужна, всё в одном файле с FTS5 (гибридный поиск) и транзакциями.

**Локальные эмбеддинги.** Подтверждено: all-MiniLM-L6-v2 — 22M параметров, ~46–90 MB на диске, 384d, ~14k предложений/с на CPU; fastembed (Qdrant) гоняет квантованный ONNX без гигабайтов PyTorch. Но есть задокументированная проблема роста памяти в долгоживущем процессе (fastembed issue #222: с 1.5 GB до 6 GB RSS) — эмбеддер обязан жить в отдельном воркере с автоперезапуском по порогу RSS. Облако имеет смысл только как fallback: локальная модель дешевле, приватнее и не зависит от сети.

**Разделение процессов.** Подтверждено прецедентами: Chromium — named pipe на каждый renderer, асинхронный режим; VS Code — Node IPC-сервер на named pipe/unix socket, роли разнесены по процессам; Tauri формализует «sidecar» (движок как отдельный бинарь, IPC через stdout-хендшейк/локальный сокет). Для Jarvis: UI-процесс (tkinter или что угодно) ↔ движок через named pipe/локальный WebSocket с JSON-сообщениями — падение UI не убивает движок, GC-паузы и GIL движка не фризят интерфейс. Издержки IPC реальны: multiprocessing сериализует всё pickle'ом, и на больших объектах IPC съедает выигрыш (SharedMemory+pickle5 в 2–3 раза быстрее pipe, joblib #1094) — значит, между процессами гонять ссылки/ID строк SQLite, а не блобы; БД и так общая.

**Самомониторинг.** psutil даёт RSS своего процесса и детей; на Windows нет rlimit на память, поэтому рабочий паттерн — watchdog-цикл: раз в N секунд проверять RSS воркеров и перезапускать при превышении порога (перезапуск дешёв, если воркер stateless и состояние в SQLite). Это же — страховка от фрагментации: подтверждено, что pymalloc возвращает арены ОС только полностью пустыми, и «стабильная куча + растущий RSS» — типичная картина не-утечки, которую в долгоживущем процессе проще лечить рестартом воркера, чем тюнингом аллокатора (glibc-arena история — линуксовая, на Windows свой аллокатор, но паттерн «долгоживущие объекты выделять при старте, churn — в воркерах» универсален).

**Rust.** Подтверждено: pydantic-core — 17x к v1, ruff ~1000x к flake8-стеку, polars/tokenizers/uv — тот же паттерн «профилируй, перепиши 5% горячего кода через PyO3, остальное — Python». Но для соло-разработчика Jarvis мой вывод: писать свой Rust не нужно — «скорость Rust/C» уже приходит через выбор библиотек (SQLite — C, fastembed — ONNX Runtime, watchdog — нативные API, orjson, pydantic-core). PyO3 — запасной выход на 5+ летнем горизонте, если профилировщик покажет конкретный горячий цикл (например, диффы world model на сотнях тысяч объектов), и это осознанная плата сложностью сопровождения.

**Итог для проекта:** архитектура из 3–4 процессов (UI, движок-ядро с asyncio, индексатор под background mode + EcoQoS, эфемерные воркеры для эмбеддингов/Playwright), единый SQLite-файл (WAL, FTS5, sqlite-vec) как замена плоскому JSON и как шина состояния, ленивые импорты, событийность вместо поллинга, психология «всё тяжёлое — лениво, всё фоновое — на минимальном приоритете, всё долгоживущее — перезапускаемо».

## Идеи

- **Ленивые импорты тяжёлых библиотек** [PEP 810 / PEP 690 (Meta), кейс dev.to о демоне 708MB→22MB]: Тяжёлые библиотеки (cv2, playwright, SDK моделей) импортируются внутри функций-обработчиков тулов, а не на верхнем уровне; с Python 3.15 — явный синтаксис `lazy import`. Профилирование через `python -X importtime` + tuna. | Почему: Подтверждённые цифры: до 40% экономии памяти и до 70% ускорения старта (PEP 690 на реальных CLI Meta); демон с изоляцией импортов ужался в 32 раза. Ноль изменений логики — только место импорта. | Применимость: high — у Jarvis 25 тулов, большинство из которых в конкретной сессии не вызываются; ленивый импорт их зависимостей срезает базовый RSS движка сразу
- **Журнал изменений вместо повторной индексации (паттерн Everything/USN)** [voidtools FAQ и форум (Everything)]: Первичная индексация — быстрый полный проход, дальше — только чтение системного журнала изменений (NTFS USN Journal через pywin32). После простоя система догоняет пропущенное по журналу, без рескана диска. | Почему: Everything держит индекс 1 млн файлов в ~100 MB RAM, строит его за минуту и не теряет изменения даже когда процесс не работал — журнал ведёт ОС, а не приложение. Это эталон инкрементальности. | Применимость: high — awareness-слой Jarvis сейчас видит только то, что случилось при живом watchdog; USN-катчап закрывает слепую зону после перезапуска и позволяет держать world model актуальной задёшево
- **Фоновый индексатор под PROCESS_MODE_BACKGROUND_BEGIN + EcoQoS** [Microsoft Learn (SetPriorityClass), devblogs.microsoft.com (Introducing EcoQoS, Efficiency Mode)]: Процесс-индексатор сам включает себе background mode (понижает CPU-, page- и I/O-приоритет разом) и EcoQoS через ProcessPowerThrottling (планирование на эффективные ядра/частоты). | Почему: Microsoft явно документирует: одного низкого CPU-приоритета недостаточно — диск фонового потока всё равно душит отзывчивость; индексатор Windows 11 сам работает под EcoQoS. Комбинация даёт «невидимый» для пользователя фон. | Применимость: high — прямо применимо к воркеру индексации файлов/эмбеддингов Jarvis; включается парой вызовов через pywin32/ctypes при старте воркера
- **Debounce с тихим окном + потолком и дедупликацией по пути** [статья «File Watchers Lie» (Medium), доки/практика watchdog]: События ФС собираются в батч: фильтрация мусорных событий на входе, дедуп по пути, срабатывание после 50мс–1с тишины, но не позже жёсткого потолка (чтобы непрерывный поток вроде git checkout не откладывал обработку бесконечно). | Почему: Один сейв в редакторе — 3–4 события; всплески >500 соб./с переполняют дефолтную очередь watchdog (1024) с потерей событий. Батчинг превращает шторм в одно инкрементальное обновление world model. | Применимость: high — обязательный слой между watchdog и world model Jarvis; сейчас каждое событие дергает обработчик напрямую
- **SQLite (WAL + FTS5 + sqlite-vec) как единое хранилище памяти и индекса** [phiresky.github.io (SQLite performance tuning), alexgarcia.xyz (sqlite-vec), blog.sqlite.ai (FTS5)]: Один файл SQLite: WAL, synchronous=NORMAL, busy_timeout, периодический PRAGMA optimize; FTS5 для полнотекста, sqlite-vec для векторов, обычные таблицы для world model и журнала действий. Один писатель — движок. | Почему: Подтверждено: 100k+ SELECT/с, FTS5 держит миллионы строк с мс-задержкой (Firefox history), sqlite-vec brute-force даёт ~17–35 мс на 1 млн векторов 128d — для личного ассистента (сотни тысяч чанков, 384d) запас огромный. Транзакции, бэкап одним файлом, нулевая эксплуатация. | Применимость: high — заменяет плоский JSON памяти, даёт гибридный (BM25+вектор) поиск и историю изменений; ключевое инфраструктурное решение нового витка
- **Событийный «спящий» демон на asyncio.Event/Queue + TaskGroup** [Inngest blog (asyncio primitives), Real Python, доки asyncio 3.11]: Все циклы вида `while True: check(); sleep(n)` заменяются на `await event.wait()` / `await queue.get()`; фоновые задачи живут в asyncio.TaskGroup, который гарантирует уборку при исключениях. Периодика — редкая и с грубыми допусками, чтобы ОС коалесцировала таймеры. | Почему: Нулевые пробуждения в idle — это и CPU, и батарея (таймер-коалесцинг у Apple снижал CPU-активность на 72%); TaskGroup закрывает документированный класс утечек через осиротевшие таски. | Применимость: high — ядро Jarvis уже на asyncio (4 задачи аудио); нужно распространить событийную модель на весь движок и ввести шину событий на asyncio.Queue
- **Разделение на процессы: UI ↔ движок ↔ воркеры через named pipe/локальный WebSocket** [Chromium IPC design doc, VS Code process architecture, Tauri sidecar (v2.tauri.app, Evil Martians)]: UI — отдельный процесс, общается с движком JSON-сообщениями по named pipe или локальному WebSocket; тяжёлые подсистемы (Playwright, эмбеддинги) — эфемерные воркеры, запускаемые лениво и убиваемые по простою. Между процессами — ссылки/ID (данные в общей SQLite), не блобы. | Почему: Проверено Chromium/VS Code: изоляция падений, GC-паузы и GIL движка не фризят UI, воркер с текущим Chromium (сотни MB) не входит в базовый footprint. Pickle-издержки multiprocessing обходятся передачей ссылок. | Применимость: high — решает сразу две боли Jarvis: tkinter в одном процессе с движком и невозможность заменить UI; заодно открывает путь к Tauri/веб-UI без переписывания ядра
- **Квантованный all-MiniLM через fastembed/ONNX в перезапускаемом воркере** [qdrant/fastembed (GitHub, статья Qdrant), sbert.net efficiency docs, fastembed issue #222]: Локальные эмбеддинги: all-MiniLM-L6-v2 (22M параметров, ~14k предложений/с на CPU, 384d) в квантованном ONNX без PyTorch; процесс-эмбеддер перезапускается при превышении порога RSS. | Почему: Десятки MB на диске и без GPU — эмбеддинг всего архива пользователя за минуты; известная проблема роста памяти fastembed в долгоживущем процессе (1.5→6 GB, issue #222) нейтрализуется дизайном «эфемерный воркер». | Применимость: high — даёт семантический поиск по памяти/файлам без облака; батчи эмбеддинга — под фоновым приоритетом из идеи 3
- **Самонаблюдение через psutil с политикой перезапуска воркеров** [psutil docs, pythonspeed.com (measuring memory)]: Движок раз в 30–60 с снимает RSS/CPU себя и дочерних воркеров через psutil; при превышении бюджета — сброс кэшей, а для stateless-воркеров — рестарт. Метрики пишутся в ту же SQLite для трендов. | Почему: На Windows нет rlimit на память — polling+restart единственный кроссплатформенный механизм; рестарт заодно лечит фрагментацию аллокатора (pymalloc возвращает арены только пустыми), которую иначе не победить. | Применимость: high — дёшево реализуется, превращает «Jarvis съел 2 GB за неделю» из инцидента в невозможное состояние; вписывается в существующие circuit breakers
- **«Rust через библиотеки», PyO3 — только по профилю** [pydantic/pydantic-core (discussion #5279), DevTools Academy (uv/ruff), кейсы PyO3]: Скорость нативного кода получать выбором Rust/C-backed зависимостей (SQLite, ONNX Runtime, orjson, pydantic-core, watchdog); собственный PyO3-модуль писать только когда профилировщик покажет конкретный горячий цикл, и он не сводится к SQL/векторизации. | Почему: Прецеденты (pydantic-core 17x, ruff ~1000x) подтверждают потенциал, но и цену: сопровождать Rust-код соло-разработчику дорого. Стратегия «библиотеки сначала» даёт 90% выигрыша без новой компетенции в стеке. | Применимость: medium — на старте нового витка достаточно правильного выбора зависимостей; PyO3 — задокументированный запасной выход для 5-летнего горизонта
- **Инкрементальная world model как diff-журнал, а не снимок** [паттерн Everything (USN) + SQLite журнал; синтез, экспертная оценка]: Состояние окружения хранится как последовательность событий-диффов в SQLite (append-only) плюс материализованный текущий снимок; «история изменений» и «недавние действия» — это просто запросы к журналу, а откат — обратное применение диффа. | Почему: Append-only записи дёшевы в WAL-режиме, дают бесплатное журналирование и основу для undo; полный ресинк нужен только при потере журнала — та же логика, что у Everything с MFT/USN. | Применимость: high — объединяет требования «история изменений», «журналирование» и «откат» из целей проекта в одну структуру данных вместо трёх подсистем

## Анти-паттерны

- **Эager-импорт всего стека при старте** [PEP 810/690, кейс дедупликации демона (dev.to)]: Каскад импортов задаёт базовый RSS независимо от использования: pandas ~44 MB, boto3 ~25 MB только за импорт; реальный демон-индексатор держал 708 MB, из которых 686 MB были импортами, нужными эпизодически. Для always-on ассистента это постоянный налог на память ради кода, который может не выполниться ни разу за день.
- **Поллинг-циклы `while True: check(); sleep(n)`** [Inngest blog, Apple Power Efficiency whitepaper, Microsoft timer coalescing docs]: Каждое пробуждение выводит CPU из глубокого idle — на ноутбуке это батарея, на десктопе — фоновая нагрузка, которую видно в Task Manager. Апскейлится плохо: десяток модулей с секундными поллами дают постоянный фоновый шум. Apple мерила, что коалесцинг таймеров срезает CPU-активность на 72% — то есть именно столько сжигают несогласованные пробуждения.
- **UI, движок и тяжёлые задачи в одном процессе** [архитектуры Chromium/VS Code как контрпример; текущий MARK XXXV]: GIL и GC-паузы движка фризят интерфейс, синхронный вызов Playwright блокирует аудио-контур, падение любого модуля убивает всё. Chromium и VS Code разнесли роли по процессам именно после того, как монолит упёрся в отзывчивость и надёжность. В MARK XXXV tkinter уже живёт в процессе движка — это тупик для замены UI.
- **Плоский JSON как долговременная память с полной перезаписью** [текущий MARK XXXV; сравнение с phiresky/FTS5]: Каждое обновление — сериализация и запись всего файла: O(N) диска на каждое изменение, риск потери при падении в момент записи, нет ни индексов, ни поиска, ни конкурентного чтения. На горизонте лет память растёт, и линейная перезапись превращается в секунды I/O на каждое воспоминание; SQLite в WAL делает то же за микросекунды с транзакционной гарантией.
- **Обработка каждого события ФС по отдельности** [«File Watchers Lie» (Medium), практика watchdog]: Один сейв в VS Code — это 3–4 низкоуровневых события; git checkout или сборка — сотни в секунду. Дефолтная очередь watchdog (1024) переполняется с молчаливой потерей событий, а обработчик, дергающий LLM или БД на каждое событие, умножает нагрузку на порядок. Без debounce/коалесцинга awareness-слой сам становится главным потребителем CPU.
- **Передача больших объектов через multiprocessing-очереди** [pythonspeed.com, joblib issue #1094]: multiprocessing pickle'ит всё: большие массивы/словари сериализуются, копируются и десериализуются, и IPC-издержки съедают выигрыш от параллелизма (SharedMemory+pickle5 быстрее pipe в 2–3 раза именно потому, что убирает копии). В архитектуре с общей SQLite гонять блобы между процессами вообще незачем — передаются ID строк.
- **Долгоживущий процесс без стратегии перезапуска и бюджета памяти** [fastembed issue #222, finbox.in (jemalloc), ragoragino.dev]: В многолетнем демоне «не-утечки» неизбежны: фрагментация аллокатора (pymalloc отдаёт арены только пустыми), осиротевшие asyncio-таски, рост нативных буферов (fastembed: 1.5→6 GB RSS без бага в Python-коде). Если процесс монолитен и незаменим, единственное лекарство — перезапуск всего ассистента; если тяжёлое вынесено в stateless-воркеры — рестарт воркера незаметен.
- **Фоновая работа на обычном приоритете (или только с низким CPU-приоритетом)** [Microsoft Learn: SetThreadPriority/SetPriorityClass]: Microsoft документирует прямо: даже поток с IDLE CPU-приоритетом легко убивает отзывчивость системы диском и памятью — CPU-приоритет не управляет I/O. Индексатор, читающий тысячи файлов на нормальном I/O-приоритете, конкурирует с активной работой пользователя; нужен PROCESS_MODE_BACKGROUND_BEGIN (снижает и I/O, и page priority) + EcoQoS.
- **Преждевременное «перепишем на Rust» целиком** [обсуждения pydantic-core, JetBrains blog (Rust vs Python)]: Успехи ruff/polars/pydantic-core — это переписывание измеренного горячего ядра командами с Rust-компетенцией, а не миграция приложений. Для соло-сопровождаемого проекта чужой язык в стеке — постоянная плата за каждую правку; 90% той же скорости даёт выбор нативно-backed библиотек. Rust оправдан только для профилированного горячего цикла, который нельзя выразить через SQL/векторизацию.
- **Неограниченные in-memory кэши и world model без вытеснения** [ragoragino.dev (production Python memory), экспертная оценка]: In-memory world model, растущая с каждым наблюдением, — классический «легальный» пожиратель памяти долгоживущего процесса: куча стабильна, утечки нет, а RSS растёт месяцами. Ориентир Everything (1 млн файлов = 100 MB) достижим только при компактном представлении и вытеснении холодных данных в SQLite; в памяти — только горячий срез с лимитом записей.
