Я изучил шесть групп первоисточников: permission-модель Claude Code, сервисный слой Home Assistant, Windows-API файловых операций (IFileOperation/SHFileOperation, ReplaceFile, судьба TxF), saga/журнал компенсаций, undo-стек Nautilus и PowerRename, capability-модель WASI и плагинные песочницы Zellij/Lapce/Extism, плюс работы по risk-tiered подтверждениям для LLM-агентов. Ниже — синтез применительно к action-слою Jarvis.

Самый важный сквозной вывод (подтверждён документацией Claude Code дословно): «Permission rules are enforced by Claude Code, not by the model» — политика живёт в harness, а промпт лишь влияет на то, что модель ПОПЫТАЕТСЯ сделать. Это ровно ваш паттерн «capability truth» из core/security.py, но доведённый до конца: в Claude Code ЛЮБОЙ вызов инструмента проходит один pipeline: deny → ask → allow, первое совпадение решает; поверх — permission modes (default/acceptEdits/plan/auto/dontAsk/bypassPermissions) как режимы сессии; поверх — PreToolUse-hooks, которые могут вернуть permissionDecision (allow/deny/ask) и даже updatedInput, но deny-правила действуют независимо от хука. Отдельно показателен «circuit breaker»: даже в bypassPermissions удаление корня/домашней директории всё равно требует подтверждения — жёсткий пол, который не отключается режимом. Для Jarvis это прямой рецепт закрытия дыры agent/executor: не «executor тоже вызывает security.check()», а архитектурно единственная точка исполнения — ActionBus/Executor-сервис, в который обязаны ходить все три пути (голосовой вызов тула, агентный план, плагин), и вне которого мутирующие вызовы ОС просто недоступны модулям.

Второй столп — типизированные действия. Home Assistant регистрирует каждый service call со схемой voluptuous; данные валидируются ДО хендлера, из описаний сервисов автоматически генерируется UI, а контекст вызова пробрасывается сквозь цепочку «для audit trails» (это из их дев-документации). С 2025.10 HA принудительно запрещает кастомные схемы entity-сервисов, не основанные на cv.make_entity_service_schema — интересный прецедент: платформа силой убирает дрейф схем. Бонус: библиотека voluptuous-openapi конвертирует те же схемы в OpenAPI — т.е. одна декларация действия даёт и валидацию, и tool-definition для любой LLM. Это усиливает ваш анти-дрейф паттерн: единый ActionRegistry, где у действия есть schema, risk-уровень, флаги supports_preview/reversible, generate — из него и промпт-декларации тулов, и валидация, и политика.

Третий столп — «plan как артефакт». Terraform разделяет plan/apply не для красоты: сохранённый план (-out=FILE) гарантирует, что исполняется ровно то, что было отревьюировано, а при изменении state план объявляется «stale» и требует пересоздания. Диффы помечают разрушительные операции («forces replacement»). Ansible добавляет нюанс: check mode работает только для модулей, объявивших supports_check_mode, а command/shell всегда врут «changed» — вывод: dry-run должен быть контрактом каждого action-хендлера (метод preview() → typed diff), а не эмерджентным свойством. Из HITL-исследований для агентов (arXiv 2506.08837 и практические разборы) — критичный производственный баг: аргументы мутируют между показом подтверждения и исполнением, если агент перегенерирует вызов; лечение — зафиксировать одобренный payload хэшем и отказаться исполнять при расхождении. Для Jarvis: planner выдаёт неизменяемый typed-план, пользователь подтверждает конкретный объект плана, executor исполняет именно его.

Четвёртый — откат. Литература по saga единодушна: компенсация ≠ rollback. Temporal прямо объясняет, почему восстановление снапшота в живой среде теряет параллельные изменения (на десктопе другие программы трогают те же файлы). Рабочая схема: журнал с write-ahead intent-записью → операция → completion-запись; у каждого шага — идемпотентное компенсирующее действие; после сбоя координатор дочитывает журнал и докатывает/откатывает; есть «pivot» — точка невозврата (финальный атомарный rename). Nautilus показывает прикладную реализацию: per-операционные объекты NautilusFileUndoInfo* (Rename хранит old_file/new_file и display-имена; BatchRename группирует пачку в одну undo-единицу), менеджер с тремя состояниями (base/undo/redo), человекочитаемые парные подписи («Move X back to Y»). PowerRename сознательно делегирует переименование движку Explorer именно ради бесплатного Ctrl+Z — и это подводит к Windows-специфике: для удалений использовать IFileOperation с FOFX_RECYCLEONDELETE | FOFX_ADDUNDORECORD (корзина + запись в undo-стек Explorer), а не os.remove; для «сохранить документ» — паттерн temp-файл + ReplaceFile (Microsoft сам называет его заменой TxF; TxF деприкейтнут из-за сложности и не работает на ReFS). Важно: программное восстановление ИЗ корзины ненадёжно (старые обсуждения это подтверждают), поэтому собственный undo ассистента должен опираться на свой журнал + staging (копия файла перед перезаписью в каталог ассистента), а корзина — это подстраховка для пользователя через привычный Explorer. System Restore Points для этой задачи бесполезны: официально они покрывают только системные файлы/реестр, НЕ документы пользователя, и в Win10/11 выключены по умолчанию.

Пятый — capability-объекты. WASI (через сюда же Capsicum/CloudABI, блог sunfishcode) строит доступ к ФС на дескрипторах-возможностях: нет ambient authority, только openat от преданного handle; «..», абсолютные пути и symlink-побеги отклоняются на уровне API; в компонентной модели дескриптор /data/tenant-a физически не может открыть /data/tenant-b. Признанные проблемы: крупная гранулярность preopen-ов и UX динамического запроса новых прав (WASI issue #66). Для Jarvis это означает: модуль получает не строки путей, а объект ScopedRoot (handle на разрешённый корень) с методами open/list/move — та самая дырка copy_file-без-safe-roots закрывается типом, а не проверкой. Плагины: Zellij держит WASM-плагины в песочнице, монтирует /host,/data,/tmp, проверяет каждый PluginCommand на границе хоста (check_command_permission) и заставляет плагин явно запрашивать декларированные permissions (в т.ч. отдельная FullHdAccess); Extism формулирует принцип чётко: возможности существуют только те, что хост инжектировал host-функциями; Lapce изолирует плагины за прокси-процессом. Моя экспертная оценка: для одного мейнтейнера полный WASM — оверкилл на старте; правильная последовательность — сначала in-process плагины со строгим API (плагин видит только ActionBus + ScopedRoot + EventBus-подписки), затем при необходимости вынос в отдельный процесс; WASM оставить как опцию для чужого кода.

Наконец, подтверждения как UX. Консенсус источников: 4 уровня риска (read-only → авто; обратимое → авто с записью в журнал и toast с кнопкой Undo; внешнее/пишущее наружу → ask; необратимое → блокирующее подтверждение с точным payload, не пересказом). AWS Agentic Lens и практики прямо называют «confirm everything» ломающим оversight: пользователь перестаёт читать и жмёт «да» рефлекторно. Полезные детали: standing-grants («разрешить такое всегда») должны быть привязаны к конкретному паттерну команды/ресурсу и отображаться/отзываться в UI (у Claude Code «Yes, don't ask again» сохраняет по отдельному правилу на каждый субкоманд компаунда — до 5 правил); подтверждения устаревают (expiry); Ctrl+E-объяснение команды по запросу — хорошая ленивая модель «объясни, что это сделает». Итоговая архитектура для Jarvis: ActionRegistry (схема+риск+preview+inverse) → единый Executor-гейт с policy-таблицей → журнал saga-типа со staging-каталогом → undo-стек команд поверх журнала → IFileOperation/ReplaceFile на нижнем уровне → ScopedRoot-capabilities для модулей и плагинов. Всё это эволюция вашего core/security.py, а не замена.

## Идеи

- **Единый гейт исполнения: политика в harness, не в промпте** [Claude Code permissions (code.claude.com/docs/en/permissions)]: Все вызовы инструментов проходят один pipeline deny→ask→allow (первое совпадение решает), поверх — permission modes как режимы сессии и PreToolUse-hooks, которые могут вернуть allow/deny/ask или изменить input, но не могут обойти deny. Правила enforced кодом, а не моделью. | Почему: Один chokepoint делает политику проверяемой и не даёт путям исполнения дрейфовать; режимы (plan/acceptEdits/dontAsk) дают пользователю переключатель автономии без правки правил. | Применимость: high — прямое лекарство от незакрытой дыры agent/executor: сделать Executor единственным местом, где вообще возможны мутирующие вызовы ОС; policy-таблица core/security.py остаётся source of truth, executor и плагины физически не имеют другого пути.
- **Circuit breaker поверх режимов** [Claude Code: rm -rf / и ~ требуют подтверждения даже в bypassPermissions]: Небольшой жёсткий список катастрофических операций (удаление корня/домашней папки, форматирование), который требует подтверждения независимо от режима автономии и standing-grants, включая варианты через подстановки. | Почему: Пол безопасности, не зависящий от конфигурации: пользователь может ослабить всё, кроме этого; дёшево реализуется и спасает от worst case. | Применимость: high — добавить в policy-таблицу немодифицируемый tier «always-confirm» для операций над корнями дисков, %USERPROFILE%, каталогами проекта самого Jarvis.
- **ActionRegistry: типизированные действия со схемой как единый источник** [Home Assistant dev_101_services + voluptuous-openapi]: Каждое действие регистрируется со схемой (voluptuous/pydantic): валидация данных до хендлера, автогенерация UI/описаний из тех же схем, проброс context id через всю цепочку вызова для аудита. voluptuous-openapi конвертирует схему в OpenAPI. | Почему: Одна декларация даёт валидацию, документацию, tool-definitions для LLM и вход для политики — нулевой дрейф между «что модель думает, что умеет» и «что код делает». HA с 2025.10 принудительно запрещает нестандартные схемы — показатель, что дрейф схем реальная болезнь. | Применимость: high — расширить паттерн «capability truth»: из ActionRegistry генерировать и промпт-секцию, и Gemini/любые tool-declarations, и risk-метаданные; это же основа LLM-независимости.
- **План как неизменяемый артефакт + защита от устаревания** [Terraform plan/apply (-out=FILE, stale plan detection)]: Планирование отделено от исполнения; сохранённый план исполняется байт-в-байт как отревьюировано; если состояние мира изменилось между plan и apply — план объявляется stale и пересоздаётся; разрушительные шаги помечаются в диффе. | Почему: Убирает разрыв «пользователь одобрил одно, исполнилось другое»; диффы с пометкой destructive направляют внимание туда, где риск. | Применимость: high — planner выдаёт typed-план (список action-вызовов из Registry), подтверждение привязывается к хэшу плана, executor сверяет хэш и релевантные факты world model перед исполнением.
- **Пиннинг одобренного payload хэшем** [Практика HITL-агентов (Truto/Velt/AWS Agentic Lens разборы)]: Между показом подтверждения и исполнением аргументы не должны меняться: одобренный payload фиксируется хэшем на момент interrupt, executor отказывает при расхождении (баг возникает, когда агент перегенерирует вызов LLM при resume). | Почему: Закрывает документированный производственный класс ошибок «UI показал одно, исполнилось другое» — критично для доверия к подтверждениям. | Применимость: high — тривиально добавить в confirm-поток: confirm_token = hash(action, args); executor исполняет только по валидному токену.
- **Preview/dry-run как контракт каждого хендлера** [Ansible check mode (supports_check_mode, diff mode) + PowerRename live preview]: Хендлер действия обязан реализовать preview() → typed diff («N файлов будет перемещено, вот список»); хендлеры без поддержки честно объявляют это (как supports_check_mode=False), а не молча пропускаются. PowerRename показывает живой диф до применения и остаётся недеструктивным до нажатия Rename. | Почему: Dry-run, встроенный в интерфейс действия, не может «соврать» как ansible shell (всегда changed); превью пачки — лучший UX для batch-операций типа «разложи загрузки по папкам». | Применимость: high — для файловых действий preview почти бесплатен (просчитать список src→dst); показать в UI со чекбоксами включения/исключения как в PowerRename.
- **Журнал операций saga-типа с компенсациями** [microservices.io, Azure Architecture Center, Temporal blog]: Write-ahead запись намерения → операция → completion-запись; у каждого шага idempotent-компенсация (inverse op); после краха координатор дочитывает журнал и завершает/откатывает; pivot-точка отмечает «после этого только вперёд». | Почему: Компенсация вместо снапшот-отката корректно живёт в среде, где файлы параллельно меняют другие программы; журнал даёт и recovery после падения процесса, и полный аудит «кто/что/почему». | Применимость: high — ядро undo-подсистемы Jarvis: append-only журнал (SQLite), каждая запись содержит action, args, inverse-op, ссылки на staging-копии.
- **Undo-стек Command-паттерна поверх журнала** [Nautilus nautilus-file-undo-operations.c / nautilus-file-undo-manager.c]: Per-операционные undo-info объекты хранят состояние для реверса (у Rename — old/new GFile и display-имена); batch-операции группируются в одну undo-единицу; менеджер — конечный автомат base/undo/redo; у каждой единицы парные человекочитаемые подписи («Move X back to Y»). | Почему: Проверенная годами модель GNOME Files; человекочитаемые подписи превращают undo из технической фичи в понятный диалог («отмени последнее» голосом). | Применимость: high — реализовать 1:1: UndoUnit с describe_undo()/describe_redo(), группировка batch-переименований, голосовая команда «отмени» снимает верхний unit.
- **IFileOperation + Recycle Bin как нижний слой файловых мутаций** [Microsoft Learn (SHFileOperation/IFileOperation), PowerRename design wiki]: Удаление — только через IFileOperation с FOFX_RECYCLEONDELETE | FOFX_ADDUNDORECORD (корзина + undo-record Explorer); PowerRename сознательно вызывает движок Explorer именно чтобы Ctrl+Z работал после выхода из программы. | Почему: Ассистент играет по правилам платформы: удалённое видно в привычной корзине, отмена доступна и без Jarvis; батчинг нескольких операций в один вызов даёт прогресс и atomic-подобную семантику. | Применимость: high — заменить все os.remove/shutil в actions/ на обёртку поверх IFileOperation (через pywin32); программное восстановление из корзины ненадёжно, поэтому свой undo — через журнал+staging, корзина — подстраховка.
- **Temp-файл + ReplaceFile для перезаписи содержимого** [Microsoft Learn «Alternatives to using Transactional NTFS», LWN «Atomic rename in Windows»]: Документ пишется в новый файл, затем ReplaceFile атомарно подменяет оригинал (Microsoft называет это официальной заменой TxF); обязательное условие атомарности — один том. | Почему: Файл никогда не существует в полузаписанном состоянии; ReplaceFile к тому же сохраняет атрибуты/ACL оригинала в отличие от голого MoveFileEx. | Применимость: high — обязательный паттерн для памяти/конфигов самого Jarvis (сейчас плоский JSON!) и для любых «отредактируй файл» действий; плюс staging-копия оригинала в каталог ассистента до замены = материал для undo.
- **ScopedRoot: capability-хэндл вместо путей-строк** [WASI preopens / sunfishcode «Capabilities and Filesystems» / Wasmtime security]: Модуль получает объект-дескриптор разрешённого корня; все операции — методы этого объекта в стиле openat; абсолютные пути, «..» и symlink-побеги отклоняются на уровне API, а не проверкой в вызывающем коде. | Почему: Права выражены типом: код без хэндла физически не может тронуть чужой каталог; исчезает класс ошибок «забыл проверить путь» (ваш copy_file без safe-roots). | Применимость: high — небольшой класс ScopedRoot поверх pathlib с канонизацией и проверкой принадлежности корню; все файловые action-хендлеры и плагины получают только его, конструирует его только policy-слой.
- **Плагин запрашивает декларированные permissions, хост проверяет на границе** [Zellij plugin permissions (zellij.dev) + Extism host functions]: У Zellij фиксированный словарь permissions (OpenFiles, RunCommand, FullHdAccess...), плагин просит их через request_permission, хост проверяет каждый PluginCommand в check_command_permission на границе. У Extism возможности плагина — только те host-функции, что хост явно инжектировал. | Почему: Манифест возможностей читается человеком до установки плагина; enforcement на границе хоста не зависит от дисциплины автора плагина; понижает барьер доверия к чужим расширениям. | Применимость: medium — на старте достаточно in-process плагинов, которым передаётся только узкий API-объект (ActionBus + ScopedRoot + подписки), с манифестом требуемых action-групп; WASM/отдельный процесс — later, каркас манифеста заложить сразу.
- **4-уровневая шкала риска вместо бинарного confirm** [AWS Agentic AI Lens AGENTSEC04-BP02, обзоры HITL-паттернов]: read-only → авто; обратимое → авто + запись в журнал + toast с кнопкой Undo; внешнее (письмо, пост, покупка) → ask; необратимое → блокирующее подтверждение с точным payload. Standing-grants привязаны к конкретному паттерну и отзываемы; у подтверждений есть expiry. | Почему: Прямо адресует усталость от подтверждений: человек читает диалог только там, где его решение реально меняет исход; «обратимое → авто+Undo» возможно ровно потому, что есть журнал и undo-стек. | Применимость: high — уточнить существующую таблицу blocked/confirm/auto до 4 уровней; toast «Перемещено 12 файлов — Отменить» вместо диалога для reversible-операций — главный выигрыш UX.
- **Ленивое объяснение действия по запросу** [Claude Code Ctrl+E explanation on permission prompt]: Диалог подтверждения показывает точную команду, а LLM-объяснение («что сделает, что может пойти не так», Low/Med/High risk) генерируется только по нажатию, не на каждый промпт. | Почему: Экономит латентность и токены на 95% подтверждений, но даёт глубину, когда пользователь сомневается — образец ленивых вычислений в UX. | Применимость: medium — кнопка/голосовая команда «объясни» в confirm-диалоге Jarvis, объяснение генерирует та же LLM по требованию.

## Анти-паттерны

- **Строить откат на транзакциях файловой системы (TxF/KTM)** [Microsoft Learn «Alternatives to using Transactional NTFS»]: Microsoft деприкейтнул TxF из-за сложности и минимального adoption, прямо рекомендует ReplaceFile и др.; на ReFS транзакционного I/O нет вовсе. Любая ставка на «настоящие» ФС-транзакции в Windows — тупик для 5-летнего проекта.
- **System Restore Points как undo пользовательских файлов** [Wikipedia System Restore, Microsoft Q&A]: Restore points покрывают только системные файлы/реестр/драйверы и явно НЕ трогают документы, музыку, фото; в Win10/11 выключены по умолчанию. Для отката действий ассистента над данными пользователя они бесполезны — нужен собственный журнал+staging.
- **Подтверждать всё подряд** [AWS Agentic AI Lens, обзоры HITL-производств]: Документированный эффект: при потоке диалогов пользователь перестаёт читать payload и жмёт «да» рефлекторно — оversight превращается в rubber-stamp, а UX в мучение. Подтверждение должно быть дефицитным ресурсом, зарезервированным за необратимым.
- **Политика в промпте вместо кода** [Claude Code docs: «rules are enforced by Claude Code, not by the model»]: Инструкции в промпте меняют то, что модель попытается сделать, но не то, что ей позволено; при новых моделях/провайдерах поведение дрейфует. Ваша дыра executor-в-обход-гейта — частный случай: путь исполнения, не проходящий через policy-код, равен отсутствию политики.
- **Фильтрация опасных операций по паттернам аргументов** [Claude Code docs (ненадёжность URL-паттернов в Bash, обход через подстановки; Bash(command:...) игнорируется как обходимый)]: Сопоставление строк аргументов обходится компаундами, подстановками, переменными — сам Claude Code отказывается принимать такие правила. Гейтить надо типизированные действия на границе исполнения, а не строки команд; обход allowlist в вашем cmd_control через сырое поле command — ровно этот класс.
- **Снапшот-rollback вместо компенсаций в живой среде** [Temporal «Compensating actions, part of a complete breakfast with sagas»]: Восстановление состояния «как было» стирает параллельные изменения, сделанные другими процессами между снапшотом и откатом; на десктопе файлы постоянно трогают другие программы. Правильно — компенсирующая операция (вернуть файл на место), а не восстановление образа каталога.
- **Ambient authority: модули оперируют сырыми строками путей** [sunfishcode «Capabilities and Filesystems», Node.js WASI docs]: Когда любой модуль может open() любую строку, каждая проверка безопасного корня — ручная и однажды будет забыта (ваш copy_file). Node.js честно пишет, что его preopens «не образуют security model» — полумеры без enforcement на границе API создают ложную уверенность.
- **Ad-hoc схемы действий у каждого модуля свои** [Home Assistant blog «Validation of entity action schemas» (2024) и запрет кастомных схем с 2025.10]: HA годами разгребал зоопарк: сервисы с самодельными схемами не поддерживали стандартные способы адресации и ломали автогенерацию UI — пришлось запрещать принудительно. В 25 тулах Jarvis тот же дрейф уже виден (14 загрузок ключа, 36 хардкодов моделей); без единого Registry он будет расти.
- **Подтверждение по пересказу, а не по точному payload** [Edilec/Velt разборы approval-UX; практика args-drift при resume]: Если диалог показывает сгенерированное резюме, а исполняется перегенерированный вызов, пользователь одобряет не то, что произойдёт; известный производственный баг — мутация аргументов между approve и execute. Показывать точные параметры и пиновать их хэшем.
- **Dry-run как эмерджентное свойство, а не контракт** [Ansible check mode docs (command/shell всегда «changed», модули без supports_check_mode молча пропускаются)]: Ansible показывает, что превью, не встроенное в интерфейс модуля, либо молчит, либо врёт — «--check это preview, не доказательство». Если preview() не обязателен в интерфейсе Action, половина хендлеров его не реализует и UI подтверждений останется слепым.
