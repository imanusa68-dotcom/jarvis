Я изучил основные архитектуры долговременной памяти для AI-ассистентов: MemGPT/Letta, Zep/Graphiti, mem0, Cognee, продакшн-память ChatGPT и Claude (по реверс-инжинирингу и официальным публикациям), академическую таксономию CoALA и Generative Agents, политики забывания и десктопный стек SQLite + FTS5 + sqlite-vec. Главный вывод для MARK XXXV: оптимальная схема — слоистая память на одном SQLite-файле с фоновой консолидацией в простое, а не «серьёзный» стек с векторной БД и графовой СУБД.

Что подтверждено первоисточниками. MemGPT/Letta (arXiv:2310.08560, docs.letta.com) ввели иерархию: core memory — небольшие именованные текстовые блоки прямо в контексте (лимит по умолчанию ~2000 символов на блок, рекомендация <20 блоков), которые агент сам редактирует тулами; recall memory — поиск по истории диалогов; archival memory — векторное хранилище, дергаемое тулом. Признанная слабость самоуправляемой памяти: качество целиком зависит от суждений модели — «если модель не сохранила, факт потерян», и каждая операция памяти стоит токенов и задерживает ответ. Letta закрыла это sleep-time compute (arXiv:2504.13171): отдельный «спящий» агент в фоне переписывает память (tool rethink_memory), давая до 5x экономии токенов на инференсе. OpenAI независимо пришла к тому же — их «dreaming»: фоновый процесс курирует память по истории чатов и обновляет устаревшее («едешь в Сингапур» → «съездил в июле»). Это конвергенция двух независимых команд — сильный сигнал, что фоновая консолидация в простое — правильный паттерн, и он идеально ложится на ваш awareness-слой: у десктопного ассистента много «сна».

Zep/Graphiti (arXiv:2501.13956) — темпоральный граф знаний с би-темпоральной моделью: у каждого факта-ребра четыре метки времени (когда стал истинным/перестал, когда записан/инвалидирован в системе). Противоречащий факт не удаляется — закрывается интервал валидности. Ретривал без LLM: BM25 + косинус + BFS-обход графа, P95 ~300 мс. Но цена записи высокая: один эпизод порождает несколько LLM-вызовов (извлечение узлов, дедуп, извлечение рёбер, разрешение противоречий), плюс Neo4j требует ~2 ГБ RAM — для фонового десктоп-процесса неприемлемо. Вывод: брать идею би-темпоральности (колонки valid_from/valid_to/recorded_at в SQLite), не брать стек.

mem0 (классический пайплайн): LLM извлекает факты из диалога, ищет похожие по эмбеддингам, второй LLM-вызов решает ADD/UPDATE/DELETE/NOOP. Важный поворот: в v3 mem0 сам отказался от этой схемы и от внешних графовых хранилищ (~4000 строк кода удалено) в пользу single-pass ADD-only извлечения + entity linking + мультисигнального ретривала (семантика + BM25 + сущности). Причина: LLM-роутинг на каждой записи — чёрный ящик и стоимость, пропорциональная числу реплик. Cognee — ECL-пайплайн (Extract–Cognify–Load) с онтологиями; интересна идея строго аддитивной онтологии (начать с LLM-извлечения, схему добавлять по мере зрелости), но это оверкилл для персонального ассистента.

Продакшн-системы разошлись на два полюса. ChatGPT (реверс Rehberger/Khemani, подтверждено постом OpenAI): без векторных БД и RAG — профиль пользователя (Model Set Context, User Insights, саммари ~40 последних чатов) инжектится в каждый промпт. Claude — противоположность: чистый контекст на старте, память только через явные тулы conversation_search/recent_chats по сырой истории. Разбор Manthan Gupta четырёх систем даёт ключевую формулу: «хранение — легко, политика извлечения — сложно»; «always inject» — худший режим (утечка нерелевантных фактов в задачи, гниение контекста, невозможность отладки), а лучший найденный паттерн — Hermes: крошечная «горячая» память (~1300 токенов) в промпте + «холодная» SQLite с поиском по требованию. Его чеклист: память обязана быть видимой и редактируемой пользователем, retrieval — скоупируемым.

Таксономия CoALA (arXiv:2309.02427) стала отраслевым стандартом: working / episodic (события) / semantic (факты) / procedural (навыки) — это разные хранилища с разными политиками; применять decay эпизодов к семантическим фактам — ошибка корректности. Generative Agents (arXiv:2304.03442) дают формулу ретривала score = recency·w1 + importance·w2 + relevance·w3 (в референс-коде 0.5/2/3) и механизм reflection: при накоплении важности порождаются обобщения, которые сами становятся памятью. По забыванию консенсус: гибридный скор recency×frequency×importance с экспоненциальным (Эббингауз) распадом; сжимать в саммари, а не удалять; «вечнозелёные» записи исключать из decay.

По хранилищу подтверждено бенчмарками: sqlite-vec (брутфорс-скан) даёт единицы миллисекунд до ~100k векторов — на годы хватит персональному ассистенту (это десятки фактов в день); деградирует к 1M (192 мс — 8.5 с). FTS5 встроен, гибрид через Reciprocal Rank Fusion. Локальный эмбеддер nomic-embed-text: 137M параметров, ~274 МБ, 15–50 мс. OpenClaw — готовый образец именно вашего сценария: markdown-файлы как источник истины (MEMORY.md + memory/YYYY-MM-DD.md), SQLite-индекс полностью производный и перестраиваемый, гибрид BM25+вектор (веса 0.7/0.3), MMR-диверсификация, temporal decay с half-life и исключением evergreen-файлов, debounce-переиндексация; «memory flush» перед обрезкой контекста. По маршрутизации ретривала (Cognis, arXiv:2604.19771; enterprise-бенчмарки): ~30% запросов содержат точные якоря (имена файлов, коды ошибок, названия), где BM25 критичен и эмбеддинги проваливаются; дефолт — гибрид RRF ~70/30 в пользу векторов.

Рекомендация для проекта (моя экспертная сборка из подтверждённых блоков): (1) один SQLite-файл: таблица сущностей (файлы/проекты/приложения/люди) с FK-связями — «граф-лайт» без графовой СУБД; append-only журнал эпизодов из awareness-слоя; таблица семантических фактов с би-темпоральными колонками и provenance-ссылкой на эпизоды-источники; FTS5 + sqlite-vec поверх. (2) Горячий слой — 3–5 капированных блоков в промпте (профиль, текущая задача, рабочий контекст), генерируемых из БД тем же анти-дрейф-паттерном, что ваш capability truth. (3) Консолидация — фоновый sleep-процесс в простое (у вас уже есть circuit breakers и квоты — они пригодятся): извлечение фактов из эпизодов, обновление блоков, инвалидация устаревшего, сжатие старых эпизодов в саммари. (4) Ретривал детерминированный, без LLM на чтении, с маршрутизацией keyword/semantic/hybrid. (5) Пользовательская память — в редактируемых markdown-файлах, индекс производный. Стоимость: фоновый процесс ~0 CPU в ожидании, всплески на эмбеддинги (мс) и редкие LLM-вызовы консолидации; RAM — десятки МБ против 2+ ГБ у графового стека; диск — один файл БД, годы накопления уложатся в сотни МБ.

## Идеи

- **Капированные memory-блоки в контексте (core memory)** [MemGPT/Letta (arXiv:2310.08560, docs.letta.com)]: Небольшие именованные текстовые блоки (профиль пользователя, персона, текущая задача) всегда в промпте, с жёстким лимитом длины (~2000 символов) и обязательным description, объясняющим модели назначение блока. Всё остальное — вне контекста, доступ через тулы. | Почему: Решает главный компромисс: важное всегда видно без ретривала, а лимит не даёт памяти сожрать контекст. Ошибка переполнения блока видна агенту и форсирует вытеснение в архив. | Применимость: high — заменить текущую плоскую JSON-память на 3-5 блоков; генерировать их из SQLite тем же анти-дрейф-паттерном, что уже применён для capability truth в core/security.py
- **Sleep-time консолидация (фоновый агент памяти)** [Letta sleep-time compute (arXiv:2504.13171) + OpenAI «Dreaming» (openai.com/index/chatgpt-memory-dreaming)]: Отдельный фоновый процесс в простое переписывает память: извлекает факты из накопленных эпизодов, обновляет блоки, помечает устаревшее, строит саммари. Разговорный агент память не администрирует. | Почему: Убирает латентность и токен-налог из диалога; качество памяти не зависит от того, вспомнила ли модель сохранить факт посреди разговора. Две команды (Letta и OpenAI) пришли к паттерну независимо. До 5x экономии токенов на инференсе. | Применимость: high — у десктоп-ассистента много простоя; awareness-слой уже детектит активность, а существующие квоты/circuit breakers ограничат фоновые LLM-вызовы
- **Би-темпоральные факты: инвалидация вместо удаления** [Zep/Graphiti (arXiv:2501.13956)]: У каждого факта четыре времени: когда стал истинным / перестал (valid_from, valid_to) и когда записан / инвалидирован системой. Противоречащий новый факт закрывает интервал старого, не стирая его. | Почему: Память умеет отвечать «какой была ситуация в марте», корректно обрабатывает исправления и устаревание без потери истории; фактически бесплатный undo-журнал знаний. | Применимость: high — реализовать как 4 колонки в таблице фактов SQLite, НЕ тащить Neo4j/Graphiti (2 ГБ RAM и несколько LLM-вызовов на эпизод записи)
- **SQLite + FTS5 + sqlite-vec + RRF как единственное хранилище** [Alex Garcia (alexgarcia.xyz, автор sqlite-vec), sqlite-rag, OpenClaw builtin engine]: Один файл БД: FTS5 (BM25) для точных совпадений, sqlite-vec для семантики, слияние ранков через Reciprocal Rank Fusion. Брутфорс-скан — единицы мс до ~100k векторов. | Почему: Ноль инфраструктуры, ноль фоновых демонов, бэкап = копирование файла. Персональный ассистент за годы не выйдет за 100k записей; при деградации есть квантование и партиционирование. | Применимость: high — это хребет всей подсистемы памяти; локальный эмбеддер nomic-embed-text (274 МБ, 15-50 мс) закрывает и офлайн, и LLM-независимость
- **Файлы как источник истины, индекс производный** [OpenClaw (docs.openclaw.ai/concepts/memory)]: Пользовательская память живёт в markdown (MEMORY.md — вечное, memory/YYYY-MM-DD.md — дневные заметки); SQLite-индекс строится из файлов, при удалении перестраивается, правка файла триггерит debounce-реиндексацию. | Почему: Память видима, редактируема в любом редакторе, диффабельна, версионируется git-ом; нет скрытого состояния — критично для доверия и отладки single-user системы, сопровождаемой одним человеком. | Применимость: high — идеально для слоя «явных» фактов и предпочтений; журнал эпизодов при этом остаётся в чистом SQLite (машинные данные)
- **Память как тул, а не фоновая инъекция (hot/cold split)** [Claude memory (shloked.com/writing/claude-memory, simonwillison.net) и Hermes-паттерн (manthanguptaa.in)]: Крошечный горячий набор (~1-2k токенов) всегда в промпте; всё остальное — холодное хранилище, доступное через явные поисковые тулы, вызовы которых видны пользователю. | Почему: Стабильный промпт дружит с кэшированием, нерелевантные воспоминания не протекают в несвязанные задачи, каждое обращение к памяти отлаживаемо и объяснимо. | Применимость: high — прямо задаёт границу между memory-блоками и тулом memory_search в новом ядре
- **Скоринг ретривала recency × importance × relevance + reflection** [Generative Agents (arXiv:2304.03442)]: Ранжирование памяти суммой трёх нормированных сигналов (в референс-коде веса 0.5/2/3); при накоплении суммарной важности фоново порождаются обобщения (reflections), которые сами становятся памятью. | Почему: Дёшево и детерминированно решает «что из тысяч записей достать»; reflections превращают сырые эпизоды в переиспользуемые выводы о привычках пользователя. | Применимость: medium — брать формулу скоринга и триггер по накопленной важности; top-k держать 3-5, больше 10 записей в контексте вредит
- **Забывание = decay-скор + сжатие в саммари + evergreen-исключения** [Обзор политик забывания (arXiv:2512.13564, FSFM arXiv:2604.20300), OpenClaw temporal decay]: Скор записи = f(давность, частота обращений, важность) с экспоненциальным распадом (half-life недели); низкоскоровое не удаляется, а сжимается в саммари; помеченное evergreen из decay исключено. | Почему: Не даёт памяти стать свалкой, сохраняя восстановимость: устаревшее уходит из ретривала, но след остаётся. Staleness — вопрос корректности: старый факт может противоречить новому. | Применимость: high — работа для того же sleep-процесса; политика забывания должна различаться для эпизодов (агрессивный decay) и семантических фактов (инвалидация, не decay)
- **Маршрутизация ретривала: keyword / semantic / hybrid** [Cognis (arXiv:2604.19771), Redis blog, EnterpriseRAG-Bench (arXiv:2605.05253)]: ~30% запросов к памяти содержат точные якоря (имена файлов, названия проектов, коды ошибок) — там нужен BM25; парафразы — эмбеддинги; дефолт — RRF-гибрид с весами ~0.7 вектор / 0.3 текст. | Почему: Для ассистента, оперирующего файлами и приложениями, точные идентификаторы — постоянный случай, и чистые эмбеддинги на них систематически проваливаются (обучены на публичных корпусах, не знают локальный жаргон). | Применимость: high — простой роутер по признаку «есть ли в запросе идентификатор» + гибрид по умолчанию; без LLM на пути чтения
- **Раздельные хранилища по типам памяти (CoALA)** [CoALA (arXiv:2309.02427) — таксономию приняли Letta, mem0, LangChain]: Эпизодическая (журнал событий awareness-слоя), семантическая (факты о файлах/проектах/предпочтениях), процедурная (сохранённые сценарии автоматизации) память — разные таблицы с разными политиками записи, ретривала и забывания, плюс provenance-ссылки от фактов к эпизодам-источникам. | Почему: Каждый факт трассируется к событию-источнику (цитируемость, отладка); политики не конфликтуют — decay эпизодов не ломает корректность фактов. Процедурная память — естественное место для «автоматизации повторяющихся сценариев» из целей проекта. | Применимость: high — прямой каркас схемы БД нового ядра
- **Урок mem0 v3: ADD-only запись + entity linking вместо LLM-роутера** [mem0 OSS v3 migration (docs.mem0.ai/migration/oss-v2-to-v3)]: mem0 отказался от LLM-решения ADD/UPDATE/DELETE на каждой записи и от внешних графовых БД (~4000 строк удалено) в пользу однопроходного извлечения, связывания сущностей и мультисигнального ретривала. | Почему: Эволюция зрелого проекта под давлением реальной эксплуатации: LLM-роутер записи оказался дорогим чёрным ящиком. Разрешение конфликтов уехало на этап чтения и фоновую обработку. | Применимость: medium — подтверждает выбор: писать дёшево и append-only, разбираться с противоречиями в sleep-процессе

## Анти-паттерны

- **Always-inject: полный профиль пользователя в каждом промпте** [ChatGPT memory (реверс Rehberger/embracethered.com, Khemani/shloked.com; критика — manthanguptaa.in)]: Нерелевантные воспоминания протекают в несвязанные задачи (просьба о рецепте возвращает идеи, привязанные к недавнему переезду), контекст растёт и «гниёт» (качество моделей падает с длиной входа), промпт-кэш инвалидируется при каждом изменении памяти, а отладка невозможна — профиль пишется отдельным пайплайном, которого нет в логах запроса. Самый копируемый паттерн, потому что самый простой в реализации.
- **Графовая СУБД и temporal KG на десктопе** [Zep/Graphiti + Neo4j (getzep/graphiti, mem0 self-host guide, критика — medium.com/@visrow)]: Neo4j требует ~2 ГБ RAM фоново — против цели «минимальный фоновый CPU/RAM»; каждый эпизод записи стоит нескольких LLM-вызовов (извлечение узлов, дедуп, рёбра, противоречия) — пользователи Graphiti жалуются на стоимость при масштабной инжестии; онтология требует недель работы против дней у векторного пайплайна. Правило: если нет запросов вида «что можно вывести транзитивно» — граф это дорогой document store. Даже mem0 выпилил внешние графовые БД в v3. Для связей файл-проект-приложение достаточно FK-таблицы в SQLite.
- **LLM-вызов на каждую запись в память (роутер ADD/UPDATE/DELETE)** [mem0 классический пайплайн (arXiv-разборы, emergentmind.com/topics/mem0-system)]: Стоимость записи пропорциональна числу реплик независимо от новизны; решения LLM — недетерминированный чёрный ящик (невоспроизводимые UPDATE/DELETE); сам mem0 отказался от схемы в v3. Для ассистента, где awareness-слой генерирует сотни событий в день, это ещё и постоянная фоновая нагрузка.
- **Самоуправляемая память внутри разговорного агента** [Оригинальный MemGPT — признано самим Letta (letta.com/blog/sleep-time-compute)]: Если модель не вызвала сохранение — факт потерян навсегда; операции памяти тормозят ответ и жгут токены диалога; качество памяти = качество сиюминутных суждений модели. Letta сам признал проблему и вынес управление памятью в отдельный фоновый агент.
- **Плоский JSON / 100% retention без индекса и политики забывания** [Текущая память MARK XXXV; критика 100% retention — fazm.ai, обзор arXiv:2512.13564]: Без поиска память либо целиком грузится в контекст (не масштабируется за месяцы), либо не используется; без забывания копится шум, растёт латентность ретривала, устаревшие факты противоречат новым — staleness это баг корректности, не только стоимости. Годы накопления гарантированно превращают такой стор в свалку.
- **Жёсткое удаление как способ забывания** [Обзоры политик забывания (FSFM arXiv:2604.20300, dev.to «The Case for Intelligent Forgetting»)]: Агрессивный prune стирает редкие, но важные знания безвозвратно; для персонального ассистента потеря памяти о пользователе — worst case UX. Правильно: сжатие в саммари + закрытие интервала валидности + исключение evergreen-записей; удалять только по явной команде пользователя.
- **Скрытая, нередактируемая память** [ChatGPT User Insights (нельзя посмотреть/править без промпт-хаков) vs чеклист manthanguptaa.in]: Пользователь не может исправить ложный вывод системы о себе — «отлаживаешь отношения, а не запрос»; для single-user системы на годы доверие к памяти критично. Память обязана быть видимой, редактируемой и скоупируемой — иначе ошибки экстракции накапливаются необратимо.
- **Эмбеддинги как единственный механизм поиска** [EnterpriseRAG-Bench (arXiv:2605.05253), Cognis (arXiv:2604.19771), redis.io]: На точных якорях (имена файлов, названия проектов, коды ошибок — постоянные запросы desktop-ассистента) векторный поиск систематически проваливается: в enterprise-бенчмарке BM25 обошёл эмбеддинги даже на «семантических» вопросах (32.8% корректности у векторов). ~30% реальных запросов к памяти содержат такие якоря.
