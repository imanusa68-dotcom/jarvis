## 1. Архитектурный анализ задачи

### 1.1. Что мы на самом деле строим

«Jarvis» декомпозируется на шесть взаимосвязанных, но разных инженерных задач:

1. **Естественно-языковой интерфейс к ПК** — голос и текст как основной способ управлять
   компьютером. Требование латентности: простая команда должна исполняться быстрее, чем
   пользователь сделал бы её руками, иначе ассистента перестают звать (урок Cortana).
2. **World model** — актуальное представление о рабочем окружении: файлы, папки, окна,
   приложения, проекты, история изменений, связи, текущая задача. Это *данные*, а не «магия»:
   индекс + журнал событий + производные.
3. **Слой действий** — типизированные операции над ОС с подтверждениями, журналом и откатом.
   Требование: случайное повреждение данных пользователя должно быть *конструктивно
   невозможным состоянием*, а не следствием благоразумия модели.
4. **Память** — накопление знаний о пользователе, его файлах, привычках и предпочтениях
   на горизонте лет, без превращения в свалку.
5. **Мозг** — агентный цикл: маршрутизация запросов, вызов инструментов, многошаговые планы,
   восстановление после ошибок. Независимый от конкретной LLM.
6. **Платформа** — always-on демон на Windows: бюджет ресурсов, шина событий, плагины,
   наблюдаемость, тестируемость, обновление самой системы.

### 1.2. Неторгуемые требования

Исследование и судейская панель сошлись на трёх требованиях, которые реализуются
**структурно** (в коде границ), а не дисциплиной:

- **Р1. Единый гейт разрешений для всех путей исполнения.** Любой вызов инструмента —
  из live-сессии, из текстового чата, из шага плана, из плагина — проходит через одну
  функцию `dispatch()`. Второго пути к действиям в системе нет. Это прямое лекарство от
  подтверждённой дыры прототипа: `agent/executor` работает мимо `core/security.py`,
  а свободный параметр `command` в `cmd_control` обходит allowlist.
- **Р2. Независимость от LLM-провайдера.** Смена модели — правка одной строки конфига;
  смена провайдера — написание адаптера (~200–500 строк), а не переписывание системы.
- **Р3. Откат файловых операций.** У каждой мутирующей операции есть preview, журнальная
  запись и обратная операция; «отмени последнее» работает голосом.

### 1.3. Рамочные ограничения

- **Один сопровождающий, горизонт 5+ лет.** Каждая сущность (процесс, БД, формат, зависимость)
  оплачивает своё существование. Оверинжиниринг — такой же враг долгоживучести, как и плохая
  модульность.
- **Always-on на десктопе.** Бюджет idle: движок ≤150 МБ RSS, <1% CPU, ноль пробуждений чаще
  раза в минуту; всё тяжёлое — лениво и на фоновом приоритете.
- **Ассистент работает каждый день миграции.** «Выключим на полгода и перепишем» — запрещённый
  путь (урок «долины смерти» rewrite-проектов и признание Apple, что гибрид LLM поверх
  legacy-ядра Siri «не работал»).
- **Ассистент не работает от администратора.** Elevation — только у изолированных внешних
  компонентов (служба Everything), никогда у самого движка.

## 2. Обзор существующих решений

Краткая выжимка; полные дайджесты с источниками — `docs/architecture/research/research_*.md`
и `gapfill_*.md`.

### 2.1. Агентные фреймворки и оркестрация

Индустрия сошлась на формуле **«простой однониточный цикл + серьёзная инфраструктура вокруг
него»**. Claude Code — эталон: главный цикл — буквально while-loop с плоской историей
сообщений; вся инженерия — в пайплайне разрешений (hooks → deny → allow → ask → режим; deny
непереопределяем никаким режимом), компактации контекста (~92% заполнения), steering-очереди
для инъекции реплик без рестарта и субагентах со свежим контекстом. То же независимо
формулируют Anthropic («Building Effective Agents»), 12-Factor Agents («own your control
flow») и Cognition («Don't Build Multi-Agents»: работают только схемы с однопоточной записью).

Судьба отдельных LLM-планировщиков показательна: Semantic Kernel депрецировал и удалил свои
планировщики (в их бенчмарке Stepwise-планировщик тратил 1869 токенов против 755 у нативного
function calling) — ReAct теперь «вшит» в модели. CrewAI-стиль manager-worker в независимом
разборе не работает как задокументировано. Production-кейсы отказа от LangChain (Octomind,
Zup) сводятся к одному: цепочечная модель не ложится на stateful-цикл, отладка через 5 слоёв
абстракций хуже собственного кода; LangChain v1.0 сам признал критику и переориентировался
на «голый» agent loop.

Самая ценная механика — **interrupt/checkpoint из LangGraph**: подтверждение опасной операции
превращается из блокирующего диалога в данные (pending-операция в SQLite переживает рестарт,
показывается в UI, редактируется). Паттерн достаточно мал, чтобы реализовать самостоятельно,
не принимая зависимость от экосистемы LangChain на 5 лет.

**MCP** принимается дозированно: внутренний реестр инструментов делается MCP-совместимым по
форме (name, description, JSON Schema + колонка риска), сторонние MCP-серверы подключаются
адаптером, свои инструменты остаются in-process. Документированная цена MCP — токены: схемы
съедают до 40–50% контекста, порог деградации выбора — 10–15 активных тулов; лечится ленивым
скоупом схем (−85% токенов по данным Anthropic Tool Search).

**Вывод:** не брать фреймворк-каркас; свой цикл ~2 тыс. строк; interrupt-паттерн — свой поверх
SQLite; MCP — граница расширения; code-as-action (генерация произвольного Python как способ действия) — запрещён: гейт не может
классифицировать риск произвольного кода, аудит и откат разваливаются.

### 2.2. Память

- **MemGPT/Letta**: иерархия «core-блоки в контексте (капированные, ~2000 симв.) → recall →
  archival». Признанная слабость самоуправляемой памяти («если модель не сохранила — факт
  потерян») закрыта **sleep-time compute**: отдельный фоновый агент переписывает память в
  простое. OpenAI независимо пришла к тому же («dreaming») — сильный сигнал конвергенции.
- **Zep/Graphiti**: би-темпоральные факты (valid_from/valid_to + recorded_at) — противоречащий
  факт не удаляется, а закрывается по интервалу. Идею берём (4 колонки в SQLite), стек нет
  (Neo4j ~2 ГБ RAM, несколько LLM-вызовов на каждую запись).
- **mem0 v3** сам отказался от LLM-роутера ADD/UPDATE/DELETE на каждой записи и от внешних
  графовых БД (~4000 строк удалено) в пользу дешёвой append-only записи + разбор противоречий
  на чтении и в фоне.
- **Продакшн-полюса**: ChatGPT инжектит профиль в каждый промпт (худший режим: утечка
  нерелевантного, гниение контекста, инвалидация кэша); Claude — чистый контекст + явные
  поисковые тулы. Лучший найденный паттерн — hot/cold: крошечная горячая память (~1–2k
  токенов) в промпте + холодная SQLite с поиском по требованию.
- **Хранилище**: SQLite + FTS5 (BM25) + sqlite-vec (брутфорс KNN — единицы мс до ~100k
  векторов) + слияние RRF. ~30% запросов к памяти содержат точные якоря (имена файлов),
  где BM25 обязателен. Память должна быть видимой и редактируемой пользователем.

### 2.3. World model рабочего стола

Все зрелые системы наблюдения сходятся к одной схеме: **bootstrap-снапшот + инкрементальный
поток событий ОС + компактирование при записи + жёсткий бюджет хранения**.

- **Everything (voidtools)** — эталон: первичный индекс читается из NTFS MFT (~1 млн файлов
  за ~1 мин, ~100 МБ RAM), дальше — только USN Change Journal, который ведёт сам драйвер NTFS:
  изменения не теряются, пока приложение выключено (catch-up при старте). Microsoft прямо
  позиционирует журнал для indexing-сервисов и называет сканирование неприемлемым. Это
  приговор watchdog-подходу прототипа (теряет историю между запусками, искажает семантику,
  переполняет очередь на всплесках).
- **Важная поправка судей**: чтение MFT/USN (`FSCTL_ENUM_USN_DATA`, открытие `\\.\C:`) требует
  прав администратора — именно поэтому Everything ставит службу. Основной путь — делегировать
  Everything (его служба уже решает elevation); IPC — WM_COPYDATA/SDK DLL или ES.exe (в 1.5 —
  named pipe). Свой USN-ридер — резерв, и только с крошечным elevated-хелпером; движок целиком
  под админом — запрещённое состояние.
- **ActivityWatch**: heartbeat-слияние (часы одинаковой активности → одна строка интервала);
  AFK — системное «время с последнего ввода». **Окна** — событийно через
  `SetWinEventHook(EVENT_SYSTEM_FOREGROUND, OUTOFCONTEXT)`, не поллингом.
- **screenpipe** — предостережение: непрерывный медиазахват в ядре не выдержал собственных
  бюджетов (issue: CPU >100%, утечки до OOM 25 ГБ; один вспомогательный poll-цикл дал 56%
  всех строк логов). Сырых скриншотов в v1 не делаем — только производные (пути, заголовки,
  интервалы, извлечённый по требованию текст): они на 2–3 порядка дешевле и закрывают 95%
  запросов.
- **Windows Recall (редизайн 2024)** — образец архитектурного ответа на приватность: хранилище
  истории изолировано, UI — недоверенный потребитель, доступ только через шлюз, квоты диска,
  retention, индикатор записи, opt-in. Переносим принцип: `history.db` читается только через
  модуль-шлюз `world_gateway`, в облачную LLM уходит только производный текст (граница Rewind).

### 2.4. Слой действий: подтверждения и откат

- **«Rules are enforced by the harness, not the model»** (Claude Code, дословно из
  документации): политика живёт в коде диспетчера, промпт лишь информирует модель. Поверх
  режимов — немодифицируемый «пол»: катастрофические операции (корни дисков, %USERPROFILE%,
  каталог самого ассистента) требуют подтверждения в любом режиме.
- **Типизированные действия со схемами** (Home Assistant service registry): одна декларация
  даёт валидацию, UI, tool-definitions и вход для политики. Фильтрация опасного по строкам
  аргументов — обходимый анти-паттерн (сам Claude Code отказывается от таких правил).
- **План как неизменяемый артефакт** (Terraform plan/apply): подтверждение привязывается к
  хэшу payload; расхождение при исполнении — отказ (документированный класс багов «показали
  одно, исполнили другое» при перегенерации вызова моделью).
- **Preview — контракт хендлера, не эмерджентное свойство** (урок Ansible check mode: модули
  без `supports_check_mode` молча врут). PowerRename показывает UX: живой дифф до применения.
- **Откат** — компенсации, не снапшоты: saga-журнал (intent до, completion после, идемпотентная
  обратная операция), staging-копии, поверх — undo-стек Command-паттерна с человекочитаемыми
  подписями (Nautilus). Нижний слой — платформенные API: удаление только через `IFileOperation`
  с корзиной и undo-record Explorer; перезапись — temp-файл + `ReplaceFile` (официальная
  замена депрецированного TxF). System Restore Points документы не покрывают.
- **Capability-объекты** (WASI preopens): модуль получает не строки путей, а `ScopedRoot` —
  хэндл разрешённого корня с канонизацией и запретом побегов на уровне типа. Класс ошибок
  «забыл проверить путь» (copy_file прототипа) исчезает конструктивно.
- **4 уровня риска** вместо бинарного confirm: read → авто; обратимое → авто + журнал + тост
  «Отменить»; внешнее → ask; необратимое → блокирующее подтверждение с точным payload.
  «Подтверждать всё» документированно ломает надзор: пользователь жмёт «да» рефлекторно.

### 2.5. Абстракция LLM-провайдеров

- **Batch-слой — решённая задача**: Chat Completions стал lingua franca (Ollama, LM Studio,
  llama.cpp, vLLM, OpenRouter говорят его нативно). Правильный путь — обёртки **официальных
  SDK** с нормализацией к внутренним типам (философия any-llm), а не реимплементация HTTP.
  Два адаптера закрывают всё: google-genai (новый SDK) + openai-совместимый.
- **LiteLLM как зависимость — нет** (спроектирован под мультитенантный прокси на 100+
  провайдеров; история supply-chain-инцидентов 2026 неприемлема для программы с доступом ко
  всем личным файлам); **как источник паттернов — да**: fallback-обёртка ПОВЕРХ retry, классы
  fallback по таксономии ошибок, CooldownCache, поле raw рядом с нормализованным (OpenRouter).
- **Structured output** — минное поле поднаборов JSON Schema (OpenAI strict ≠ Gemini
  responseSchema ≠ Anthropic; Gemini отказывает тихо). Правило: общий поднабор (плоско, без
  union), клиентская валидация, одна repair-итерация. Локально llama.cpp конвертирует схему
  в GBNF-грамматику — валидный JSON даже на 4B-модели: роли memory-extractor и classifier —
  идеальные кандидаты на локальную модель.
- **Realtime-голос полностью не абстрагируется** — подтверждено болью LiveKit (issue #6002:
  Gemini Live не умеет GPT-семантику tool control) и Pipecat (Gemini не эмитит speech-события).
  Жизненные циклы фундаментально разные: у Gemini resumption-хэндлы (2 ч) + GoAway + compression,
  у OpenAI Realtime — жёсткие 60 мин без resumption (context-replay вручную). Честная граница:
  абстрагировать **семантические события сессии** + явные capability-флаги; wire-протокол,
  VAD, форматы — в непереносимых драйверах.
- **Реестр «роль→модель»** (Continue.dev): registry.yaml с ролями live-voice / chat / planner /
  memory-extractor / classifier / embedder, fallback-цепочками и capability-валидацией на
  старте. Убивает 36 хардкодов имён моделей и 14 дублей загрузки ключа по построению.

### 2.6. Плагины и событийная архитектура

- **VS Code**: ценна не процессная изоляция (она существует ради тысяч недоверенных авторов —
  цена ~7–10 МБ/процесс + RPC), а **декларативность**: манифест читается без исполнения кода,
  ленивая активация — неиспользованные расширения не стоят ни байта RAM.
- **Home Assistant** — образец событийного ядра: событийная шина («факты в прошедшем времени»)
  отделена от service registry («команды с валидацией»); per-listener try/except — упавший
  подписчик не роняет ни шину, ни соседей; lifecycle интеграций
  loaded / not_ready (retry+backoff, кап 1 час) / auth_required / error.
- **Obsidian** доказывает жизнеспособность in-process плагинов годами при дисциплине
  Component-паттерна: всё зарегистрированное автоматически снимается при выгрузке → безопасный
  hot-reload.
- **pluggy** (ядро pytest) — готовый механизм hookspec/hookimpl с валидацией сигнатур и
  hookwrapper (идеален для гейта и журналирования вокруг вызова действия).
- **Событийная часть**: event sourcing — паттерн уровня модуля (журнал действий), не всей
  системы; bounded-очереди подписчиков с политиками coalesce / latest-wins / block; маленький
  фиксированный каталог типизированных событий + correlation ID — иначе «coupling without
  a call stack». Команды по шине не летают.
- **Урок Mycroft→OVOS и Wyoming**: единственное, что нельзя менять часто, — контракт шины и
  протоколы; реализации вокруг сменяемы (шину OVOS независимо переписали на Rust и C++).
  Брокер (MQTT/Redis) для single-user системы — лишний движущийся элемент (Rhasspy v2→v3).

### 2.7. Планирование и исполнение

- **Трёхуровневый роутер**: прямой ответ / лёгкий цикл ≤2–3 хода (90% трафика десктопа) /
  Plan-and-Execute для многошаговых. Классификатор — правила + быстрый structured-вызов
  основной модели; обученный роутер при сотнях запросов в день — оверинжиниринг.
- **План — данные, а не рассуждение**: типизированный список шагов с плейсхолдерами `$1`
  (подстановка кодом, без LLM-вызова между шагами), хранится строками в `execution_log`
  (намерение ДО исполнения, результат ПОСЛЕ — WAL-паттерн; Persistasaurus/DBOS доказывают,
  что durable execution на SQLite — это сотни строк, а не Temporal).
- **Гейт — в исполнителе шага, по фактическим аргументам** (аргументы вычисляются в рантайме;
  гейтить план «на бумаге» недостаточно). Подтверждение — durable interrupt
  (WAITING_FOR_SIGNAL + хэш-пиннинг + TTL).
- **Восстановление шага** — декларативная таблица «класс ошибки → стратегия»
  (retry/skip/substitute/replan/escalate); ошибки остаются в контексте replanner'а (Manus).
- **Бюджеты — свойство ядра, не опция** (уроки AutoGPT/BabyAGI: $80 за ночь без лимитов):
  ходы, шаги, replan'ы, wall-clock, дневная стоимость — проверка ДО платного вызова; детектор
  стагнации по повторному вызову с идентичными аргументами.

### 2.8. Производительность always-on Python-демона

- **Импорты — главный налог на RAM**: pandas ~44 МБ, boto3 ~25 МБ только за импорт; кейс
  демона 708→22 МБ изоляцией импортов. Лекарство: ленивые импорты тяжёлых библиотек внутри
  хендлеров (профилировать `-X importtime`; с Python 3.15 — явный `lazy import`, PEP 810).
- **Спящий демон**: `await event.wait()` / `queue.get()` вместо poll-циклов; TaskGroup против
  осиротевших тасок; редкая периодика с грубыми допусками (таймер-коалесцинг ОС).
- **Фон на Windows**: одного низкого CPU-приоритета мало — диск фонового потока душит систему;
  нужен `PROCESS_MODE_BACKGROUND_BEGIN` (CPU+I/O+page разом) + EcoQoS (E-ядра; так работает
  индексатор Windows 11).
- **SQLite**: WAL + synchronous=NORMAL + busy_timeout + PRAGMA optimize → 100k+ SELECT/с;
  FTS5 — миллионы строк с мс-задержкой; sqlite-vec — с запасом для сотен тысяч чанков 384d.
- **Локальные эмбеддинги**: all-MiniLM (22M, 384d, ~14k предл./с на CPU) через fastembed/ONNX;
  документированный рост памяти fastembed (1.5→6 ГБ) лечится дизайном «эфемерный воркер с
  рестартом по порогу RSS».
- **Процессы**: UI отдельно (Chromium/VS Code-прецедент), между процессами — ID строк SQLite,
  не блобы (pickle-издержки съедают выигрыш). Rust — только через выбор нативно-backed
  библиотек; свой PyO3 — по профилировщику, не заранее.

### 2.9. Инженерные post-mortem похожих продуктов

- **Mycroft умер, OVOS выжил**: пережила только развязанная часть (websocket-шина, плагины
  STT/TTS); «open in code, but not in practice» (привязка к облаку Selene) убила проект.
  Для каждой облачной зависимости обязана существовать local-first альтернатива.
- **Rhasspy v2→v3 (Wyoming)**: крошечный протокол (JSONL + PCM, peer-to-peer) пережил
  собственные референсные реализации. Маленький стабильный контракт > любая реализация.
- **Siri**: гибрид LLM поверх legacy-ядра команд «не работал» (признание Federighi) — год
  задержки и переписывание с нуля. Не встраивать новый контур внутрь старого main.py.
- **AutoGPT**: автономность без бюджетов и внешнего критерия завершения не работает (24%
  успеха, бесконечные циклы); выживший AutoGPT — конструктор workflow с границами от человека.
- **Recall v1 → редизайн**: сбор «всего подряд» в открытую БД пришлось публично
  перепроектировать; правильная форма — изоляция хранилища, шлюз, opt-in, квоты, индикатор.
- **Raycast**: launcher быстр, потому что расширения — в отдельном управляемом рантайме с
  лимитами, через границу — только диффы, принимаются только зарегистрированные сообщения;
  индексатор — отдельный процесс на событиях ФС.
- **Willow**: латентность как проектное требование — «конец речи → действие ≤500 мс»
  достигается декомпозицией по звеньям и кэшем TTS.
- **Cortana**: ассистент, не выигрывающий у клавиатуры по стоимости взаимодействия, отключают;
  точность распознавания не спасает.

### 2.10. Голосовой конвейер (русский язык)

- **Wake word**: openWakeWord поставляет предобученную модель **«hey jarvis»** из коробки
  (Windows через onnxruntime, CPU-нагрузка пренебрежима, Apache 2.0 код). Porcupine русский
  не поддерживает и привязывает к консоли вендора.
- **VAD**: Silero VAD — фактический стандарт (MIT, ~2 МБ, <1 мс на 32-мс чанк, ONNX без
  PyTorch); один VAD-слой обслуживает и гейтинг Gemini Live, и каскад.
- **Локальный STT для русского** — главная находка: **GigaAM** (Сбер, MIT с v2, ONNX,
  225 МБ) даёт WER на русском примерно вдвое лучше Whisper large-v3 и работает в реальном
  времени на CPU; v3-e2e — с пунктуацией. faster-whisper large-v3 на CPU непригоден для
  диалога (RTF ~2.5); turbo/medium — на грани; с GPU — русские файнтюны (antony66: WER
  9.84→6.39). Moonshine русского не имеет.
- **Локальный TTS** — узкое место: Kokoro русского не имеет; XTTS v2 живой, но лицензия CPML
  и мёртвый апстрим; **Silero TTS v4/v5** — лучший локальный русский (автоударения, 48 кГц,
  быстрый CPU, CC BY-NC — для личного проекта ок); Piper (русские голоса medium-качества,
  GPL-форк) — резерв; **edge-tts** — лучший бесплатный облачный (риск ToS).
- **Латентность каскада**: воспринимаемая задержка = end-of-utterance (~300–500 мс тишины)
  + LLM TTFT + TTS TTFB; цель ~800 мс, отлично <500 мс. Рычаги: sentence-chunked TTS
  (−200–500 мс), кэш аудио частых фраз («Слушаю», «Сделано»), barge-in проектируется в
  интерфейсе с первого дня (тройная отмена: флаш TTS, отмена LLM, рестарт STT).
- **Гибрид**: локальный wake word гейтит открытие тарифицируемой Live-сессии (приватность:
  аудио не уходит до срабатывания; экономия квоты); нужны refractory-период против ложных
  срабатываний и idle-timeout закрытия сессии.

### 2.11. Операционная обвязка (добор критика полноты)

- **Тестирование агентной системы** (`gapfill_0`): пирамида «инфраструктура снизу, LLM
  сверху» — 90% страховочной сетки не требует модели. Ключевые паттерны: fake-модель на
  границе собственного интерфейса (aider mock_send), формат golden-сценария EvalSpec
  (files/prompt/expect-предикаты по конечному состоянию ФС, не по тексту модели),
  crash-injection по методологии SQLite (kill дочернего процесса в параметризованной
  crash-точке + проверка recovery), hypothesis stateful для саги/undo, import-linter как
  CI-гейт архитектуры, FakeVoiceSession с событийными трейсами для interruption-кейсов
  (паттерн Pipecat Evals), pass^k (не pass@k) для data-safety сценариев. Живые LLM-вызовы
  в обязательном CI-гейте — анти-паттерн.
- **Наблюдаемость** (`gapfill_1`): все «стандартные» self-hosted стеки (Langfuse — 6
  контейнеров/1.5 ГБ, Phoenix — 270–300 МБ idle) не проходят бюджет. Рабочая модель —
  «трейсы в своей SQLite + Datasette по требованию» (прецедент CLI `llm` Уиллисона +
  append-only JSONL Claude Code): таблицы events и llm_calls (content-addressed replay-кэш
  по хэшу запроса), turn_id через contextvars, flight-recorder (deque последних ~500 событий,
  дамп при ошибке), двухуровневая ретенция (сырьё коротко, агрегаты вечно), метрики
  (confirm-rate, undo-rate, эскалации) — SQL-view. Цена: ~300–600 строк, RSS ≈ 0.
- **Жизненный цикл системы** (`gapfill_2`): git-тег + uv.lock + управляемый Python (не
  PyInstaller: onefile в %TEMP%, который ОС чистит); автозапуск — Task Scheduler «At log on»
  (НЕ Windows-служба: session 0 не видит окна/аудио); single-instance — именованный мьютекс;
  graceful shutdown — WM_CLOSE/WM_ENDSESSION; обновления — версионные слоты releases/<tag>
  с атомарным junction-указателем + транзакция «снапшот → миграция → golden-смоук →
  commit/rollback»; миграции — PRAGMA user_version + нумерованные SQL-файлы (по цепочке на
  файл БД), политика даунгрейда refuse-to-start; бэкап живых WAL-баз ТОЛЬКО через
  backup API / VACUUM INTO (копирование файла молча теряет данные), еженедельный
  restore-тест; лицензии стека чисты (MIT/Apache/PSF), единственная жёлтая зона — Piper
  (GPL-3.0) → за процессной границей.

## 4. Три варианта архитектуры и вердикт судей

Были независимо спроектированы три полных варианта (см. `research/design_*.md`):

- **A «Эволюция»** — максимум переиспользования, ассистент работает на каждом этапе,
  гейт закрывается первым (через 2–3 недели); честная оценка выживаемости кода 45–55%.
- **B «Чистое ядро»** — микроядро <2000 строк, всё — плагины, 4 постоянных процесса,
  per-domain БД за шлюзами, WebSocket-мост шины; лучшие контракты, но «долина смерти»
  миграции 6–9 месяцев и самый тяжёлый idle-профиль.
- **C «Прагматичный минимализм»** — 2 долгоживущих процесса, 2 файла БД, правило
  «абстракция оплачивает существование», целевые 8–12k строк; все швы долгоживучести
  на месте (манифесты, MCP, VoiceSession, registry.yaml, каталог событий).

Панель из трёх судей (линзы: долгоживучесть / производительность+соло-сопровождение /
защита данных+UX+реализм миграции). Суммы баллов по 6 критериям × 3 судей:
**C — 150, A — 138, B — 124**. Двое судей выбрали C, один (data-safety) — A, отметив, что
«по нейтральной сумме выиграл бы C». Согласованный вердикт: **основа — C, с пересадкой
миграционной механики из A и контрактной гигиены из B**:

- из A: гейт РАНЬШЕ манифестов (этап 0.5: тонкий `dispatch()` поверх существующей
  policy-таблицы, немедленное упразднение сырого `command`); golden-сценарии как merge-гейт
  каждого этапа; feature-flag + журнал расхождений при подмене цикла; правило «старый путь
  УДАЛЁН, не выключен» с календарным лимитом двойных механизмов;
- из B: управление каталогом событий (frozen-модели в одном модуле, api_version, строгая
  аддитивность, генерируемый EVENTS.md, отладочная консоль-подписчик); lifecycle-состояния
  плагинов (loaded/not_ready+backoff/auth_required/error); perf-бюджеты как тестируемые
  артефакты; скаффолд-генератор тула; готовый чертёж выноса ingest в отдельный процесс.

Судьи также нашли **фактические дефекты**, закрытые в итоговой архитектуре (§5):
Everything IPC — это WM_COPYDATA/SDK DLL/ES.exe, не named pipe (в 1.4); «DPAPI шифрует файл
БД» — нерабочее утверждение для живого WAL-файла; чтение USN/MFT требует elevation;
Playwright-MCP пишет файлы (downloads, профиль) мимо гейта; IFileOperation — COM, нужен
выделенный STA-поток; tkinter поверх WebSocket требует моста «поток → mainloop»; бэкап WAL
простым копированием несогласован; бюджет отклика C (≤1.5 с) ужесточён до ≤500 мс.

## 5. Предлагаемая архитектура (MARK XXXVI)

### 5.1. Философия

Три неторгуемых требования (Р1–Р3) реализуются в коде границ. Всё остальное подчинено двум
метрикам: фоновая стоимость и стоимость сопровождения одним человеком. Каждая абстракция
оплачивает существование: если контракт не защищает Р1–Р3 и не экономит код минимум в двух
местах — это просто функция. Целевой объём ядра — **8–12 тыс. строк** (vs 23k прототипа).

### 5.2. Процессная топология

```
┌────────────────────────────┐   WebSocket (каталог JSON-сообщений)
│  jarvis-ui  (тонкий клиент)│◄──────────────┐
└────────────────────────────┘               │
┌─────────────────────────────────────────────────────────────┐
│  jarvis-engine (asyncio-демон, idle ≤150 МБ, <1% CPU)       │
│  цикл · роутер · гейт dispatch() · шина · память · llm      │
│  voice-драйвер · world_gateway · store (писатель jarvis.db) │
└─────────────────────────────────────────────────────────────┘
       │ stdio (MCP)              │ IPC (ID строк, не блобы)
┌──────────────────┐   ┌───────────────────────────────────────┐
│ Playwright-MCP   │   │ ingest-воркер (ленивый, background+   │
│ (браузер, песоч- │   │ EcoQoS): Everything/USN/WinEvents →   │
│ ница ScopedRoot) │   │ фильтр/дедуп/коалесц → history.db     │
└──────────────────┘   └───────────────────────────────────────┘
                       ┌───────────────────────────────────────┐
                       │ эфемерные воркеры: эмбеддер (рестарт  │
                       │ по RSS), TTS (Piper/GPL за границей)  │
                       └───────────────────────────────────────┘
```

**Два долгоживущих процесса** (движок + UI). **Ingest-воркер** — ленивый (просыпается по
активности, умирает по простою), сам ставит себе `PROCESS_MODE_BACKGROUND_BEGIN` + EcoQoS и
**владеет записью в history.db** (принцип «один писатель на файл БД»): шторм USN при
копировании дерева парсится и коалесцируется вне процесса с голосовым контуром — GIL не
даёт джиттера аудио. Движок получает по IPC только редкие агрегированные события.
Playwright — в MCP-процессе с собственным каталогом-песочницей: downloads и профиль пишутся
только туда; перенос файла из песочницы в пользовательские папки — отдельное журналируемое
действие через гейт (дыра, которую не заметил ни один из трёх вариантов).

### 5.4. Обработка запроса (голос и текст)

Оба входа сходятся в один цикл и один `dispatch()`. Путь запроса:

1. Wake word (локально, openWakeWord «hey jarvis») → открытие/использование Live-сессии,
   либо текст из UI по WebSocket → steering-очередь.
2. Роутер: уровень 0 — прямой ответ; уровень 1 — лёгкий цикл с лимитом 2–3 хода (90%
   трафика: «открой», «найди», «переименуй»); уровень 2 — Plan-and-Execute.
3. Каждый tool call — через `dispatch()`: гейт по фактическим аргументам → хендлер (для
   мутаций: preview → подтверждение по уровню риска → saga-журнал → исполнение → undo-стек).
4. План — данные в `execution_log` (intent до, результат после); подтверждение — durable
   interrupt (WAITING_FOR_SIGNAL, хэш payload, TTL); рестарт процесса продолжает с
   последнего COMPLETE-шага; replan — только при провале шага.
5. События прогресса (`run.step_finished`, `approval.requested`…) — в шину; UI и голос —
   независимые проекции (голосу — вехи, не каждый шаг).
6. Ответ: текст в UI; голосом — через VoiceSession (в каскаде — sentence-chunked TTS +
   кэш частых фраз). Steering («стоп, не эту папку») вклинивается на границе итерации.

Бюджет отклика лёгкого пути — **≤500 мс от конца реплики до действия** (уровень Willow).
Субагенты — только read-only разведка со свежим контекстом; запись — всегда главный цикл.

### 5.5. Разрешения, подтверждения, откат

- **Пайплайн гейта** фиксирован: pre-hooks → deny (непереопределяем) → circuit-breaker-пол
  (корни дисков, %USERPROFILE%, каталог Jarvis — confirm в любом профиле) → allow /
  standing-grants → ask → профиль сессии.
- **4 уровня риска**: read → авто; обратимое → авто + журнал + тост «Перемещено 12 файлов —
  Отменить»; внешнее (письмо, пост) → ask; необратимое → блокирующее подтверждение с точным
  payload. **Авто+Undo включается только при работающем журнале+staging** (самопроверка на
  старте; иначе класс деградирует до ask). Первые недели — консервативный профиль; перевод
  классов операций в авто — по накопленной статистике безошибочности (метрики confirm-rate
  и undo-rate с первого дня).
- **Confirm-UX**: правка параметров прямо в диалоге (исправить папку назначения вместо
  отказа), changeset-превью batch-операций с чекбоксами («одобрить 18 из 20 переименований»),
  ленивое «объясни, что это сделает» по запросу; standing-grants видимы, отзываемы, с TTL.
- **Откат — три слоя**: платформенный (IFileOperation с корзиной; ReplaceFile), saga-журнал
  с компенсациями, undo-стек («отмени последнее» голосом). Честная оговорка: глубина undo
  перезаписей ограничена квотой staging-каталога.
- **Честность про «единственный путь»**: для in-process Python это CI-контракт, не физика —
  import-linter (запрет os/shutil/subprocess в tools/ и plugins/) + ruff TID251 с сообщением
  «используй ScopedRoot» + юнит-тест «хендлер недоступен вне dispatch()» как merge-гейт.

### 5.6. Хранение состояния и обновление world model

- **jarvis.db** (вечное; писатель — движок): память, world-снапшот, execution_log,
  action_journal, отложенные задачи, гранты, метрики, llm_calls, конфиг-KV.
- **history.db** (вытесняемое; писатель — ingest-воркер): журнал наблюдений с квотой диска,
  oldest-first eviction, retention по категориям. Ссылки из jarvis.db в history.db — soft
  (обязаны переживать отсутствие строки): атомарного снапшота двух WAL-файлов не существует,
  слабая связность — контракт, а не скрытое предположение.
- **Механизм обновления**: текущее состояние — материализованная проекция append-only
  журнала диффов; чтения отдают замороженные снапшоты; изменение публикует событие с old+new;
  редкая периодическая реконсиляция чинит дрейф; в RAM — только горячий срез с лимитом.
- Все состояния задач, план, pending-подтверждения — в БД, не в RAM: рестарт дёшев и
  безопасен (supervisor может перезапускать движок при деградации).
- Конфиги и экспортируемые файлы — через temp + ReplaceFile (никогда полузаписанного).

### 5.7. Независимость от AI-модели

- **registry.yaml**: роли live-voice / chat / planner / memory-extractor / classifier /
  embedder → provider:model, параметры, fallback-цепочка, требуемые capabilities;
  валидация покрытия на старте. Смена модели — одна строка.
- **Batch** абстрагирован полностью (два адаптера); **realtime** — только на уровне
  семантических событий VoiceSession + capability-флаги; непереносимое (VAD, форматы,
  lifecycle сессий) — внутри драйверов. Интерфейс валидируется вторым драйвером
  (half-cascade) ДО того, как ядро на него завяжется.
- **Local-first альтернатива на каждую облачную роль** (урок OVOS): голос → каскад
  (openWakeWord + Silero VAD + GigaAM + Silero TTS/edge-tts); chat/planner → Ollama через
  openai-адаптер; memory-extractor — локальный ПО УМОЛЧАНИЮ (личные факты не уходят в облако;
  GBNF гарантирует структуру), облако — явный opt-in.
- В облако уходит только производный текст срезов world model; сырые данные не покидают
  машину (граница Rewind).

### 5.8. Защита данных в покое (решение, а не умолчание)

Матрица угроз single-user ПК: (а) кража диска — закрывается **BitLocker/Device Encryption**
(включён по умолчанию на Windows 11) + ACL каталога данных; (б) другой пользователь ПК —
ACL; (в) чужой процесс в той же сессии — вне модели угроз ассистента (это уровень ОС).
Решение: **секреты — DPAPI/keyring; БД — BitLocker + ACL как базовый уровень**; SQLCipher
(sqlcipher3-wheels / apsw-sqlite3mc, ключ под DPAPI) — опция, если понадобится защита от
(в), с проверкой совместимости с FTS5/sqlite-vec и замером накладных. Явно НЕ обещаем
«DPAPI шифрует файл БД» — для живого WAL это не работает. Это задокументированное решение;
молчание тут было главным расхождением всех трёх вариантов.

## 6. Почему именно такая архитектура

1. **Свой цикл, а не фреймворк** — консенсус индустрии (Claude Code, Anthropic, 12-Factor)
   плюс документированные production-отказы от LangChain; для соло-проекта на 5 лет
   зависимость от мутирующей экосистемы — самостоятельный риск. Нужные паттерны (interrupt,
   fallback-роутер, checkpoint) малы и копируются в сотни строк.
2. **Гейт как конструкция, а не проверка** — дыра executor-мимо-гейта уже случилась в
   прототипе; единственный способ, чтобы она не повторилась через 3 года, — сделать второй
   путь исполнения невозможным (dispatch + ScopedRoot + CI-контракты импортов).
3. **Два процесса, два файла БД** — минимальный always-on footprint (~150–200 МБ суммарно
   против 250–400 у 4-процессного варианта B) и минимум движущихся частей при сохранении
   ВСЕХ швов долгоживучести. Судья performance-solo: «единственный вариант с явным лимитом
   объёма системы, который один человек реально удержит в голове».
4. **Everything-first для файлового индекса** — целый домен (мгновенный поиск + durable
   актуальность) закрывается зрелым чужим кодом за ~50 МБ RAM, а его служба решает
   elevation-проблему MFT/USN, которую иначе пришлось бы решать своим elevated-хелпером.
5. **SQLite как единственная технология хранения** — подтверждённая производительность
   (100k+ SELECT/с, FTS5 на миллионы строк, sqlite-vec с запасом), транзакции, бэкап двумя
   файлами, ноль эксплуатации. Векторная/графовая СУБД не оплачивает существование.
6. **Голос как драйвер, а не ось** — реальный опыт LiveKit/Pipecat доказывает, что realtime
   не абстрагируется полностью; семантические события + capability-флаги — честная граница,
   а каскад на локальных моделях (GigaAM!) — настоящая независимость.
7. **Миграция strangler с гейтом первым** — самая дорогая единица ценности (закрытие
   подтверждённой дыры) доставляется за первые 2–3 недели в ежедневно используемую систему,
   а не через полгода в новое ядро, которым никто не пользуется (фатальный дефект пути B).

## 7. План развития (миграция)

Стратегия — strangler: новое ядро растёт рядом с работающим прототипом; прототип в
фичефризе с этапа 0; каждый этап заканчивается работающей системой с критерием готовности
«старый путь УДАЛЁН, не выключен» (лимит двойных механизмов — 2 недели). Один
`git checkout` в любой момент возвращает рабочую систему.

| Этап | Содержание | Критерий готовности |
|---|---|---|
| **0. Страховочная сетка + конфиг** (1–2 нед.) | Golden-сценарии: 20–30 типовых запросов (включая голосовые interruption/steering-кейсы) как смоук-гейт мержа; единый config + registry.yaml; вынос live-ключа; uv.lock; удаление мёртвых ~30% actions/ и сироты searxng | grep не находит имён моделей и чтения ключа вне config/; смоук зелёный |
| **1. Гейт** (2–3 нед.) | Тонкий `dispatch()` ПОВЕРХ существующей policy-таблицы; все вызовы из main.py И agent/executor — через него; сырой `command` в cmd_control упраздняется; circuit-breaker-пол; лог каждого вызова с вердиктом | В логе 100% tool-вызовов с вердиктом гейта; тест «агентный путь получает confirm»; grep: нет вызовов хендлеров вне dispatch() |
| **2. Store + шина + журнал** (3–4 нед.) | SQLite-схемы (jarvis.db/history.db, миграции user_version); EventBus + каталог событий + EVENTS.md + консоль-подписчик; saga-журнал + staging + undo-стек; fileops на IFileOperation (STA-поток)/ReplaceFile/ScopedRoot | «Отмени последнее» голосом для move/rename; crash-тест «kill посреди batch → докат/откат»; нет os.remove/shutil.move для пользовательских файлов |
| **3. Durable-подтверждения + память v2** (3–4 нед.) | Confirm как interrupt (хэш-пиннинг, TTL); 4-уровневая шкала; миграция JSON→SQLite (FTS5+sqlite-vec, слоистая схема, би-темпоральные факты); эмбеддер-воркер; sleep-time консолидация | Подтверждение переживает рестарт; поиск по памяти <50 мс; JSON-путь удалён |
| **4. Новый цикл** (4–6 нед., самый рискованный) | Роутер + лёгкий цикл + Plan-and-Execute на execution_log; planner/executor/task_queue/error_handler удаляются; за feature-флагом: сначала только текстовые запросы, голос — последним; журнал расхождений старого/нового пути 2 недели | main.py < 300 строк; golden зелёные; рестарт посреди плана продолжает выполнение |
| **5. LLM-слой + голос за интерфейсом** (3–4 нед.) | Batch-адаптеры (google-genai, openai-compat), удаление старого SDK; существующий Live-код оборачивается в драйвер VoiceSession; tool-calls из live — в dispatch(); сразу после — минимальный half-cascade (GigaAM + Silero TTS) КАК ТЕСТ контракта | Текстовый путь работает на Ollama сменой строки registry.yaml; один SDK Gemini в requirements; каскад проходит FakeVoiceSession-тесты |
| **6. Отделение UI** (2–3 нед.) | WebSocket-каталог сообщений; tkinter — клиент (модуль-мост WS→mainloop); движок headless | kill UI не прерывает задачу; движок работает без UI |
| **7. World model v2** (4–6 нед.) | Ingest-воркер (Everything-first; USN — резерв; watchdog — горячие папки), SetWinEventHook, heartbeat-журнал в history.db, world_gateway, квоты/retention/индикатор | Изменения при выключенном Jarvis видны после старта; idle-бюджет выдержан неделю по метрикам; perf-тест в CI |
| **8. Плагины + финальная чистка** (3–4 нед.) | Манифесты + pluggy для всех тулов, ленивая активация, скаффолд-генератор; Playwright → MCP с песочницей; lifecycle-состояния; генерация ARCHITECTURE.md из манифестов | Новый тул = один каталог с манифестом; крах браузера не трогает движок; ≤12k строк |

Итого ~6–8 месяцев соло-темпом. Жёсткий порядок: 0→1→2 (безопасность данных — раньше
всего); 3–4 — ядро ценности; 5–8 допускают перестановку. Точки невозврата нет до этапа 4.

## 8. Риски

| Риск | Митигация |
|---|---|
| Win32-специфика (USN, WinEvents, IFileOperation/COM) дороже в отладке, чем ожидается | Весь Win32 — в двух тонких модулях с чистыми интерфейсами; на каждый — фолбэк попроще (watchdog, send2trash) за тем же интерфейсом; Everything как готовый обход самой сложной части; COM — в STA-потоке с таймаутом |
| In-process плагин роняет движок (осознанная жертва) | Per-listener try/except + счётчик + авто-отключение; Component-очистка; таймауты хендлеров; supervisor с авто-рестартом (состояние в SQLite → рестарт дёшев); рецидивист выносится в MCP |
| VoiceSession протечёт: второй драйвер не ляжет на интерфейс | Capability-флаги с первого дня; half-cascade пишется сразу после этапа 5 КАК ТЕСТ контракта, до того как ядро завяжется на интерфейс |
| Confirm-усталость или, наоборот, агрессивное «авто с Undo» | Reversible→авто только при работающем журнале (проверка на старте); неотключаемый пол; метрики confirm/undo-rate; консервативный профиль первых недель |
| Миграция затянется, strangler станет вечным гибридом (сценарий Siri) | Фичефриз прототипа с этапа 0; этапы 0–2 короткие с видимой ценностью; критерий «старый путь удалён»; календарная ревизия раз в месяц; golden-сценарии как merge-гейт |
| Шквалы awareness-событий душат латентность голоса | Ingest — в отдельном воркере (background+EcoQoS), владеющем history.db; батч-коммиты; bounded-очереди; метрика глубины очередей как health-сигнал |
| Динамический скоуп тулов → галлюцинации несуществующих | Базовый набор всегда в промпте; маскирование вместо удаления (стабильность KV-кэша); метрика «вызов замаскированного тула»; откат к статичному набору |
| Внешние зависимости умрут (Gemini Live, Everything, sqlite-vec) | Каждая — за адаптером с local-first альтернативой (каскад; свой USN-ридер; FTS5-only); данные в открытых форматах — их срок жизни не привязан к зависимостям |
| Соло-фактор: выгорание на полугодовой миграции | Каждый этап атомарно полезен и завершается тегом с работающей системой; ARCHITECTURE.md и EVENTS.md генерируются из кода (возвращение после паузы дёшево) |

## 9. Компромиссы (осознанные жертвы)

- **Нет краш-изоляции in-process плагинов** — цена двух процессов вместо N; компенсируется
  Component-очисткой, авто-отключением, выносом рецидивистов в MCP.
- **Нет DAG-параллелизма планов** — шаги десктоп-сценариев конфликтуют по окнам/файлам,
  потеря мала; подстановку `$1` берём, параллелизм нет.
- **Нет полного event sourcing** — только action_journal и диффы world model; replay всей
  системы не нужен single-user приложению.
- **Нет скриншотной истории в v1** — «что было на экране час назад» система не ответит;
  это отдельный тяжёлый домен (уроки screenpipe), отложен осознанно.
- **Компенсация вместо идеального отката** — возвращает объект, а не мир в точности;
  глубина undo перезаписей ограничена квотой staging.
- **Vendor-код Gemini остаётся в драйвере** до появления каскада — плата за лучшую сегодня
  голосовую модель; изолирован интерфейсом.
- **Каждое новое действие обязано оформляться манифестом** — «быстрые хаки» запрещены
  конструкцией; выкупается скаффолд-генератором (тул из шаблона одной командой).

## 10. Рекомендации по производительности

- **Бюджеты — тестируемые артефакты**: движок idle ≤150 МБ RSS, <1% CPU, ноль пробуждений
  чаще 1/мин; perf-смоук в CI (psutil: поднять ядро, подождать, ассертить RSS и счётчик
  пробуждений) — иначе бюджет дрейфует. Отклик лёгкого пути ≤500 мс.
- **Ленивые импорты** тяжёлых библиотек внутри хендлеров (`-X importtime` для профилирования;
  Python 3.15 — `lazy import`). Неиспользованный за день тул не должен стоить ни байта.
- **Событийность вместо поллинга**: `await event.wait()`/`queue.get()`, TaskGroup; редкая
  периодика с грубыми допусками. USN/WinEvents/last-input вместо любых опросов.
- **Фоновое — на фоновом приоритете**: воркеры сами ставят PROCESS_MODE_BACKGROUND_BEGIN +
  EcoQoS; эмбеддер перезапускается по порогу RSS (лечит и утечки fastembed, и фрагментацию).
- **Debounce/coalescing** файловых событий (тихое окно 100 мс + жёсткий потолок + дедуп по
  пути); батч-коммиты записи событий раз в ~5 с (паттерн HA Recorder).
- **Между процессами — ID строк SQLite, не блобы**; тяжёлые данные — в ФС, в БД ссылки.
- **Никаких неограниченных кэшей**: у всего лимит и вытеснение; горячий срез world model
  в RAM — с капом записей.
- **Токены — тоже производительность**: динамический скоуп схем (порог деградации 10–15
  тулов), компактация по порогу, кэш TTS-фраз, дневной бюджет стоимости до вызова.

## 11. Рекомендации по качеству архитектуры

- **Пирамида тестов** (снизу вверх, 90% без LLM): (0) import-linter + ruff TID251 + юнит
  гейта/реестра — каждый коммит; (1) hypothesis property/stateful для ScopedRoot и
  saga/undo; (2) crash-injection матрица (CRASH_AT=after_intent|mid_copy|before_complete);
  (3) golden-сценарии со ScriptedModel (полный контур, песочница, ассерты конечного
  состояния + решений гейта) — merge-гейт, 100% pass; (4) те же сценарии живой моделью,
  pass^3 для data-safety — ночью/при смене модели; (5) perf-смоук. FakeVoiceSession
  проигрывает событийные трейсы для interruption/steering-тестов.
- **Наблюдаемость своими руками**: таблицы events + llm_calls (content-addressed replay-кэш),
  turn_id через contextvars, flight-recorder, Datasette по требованию; метрики — SQL-view;
  двухуровневая ретенция (содержимое промптов — 7–14 дней, скаляры — навсегда).
- **Анти-дрейф генерацией**: capability truth, tool-declarations, правила гейта, EVENTS.md,
  ARCHITECTURE.md — всё из реестров, ничего рукописного в двух местах (главный выученный
  урок прототипа: три рукописные копии знаний об инструментах разъехались).
- **Эволюция контрактов**: одно целое api_version; только аддитивные изменения (новые поля
  optional); ломающее изменение = новый тип с upcaster'ом; fixture-replay исторических
  событий в CI.
- **Жизненный цикл**: uv.lock + пин Python; Task Scheduler «At log on» + именованный мьютекс
  + обработка WM_ENDSESSION; releases/<tag>-слоты с junction-указателем; транзакция
  обновления «снапшот → миграция → golden-смоук → commit/rollback»; refuse-to-start при
  user_version новее кода; еженедельный restore-тест бэкапов.

## 12. Рекомендации по защите данных пользователя

(Как качество архитектуры и UX — предотвращение случайных повреждений и уважение к
чувствительности данных.)

1. **Один гейт, ноль исключений**: все пути исполнения через dispatch(); политика в коде,
   промпт информирует; поведенческие авторитеты (сколько спрашивать) — только явная
   настройка пользователя, никогда LLM-выведенный профиль (урок personality_engine).
2. **Мутирующие обёртки принимают ScopedRoot, не строки**; конструирует его только гейт.
3. **Preview обязателен** для мутаций; batch — changeset с чекбоксами; подтверждение — по
   точному payload с хэш-пиннингом, не по пересказу.
4. **Журнал всего**: intent до исполнения (аудит «что ассистент собирался сделать»),
   completion после; «что ассистент делал вчера с моими файлами» — SQL-запрос, а не
   археология stdout.
5. **Откат тремя слоями** + корзина Windows как привычный пользователю независимый путь.
6. **История активности — самые чувствительные данные**: только производные, только через
   world_gateway, квоты и retention с первого дня, индикатор наблюдения, opt-in по
   категориям, команда «забудь X», лёгкое удаление по диапазону дат.
7. **Локальность по умолчанию**: экстракция личных фактов — локальной моделью; в облако —
   только производный текст релевантных срезов; полные промпты в логах — отдельная таблица
   с короткой ретенцией и выключателем.
8. **Память видима и редактируема**: пользователь может посмотреть и исправить любой факт
   о себе; ложный вывод системы не должен быть неисправимым.
9. **Недоверенный текст фенсится** перед инъекцией в промпт (имена файлов, заголовки окон,
   память) — паттерн `_sanitize` прототипа становится стандартом всех секций.
10. **Секреты — DPAPI/keyring; БД — BitLocker + ACL** (задокументированное решение, §5.8);
    бэкапы — только backup API/VACUUM INTO + restore-тест.

## 13. Идеи для будущего масштабирования

- **Скриншотная история (v2+)**: событийный захват по смене окна + accessibility-текст
  прежде OCR (паттерн screenpipe), строго в изолированном процессе с квотами; включается
  только когда v1 стабильна.
- **Процедурная память → автоматизации**: сохранённые многошаговые сценарии («каждый вечер
  разбирай Downloads») как данные в реестре с теми же гейтами; триггеры от шины событий.
- **Второй realtime-драйвер** (OpenAI Realtime / будущие модели) в слот VoiceSession;
  проактивное аудио.
- **Больше MCP**: сторонние серверы (почта, календарь, мессенджеры) подключаются адаптером
  через тот же гейт с риск-метаданными — рост возможностей без роста ядра.
- **Tauri/веб-UI** вместо tkinter — замена клиента без правки движка (WebSocket-каталог);
  мобильный клиент к тому же каталогу.
- **Вынос ingest в постоянный процесс** — шов заложен (клиент шины со своим файлом БД);
  триггер — метрика глубины очередей, прогнать вынос в тесте заранее.
- **PyO3/Rust** для профилированного горячего цикла (например, диффы world model на сотнях
  тысяч объектов) — задокументированный запасной выход, не план.
- **Мульти-машинность** (ноутбук + десктоп): синхронизация памяти через экспорт в markdown +
  git, а не через сетевую БД — сначала как ручной процесс.
