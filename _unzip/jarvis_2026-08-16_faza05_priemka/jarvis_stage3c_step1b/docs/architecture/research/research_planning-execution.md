Изучены первоисточники по четырём пластам темы: паттерны цикла исполнения (ReAct, Plan-and-Execute, ReWOO, LLMCompiler), durable execution (архитектурные доки Temporal, библиотека DBOS, PoC Гуннара Морлинга «Persistasaurus» на SQLite), пауза/подтверждение (LangGraph interrupt + checkpointer, plan mode и permission-система Claude Code), и операционика: таксономии восстановления после ошибок шага (GRACE, SHIELDA, MAST, PRISM), роутинг по сложности (RouteLLM, паттерн routing у Anthropic), бюджеты (max_turns=10 в OpenAI Agents SDK, recursion_limit=25 в LangGraph, max_budget_usd в Claude Agent SDK), прогресс-события (протокол AG-UI, LangChain agent streams) и посмертный разбор AutoGPT/BabyAGI плюс инженерные уроки Manus.

Главный вывод по циклу исполнения: для ассистента, где 90% запросов — один-два вызова инструментов, оптимальна трёхуровневая схема с роутером на входе. Уровень 0 — прямой ответ без инструментов; уровень 1 — «лёгкий ReAct»: обычный function-calling цикл с жёстким лимитом 2-3 хода; уровень 2 — Plan-and-Execute для многошаговых сценариев. Это подтверждено сразу несколькими источниками: Anthropic в «Building effective agents» описывает routing как базовый паттерн (дешёвая модель/правила классифицируют запрос, сложные идут в дорогой контур), а практика RouteLLM показывает, что 70-85% продакшн-трафика — «лёгкие» запросы. Важные предостережения из практики роутинга: классификатор обязан быть радикально дешевле того, что он экономит (иначе «машина Голдберга для потери денег»), и нужен мониторинг доли эскалаций — известен случай, когда роутер молча начал отправлять 90% трафика в дорогую модель. Для single-user десктопа достаточно правил + вызова той же модели с быстрым структурным выводом; отдельный обученный классификатор — оверинжиниринг при сотнях запросов в день.

Для многошагового уровня LangChain-блог о planning agents фиксирует эволюцию: базовый Plan-and-Execute (планировщик генерирует список шагов, исполнитель выполняет, replanner после каждого шага решает — продолжать/перепланировать/финализировать), ReWOO добавляет переменные (#E2 — выход шага 2 подставляется в аргументы шага 3 без LLM-вызова), LLMCompiler (ICML 2024) превращает план в DAG с зависимостями $1/$2 и Task Fetching Unit исполняет независимые ветки параллельно (заявлено 3.6x ускорение). Для десктоп-ассистента полный DAG-параллелизм — редко нужная оптимизация (шаги обычно трогают одни и те же окна/файлы), но формат плана как списка шагов с явными зависимостями и подстановкой результатов стоит взять: он даёт preview, гейтинг и журналирование бесплатно, потому что план — это данные, а не рассуждения в контексте.

По durable execution: Temporal строится на event sourcing + детерминированном replay кода воркфлоу — это требует детерминизма пользовательского кода и тяжело для десктопа. Миниатюрная альтернатива — журнал шагов в SQLite: DBOS (по умолчанию SQLite, ноль инфраструктуры, процесс и воркфлоу в одном процессе) чекпойнтит вход воркфлоу и выход каждого шага в БД, при рестарте продолжает с последнего завершённого шага; Persistasaurus (~1000 строк) показывает минимальную схему: одна таблица execution_log с (flow_id, step, status PENDING/WAITING_FOR_SIGNAL/COMPLETE, attempts, parameters, return_value), причём намерение пишется ДО исполнения, результат — ПОСЛЕ, как WAL. Ключевое упрощение для проекта: поскольку план LLM-агента и так является данными (список шагов), не нужен replay кода вообще — достаточно интерпретатора плана, читающего строки таблицы: «шаги 1-3 COMPLETE, продолжаем с 4». Известная дыра — краш между исполнением шага и записью результата ⇒ повторное исполнение; лечится идемпотентностью побочных эффектов (например, «переместить файл X→Y» проверяет, не перемещён ли уже) — это прямо стыкуется с журналом отката из требований проекта.

По гейту разрешений — самое важное для закрытия дыры agent/executor. Архитектура permission-системы Claude Code: hooks исполняются ПЕРВЫМИ на каждом вызове инструмента и deny хука действует даже в bypassPermissions; т.е. гейт живёт в диспетчере вызова инструмента, а не в мозгах агента. Показателен разбор plan mode: энфорсмент оказался строкой в системном промпте, а не веткой в permission-резолвере — сообщество прямо называет это «prompt engineering, not hard enforcement». Вывод: единственная правильная точка гейта — исполнитель шага (та самая функция, через которую проходят И прямые вызовы, И шаги плана), проверка по policy-таблице делается в момент исполнения с фактическими аргументами (аргументы шага могут вычисляться из результатов предыдущих — гейтить план по «обещанным» аргументам недостаточно). Подтверждение confirm-шага — это LangGraph-паттерн interrupt: исполнение приостанавливается, состояние персистится через checkpointer, resume подаёт ответ пользователя; замороженная задача не ест ресурсов и переживает рестарт. Отсюда же правило прерывать только на необратимых операциях, не на каждом шаге, и TTL для брошенных подтверждений.

По ошибкам шага: GRACE даёт рабочий набор стратегий восстановления — Retry, Skip, Replan, Substitute_Tool, Regenerate_Prior_Step, Escalate (к человеку), выбираемых LLM-анализом контекста провала. Инженерные правила: не ретраить ошибки валидации/прав (ретрай не чинит конфигурацию), неидемпотентные операции ретраить только убедившись, что первая попытка не прошла; при провале LLM-вывода не повторять тот же промпт, а переформулировать. MAST (NeurIPS 2025, 1600+ трейсов) показывает, что 79% провалов — неоднозначность спецификации и разрывы координации, а >50% ошибок происходят на границе с внешней средой — то есть вложения окупаются в качестве инструментов и наблюдений, а не в изощрённости планировщика. Manus добавляет контринтуитивное: ошибки НУЖНО оставлять в контексте (модель учится «что не делать»), а не вычищать.

По бюджетам: индустриальные дефолты — max_turns=10 (OpenAI Agents SDK, исключение MaxTurnsExceeded), recursion_limit=25 (LangGraph), max_budget_usd (Claude Agent SDK); совет — обрывать ДО следующего платного вызова, не после. История BabyAGI ($80 за ночь без max_iterations) — аргумент, что лимиты шагов, перепланирований, wall-clock таймауты шага и дневной потолок стоимости должны быть в ядре, а не опцией. Плюс детектор зацикливания: повторный вызов инструмента с идентичными аргументами — сигнал стагнации.

По preview и прогрессу: Claude Code plan mode — эталон двухфазности «исследуй в read-only → покажи план → исполняй после одобрения»; это разделяет два разных отказа: «агент не понял задачу» и «агент неправильно исполняет». Протокол AG-UI даёт словарь типизированных событий (RUN_STARTED, STEP_STARTED, STEP_FINISHED, RUN_ERROR), которые UI превращает в чеклист плана: выполненные шаги с галочкой, активный пульсирует, будущие редактируемы; LangChain agent streams добавляет идею нескольких независимых проекций одного лога событий (чат, панель активности, прогресс-бар). Это идеально ложится на планируемую шину событий проекта: исполнитель публикует события, UI и голос подписываются. Для голоса — краткие вехи, не каждый шаг. Синтез с policy-таблицей (моя рекомендация, не найдена в источниках в готовом виде): в preview каждый шаг аннотируется риском из той же таблицы (auto/confirm/blocked), одобрение плана предавторизует confirm-шаги с конкретными аргументами, но шаги, чьи аргументы вычислятся в рантайме, всё равно проходят гейт заново.

Итоговая рекомендация для проекта: роутер (правила + быстрая модель) → лёгкий цикл для 90% → Plan-and-Execute с replan-узлом для 10%; план — строки в SQLite (intent-log до, результат после), исполнитель шага — единственная точка вызова инструментов и гейта; подтверждение — interrupt с персистом; бюджеты и детектор циклов в ядре; типизированные события прогресса в шину. Всё это реализуемо на asyncio + SQLite без внешних движков и сопровождается одним человеком.

## Идеи

- **Трёхуровневый роутер: ответ / лёгкий цикл / планировщик** [Anthropic «Building effective agents» (routing), RouteLLM (LMSYS), NVIDIA LLM Router]: Дешёвый классификатор (правила или маленькая модель) делит запросы на: прямой ответ, один-два вызова инструментов (обычный function-calling цикл с лимитом ходов), многошаговый план. Только последний класс попадает в дорогой контур планирования. | Почему: 70-85% продакшн-трафика — простые запросы; роутер убирает латентность и стоимость полного планирования там, где оно не нужно. Подтверждено и Anthropic (routing как базовый паттерн), и цифрами RouteLLM (85% экономии при 95% качества). | Применимость: high — прямой ответ на вопрос «какой цикл оптимален при 90/10». Реализуется правилами + structured output той же Gemini/любой модели; отдельный обученный классификатор не нужен при single-user нагрузке.
- **Plan-and-Execute с replan-узлом** [LangChain blog «Plan-and-Execute Agents», Plan-and-Solve prompting]: Планировщик генерирует полный список шагов; исполнитель выполняет шаг за шагом; после каждого шага (или провала) лёгкий replanner решает: продолжить, перепланировать остаток, финализировать. План — структура данных, а не рассуждение в контексте. | Почему: Полный план заранее = preview для пользователя, per-step гейтинг, журналирование и меньше LLM-вызовов, чем в ReAct; replan-узел снимает главный минус — ригидность при провале первого плана. | Применимость: high — это ядро «тяжёлого» пути. Шаги хранить как строки в SQLite, replanner вызывать только при провале или существенном расхождении наблюдений с ожиданиями.
- **Переменные в плане ($1/#E2) и явные зависимости шагов** [ReWOO, LLMCompiler (arXiv 2312.04511, ICML 2024)]: Шаг плана ссылается на выход предыдущего через плейсхолдер ($1, #E2); подстановка делается кодом без LLM-вызова. LLMCompiler расширяет до DAG и исполняет независимые шаги параллельно (3.6x ускорение). | Почему: Убирает LLM-вызов между шагами (скорость, стоимость) и делает зависимости данными — их видно в preview и журнале. Полный DAG-параллелизм опционален. | Применимость: medium — подстановку переменных брать обязательно; параллелизм DAG отложить: шаги десктоп-сценариев обычно конфликтуют по ресурсам (окна, файлы), а выгода мала.
- **Журнал шагов в SQLite: намерение до, результат после** [Persistasaurus (morling.dev), DBOS (dbos-transact-py)]: Таблица execution_log(flow_id, step, status: PENDING/WAITING_FOR_SIGNAL/COMPLETE, attempts, parameters, return_value). Намерение шага пишется ДО исполнения, результат — ПОСЛЕ (как WAL). При рестарте интерпретатор плана пропускает COMPLETE-шаги и продолжает со следующего. | Почему: Durable execution без Temporal-инфраструктуры и без требования детерминизма кода: так как план LLM-агента — уже данные, достаточно интерпретатора, а не replay. DBOS доказывает, что SQLite-варианта хватает для single-process. Intent-до-исполнения — одновременно и журнал аудита «что ассистент собирался сделать». | Применимость: high — «переживание рестарта посреди задачи» за ~сотни строк кода; та же таблица кормит UI прогресса и журнал операций для отката.
- **Подтверждение как durable-пауза (interrupt/resume)** [LangGraph interrupts (docs.langchain.com), Persistasaurus WAITING_FOR_SIGNAL]: Confirm-шаг не блокирует процесс модальным диалогом: исполнение приостанавливается, состояние персистится (status=WAITING_FOR_SIGNAL), пользователю уходит запрос; resume подаёт ответ и продолжает с того же шага. Замороженная задача не ест ресурсов и переживает рестарт. | Почему: Развязывает движок и UI (голос может подтвердить позже), выдерживает перезапуск между вопросом и ответом. LangGraph-правила: прерывать только необратимые операции, TTL для брошенных подтверждений. | Применимость: high — механизм подтверждений policy-таблицы для агентного пути; статус в той же execution_log, никакого отдельного стейт-менеджмента.
- **Гейт в диспетчере инструмента, hooks-first** [Claude Code permissions docs, Anthropic «claude-code-auto-mode»]: Проверка разрешений живёт в единственной функции-диспетчере, через которую проходят ВСЕ вызовы инструментов (прямые из чата и шаги плана), и выполняется первой на каждом вызове с фактическими аргументами; deny непереопределяем никаким режимом. | Почему: Закрывает дыру «executor в обход гейта» структурно: у планировщика физически нет другого пути к инструментам. Гейтить по фактическим аргументам обязательно — аргументы шага часто вычисляются из результатов предыдущих шагов и в момент планирования неизвестны. | Применимость: high — прямой ответ на вопрос «как план всегда проходит через единый гейт»: та же policy-таблица core/security.py, вызываемая внутри step-executor, а не в планировщике.
- **Preview плана с risk-аннотацией из policy-таблицы** [Claude Code plan mode + синтез с policy-таблицей проекта (экспертная оценка)]: Перед исполнением план показывается как чеклист, где каждый шаг аннотирован классом риска из policy-таблицы (auto/confirm/blocked). Одобрение плана предавторизует confirm-шаги с конкретными аргументами; шаги, чьи аргументы вычислятся в рантайме, проходят гейт повторно при исполнении. | Почему: Двухфазность «понял ли агент задачу» / «правильно ли исполняет» — разные отказы, разные чекпойнты (урок plan mode). Одно подтверждение на план вместо пяти диалогов — лучший UX без ослабления гейта. | Применимость: high — продолжение удачного паттерна «capability truth»: та же таблица генерирует и промпт, и аннотации preview.
- **Таксономия восстановления шага: retry/skip/replan/substitute/escalate** [GRACE (arXiv 2602.15039), SHIELDA (arXiv 2508.07935), Fastio retry patterns]: На провале шага выбирается одна из стратегий: Retry (транзиент), Substitute_Tool (другой провайдер/инструмент), Skip (некритичный шаг), Replan (остаток плана с контекстом провала), Escalate (спросить пользователя), Abort. Правила: не ретраить ошибки валидации/прав; неидемпотентные операции ретраить только убедившись, что первая попытка не прошла; LLM-ошибки ретраить с изменённым промптом. | Почему: Явное меню стратегий вместо ad-hoc try/except; выбор можно делать дёшево: сначала детерминированные правила по классу ошибки, LLM-решатель — только когда правила молчат. | Применимость: high — класс ошибки уже известен инструментам (сеть/права/не найдено); маппинг класс→стратегия задаётся декларативно рядом с policy-таблицей.
- **Бюджеты в ядре: шаги, replan'ы, таймауты, стоимость** [OpenAI Agents SDK (max_turns=10), LangGraph (recursion_limit=25), Claude Agent SDK (max_budget_usd)]: Жёсткие лимиты на число ходов лёгкого цикла (2-3), шагов плана, перепланирований (1-2), wall-clock таймаут шага и дневной потолок стоимости; проверка ДО следующего платного вызова. Плюс детектор стагнации: повторный вызов инструмента с идентичными аргументами. | Почему: Все зрелые SDK сошлись на консервативных дефолтах после эпохи AutoGPT; детектор одинаковых вызовов ловит зацикливание раньше, чем лимит шагов. | Применимость: high — у проекта уже есть circuit breakers и квоты модели; бюджеты агентного контура — то же семейство механизмов, единый модуль.
- **Типизированные события прогресса через шину** [AG-UI protocol, LangChain «From Token Streams to Agent Streams»]: Исполнитель публикует типизированные события (RUN_STARTED, STEP_STARTED, STEP_FINISHED, STEP_FAILED, APPROVAL_REQUESTED, RUN_FINISHED); UI, голос и журнал — независимые подписчики-проекции одного потока. UI рендерит план-чеклист: выполненные с галочкой, активный пульсирует. | Почему: Решает «молчаливый спиннер» и идеально совпадает с планируемой шиной событий: движок не знает про UI. Несколько проекций (чат/панель активности/голосовые вехи) без конкуренции за один поток. | Применимость: high — задаёт первый согласованный словарь событий новой шины; голосу отдавать только вехи, не каждый шаг (принцип attention budgeting).
- **Ошибки остаются в контексте; recitation плана** [Manus «Context Engineering for AI Agents» (manus.im)]: Провалившиеся действия и их ошибки не вычищаются из контекста — модель адаптируется, видя «что не сработало». Для длинных задач план/todo переписывается в конец контекста (recitation), удерживая цель в зоне внимания. | Почему: Проверено на продакшн-агенте с ~50 вызовами инструментов на задачу; recitation борется с «lost in the middle» и дрейфом цели без изменения архитектуры. | Применимость: medium — recitation нужен только длинным планам (уровень 2); «ошибки в контексте» — правило для replanner'а: передавать ему полную историю провала, а не очищенное состояние.
- **Идемпотентность побочных эффектов шага** [Persistasaurus (известная дыра re-execution), Temporal best practices, Fastio]: Каждый мутационный шаг (переместить/переименовать/удалить в корзину) проектируется идемпотентным: перед действием проверяет, не выполнено ли уже (файл уже в целевой папке), либо несёт idempotency-ключ в журнале. | Почему: Закрывает единственную дыру журнальной схемы (краш между исполнением и записью результата) и делает retry безопасным по построению — краеугольный камень «невозможности случайного повреждения данных». | Применимость: high — оформить как контракт инструмента: мутационные тулы обязаны реализовать check-before-act; сочетается с журналом отката.

## Анти-паттерны

- **Автономная само-пополняющаяся очередь задач** [AutoGPT / BabyAGI (разборы Tom's Hardware, Lilian Weng, ретроспектива LangChain)]: Агент, сам генерирующий себе новые задачи в цикле без внешнего критерия завершения, зацикливается и жжёт бюджет: документированные бесконечные петли AutoGPT, $80 за ночь у BabyAGI без max_iterations, компаундинг ошибок (95% на шаг = ~60% на 10 шагах). Индустрия сошлась на обратном: узкие контролируемые агенты, план от конкретного запроса пользователя, жёсткие стоп-условия.
- **Энфорсмент режимов только в промпте** [Разбор Claude Code plan mode (dev.to «prompt engineering, not hard enforcement»)]: Если «read-only режим» или «требуется подтверждение» — лишь строка в системном промпте, а диспетчер инструментов исполняет вызовы одинаково во всех режимах, то гарантия исчезает при любом дрейфе модели. Это ровно текущая дыра executor'а в MARK XXXV: правило должно быть веткой в коде диспетчера, промпт — лишь информирование модели (паттерн capability truth).
- **Гейт разрешений на этапе планирования вместо исполнения** [Синтез: Claude Code hooks-first + PRISM (Rule Violation как топ-класс провалов); экспертная оценка]: Проверка плана «на бумаге» не гейтит фактические аргументы: они вычисляются в рантайме из результатов предыдущих шагов, а LLM-исполнитель может отклониться от одобренного плана (PRISM: Tool Call Skip, Step Reordering — типовые продакшн-регрессии). Проверять нужно каждый фактический вызов в момент исполнения.
- **Durable execution через детерминированный replay кода (Temporal-в-миниатюре «по-честному»)** [Temporal architecture docs vs DBOS/Persistasaurus; экспертная оценка]: Replay требует детерминизма пользовательского кода, версионирования воркфлоу и дисциплины на годы — тяжёлая ноша для соло-мейнтейнера. Для LLM-агента план уже является данными, поэтому replay избыточен: интерпретатор строк журнала даёт ту же устойчивость на порядок дешевле. Гуннар Морлинг прямо перечисляет, чего не хватает его 1000-строчному PoC до продакшна — этот список и есть цена «честного» пути.
- **Роутер дороже экономии и молчаливая эскалация** [Burnwise/TrueFoundry разборы LLM-роутинга]: Обученный классификатор-роутер при малом трафике (<500 вызовов/день) стоит дороже в сопровождении, чем экономит; известен случай, когда изменение формата вывода дешёвой модели заставило роутер молча эскалировать 90% трафика в дорогую — без единой ошибки в логах. Для десктопа: правила + быстрый вызов основной модели, плюс метрика доли эскалаций.
- **Полный цикл планирования для каждого запроса** [LangChain planning-agents (ReAct per-step затраты), практика RouteLLM]: Прогонять «открой блокнот» через planner→plan→executor→replanner — это секунды латентности и кратный расход токенов на 90% трафика. ReAct-петля с явными «мыслями» на каждый шаг страдает тем же в меньшем масштабе. Голосовой ассистент чувствителен к отклику как ничто другое: простые запросы должны идти по пути «одна модель — один tool call».
- **Динамическое добавление/удаление инструментов посреди задачи** [Manus «Context Engineering for AI Agents»]: Смена набора тулов инвалидирует KV-кэш (тулы сериализуются в начале контекста) и провоцирует schema violations, когда модель ссылается на исчезнувший инструмент. Manus вместо удаления маскирует недоступные действия при неизменных определениях. Для проекта: policy-состояния blocked/confirm не должны менять список тулов в промпте — только помечать доступность.
- **Лимиты шагов и стоимости как опция, а не свойство ядра** [BabyAGI ($80 overnight), OpenAI Agents SDK issue #551 (вложенный агент игнорирует max_turns)]: Опциональные лимиты забывают включить, а вложенные контуры (replanner, sub-задачи) наследуют дефолты в обход настроек — это класс багов даже в зрелых SDK. Бюджет должен быть параметром конструктора контура исполнения без значения «безлимитно», с проверкой до платного вызова.
- **Крупные объекты в чекпойнтах состояния** [DBOS docs (совет держать входы/выходы < ~2 MB), Manus (файловая система как память)]: Складывание содержимого веб-страниц/документов в журнал шагов раздувает SQLite и замедляет каждое чтение состояния. Правильно: в журнале — ссылки (путь к файлу, ID наблюдения), тяжёлые данные — в файловой системе; Manus так и использует ФС как внешнюю память агента.
