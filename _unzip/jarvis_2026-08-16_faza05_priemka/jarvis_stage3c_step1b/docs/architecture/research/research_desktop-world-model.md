Я изучил пять реально работающих систем наблюдения за рабочим окружением (ActivityWatch, screenpipe, Windows Recall, Rewind.ai, Everything) плюс первоисточники по Windows-механизмам (USN Change Journal, WinEvents, UI Automation) и практику python-watchdog. Общий вывод: все зрелые системы сходятся к одной и той же схеме — «bootstrap-снапшот + инкрементальный поток событий + компактирование при записи + жёсткий бюджет хранения», а различия в том, насколько дёшево они получают события от ОС.

Эталон минимальной нагрузки — Everything от voidtools. Первичный индекс он строит не сканированием дерева, а чтением всей NTFS MFT разом: ~250 тыс. файлов индексируются за ~5 секунд, 1 млн — за ~1 минуту; индекс имён занимает ~35–100 МБ RAM и 14–45 МБ на диске (данные FAQ voidtools, подтверждено первоисточником). Дальше он вообще не трогает MFT — только читает USN Change Journal, который ведёт сам драйвер NTFS независимо от приложения. Отсюда ключевое свойство: изменения не теряются, пока приложение не запущено — при старте оно «догоняет» журнал; при переполнении журнала (обычно ~32 МБ, пара дней изменений) — честный fallback на полную переиндексацию из MFT. Документация Microsoft по Change Journals прямо называет полное сканирование неприемлемым, а directory notifications — требующими постоянно работающего приложения и дорогими на больших деревьях; журнал спроектирован именно для indexing-сервисов. Это прямой приговор нынешнему подходу MARK XXXV (watchdog поверх ReadDirectoryChangesW): у watchdog документированы конвертация rename→move, удаление каталога, отражаемое как удаление файла, неполные сканы перемещённых каталогов, и главное — отсутствие durability между перезапусками. Практический вывод: файловый индекс либо строить самому на MFT+USN, либо (быстрее и надёжнее) делегировать Everything как локальному сервису — у него официальный IPC (WM_COPYDATA, в 1.5 — именованный канал \\.\PIPE\Everything IPC), SDK и ES.exe; тогда весь домен «мгновенный поиск файлов + актуальность индекса» закрывается чужим отлаженным кодом за ~50 МБ RAM.

ActivityWatch даёт лучшую модель процессной архитектуры и компактного хранения активности. Схема: независимые процессы-watcher'ы → REST API локального сервера → «bucket на watcher» → SQLite. Отказоустойчивость встроена в топологию: упавший watcher просто перестаёт писать в свой bucket, клиентская библиотека буферизует heartbeat'ы в очередь, пока сервер недоступен. Центральный механизм — heartbeat-слияние: watcher шлёт событие нулевой длительности; если data идентична предыдущей и попадает в окно pulsetime, сервер продлевает длительность последнего события вместо создания нового. Так секундный поллинг активного окна превращается в компактные интервалы «окно X было активно 47 минут» без роста базы. Важный документированный нюанс: pulsetime нельзя ставить произвольно большим — после сна машины идентичные события ошибочно склеятся через разрыв (в aw-watcher-window pulsetime = poll_time + 1). Слабость ActivityWatch — сам поллинг раз в секунду; правильнее гибрид: событийный триггер от ОС + heartbeat для длительностей. Для активного окна это SetWinEventHook(EVENT_SYSTEM_FOREGROUND, WINEVENT_OUTOFCONTEXT) — паттерн из блога Raymond Chen: асинхронная доставка в свой процесс без внедрения в чужие, нужен message loop, и нужно корректно обрабатывать уже уничтоженное окно. AFK-детекция должна быть тривиальной: Windows отдаёт «время с последнего ввода» одним вызовом (так делает aw-watcher-afk, порог 3 минуты) — никакого перехвата ввода не требуется.

screenpipe интересен и как источник удачных решений, и как предостережение. Удачное: событийный захват вместо интервального — снимок делается по смене приложения/фокуса, клику, паузе в наборе текста, копированию в буфер, плюс idle-fallback раз в ~5 секунд; каждый снимок спарен с обходом accessibility-дерева («same timestamp, same frame»), а OCR — только fallback, когда accessibility-текст пуст (remote desktop, игры). Дедупликация кадров + захват «только когда что-то изменилось» дают заявленные ~300 МБ/8ч вместо ~2 ГБ при непрерывной записи и 5–10 ГБ/мес. Схема SQLite показательна: frames с capture_trigger и full_text (accessibility-текст с OCR-fallback), elements с FTS5, ui_events, медиа отдельно на диске JPEG'ами; наружу — localhost REST + MCP. Предостережение: заявленные 5–10% CPU и 600 МБ RAM в реальности регулярно не выдерживались — issue #183 (CPU >100%, RAM >10 ГБ), #278 (утечка: 8 ГБ за 30 минут, баунти $300), #2571 (утечка 1,5–2,7 ГБ/час до OOM на 25,7 ГБ; корневая причина — цикл восстановления аудиоустройства, поллящий каждые 2,25 с и дававший 56% всех строк логов; запись на диск 305–684 КБ/с). Уроки: непрерывный медиазахват — это отдельный тяжёлый инженерный домен, его нельзя тащить в ядро ассистента; фоновые poll-циклы «на всякий случай» становятся главным пожирателем ресурсов; квоты и авто-очистка хранилища нужны с первого дня (issue #696 о неограниченном росте).

Windows Recall (по официальному посту Microsoft о редизайне 2024 года) — лучший образец архитектуры «данные истории — отдельная привилегированная подсистема». Снапшот делается «каждые несколько секунд и при смене содержимого активного окна»; локальный семантический индекс — векторная БД поверх SQLite; бюджет диска задаётся явно по размеру накопителя (25/75/150 ГБ) с вытеснением старейших снапшотов и retention 30/60/90/180 дней; фильтрация чувствительного контента и приватных вкладок происходит до записи; в трее — постоянный индикатор захвата с паузой; всё строго opt-in. После публичной критики Microsoft перестроила систему вокруг принципа: хранилище истории изолировано (шифрование каждого снапшота своим ключом, обработка в VBS-энклаве), а UI и остальная система считаются недоверенными потребителями — данные выдаются только через шлюз после явной авторизации пользователя, сессии доступа истекают по таймауту, настройки самого механизма защищены от «тихого» изменения. Для single-user ассистента это переводится в качество архитектуры: история активности — самые чувствительные данные в системе, доступ к ним должен идти через один модуль-шлюз с политиками, а не «любой модуль читает SQLite напрямую». Показательно и то, что осталось слабым местом: защитили хранилище, но не путь данных до экрана — т.е. проектировать надо весь тракт, а не только storage.

Rewind.ai подтверждает достижимость низкой нагрузки (1–5% CPU на Apple Silicon, ~14–24 ГБ/мес при «3750x»-сжатии) и даёт правильную границу с LLM: в облачную модель уходит только производный текст (OCR/транскрипты), сырые записи никогда не покидают машину — ровно тот паттерн LLM-независимости, который нужен MARK XXXV. Судьба продукта (ребрендинг в Limitless, покупка Meta, отключение локального захвата в декабре 2025) — аргумент строить ядро на открытых компонентах.

Синтез «что событие, а что снапшот»: событиями должны быть изменения ФС (USN), смена фокуса/появление окон (WinEvents), запуск/остановка процессов, действия самого ассистента; снапшотами — bootstrap-состояния (MFT-индекс, список окон при старте) и периодическая реконсиляция для самокоррекции дрейфа. Текущее состояние («world model») — производная от журнала событий, восстановимая после сбоя, как индекс Everything из USN. Хранение двухуровневое: компактные вечные производные (интервалы активности, текст, метаданные — мегабайты в год у ActivityWatch-подхода) и дорогие сырые данные (если вообще нужны) с квотой и eviction. UI Automation использовать только по требованию и с CacheRequest (bulk-fetch свойств одним cross-process вызовом; обход дерева от корня рабочего стола — документированная ловушка, до 70 секунд), а не как фонового краулера.

## Идеи

- **MFT-bootstrap + USN-инкременты для файлового индекса** [Everything (voidtools FAQ/forum), Microsoft Docs: Change Journals]: Первичный индекс строится одним чтением NTFS MFT (секунды на сотни тысяч файлов), далее поддерживается только чтением USN Change Journal, который ведёт драйвер NTFS независимо от приложения; при переполнении журнала — переиндексация из MFT. | Почему: Журнал durable: изменения не теряются, когда приложение не запущено — при старте оно догоняет историю. Нулевая фоновая нагрузка на сканирование, копеечная память (~35–100 МБ RAM на 250К–1М файлов), моментальный поиск. Microsoft прямо позиционирует журнал как механизм для indexing-сервисов. | Применимость: high — заменить watchdog-наблюдение за файлами в awareness-слое MARK XXXV: либо собственный ридер USN, либо интеграция с Everything. Watchdog оставить максимум для 1–2 «горячих» папок, где нужна мгновенная реакция.
- **Делегировать файловый поиск Everything через IPC** [voidtools SDK docs (WM_COPYDATA, named pipe \\.\PIPE\Everything IPC, ES.exe, everything_sdk3)]: Everything работает как локальный сервис с официальным IPC/SDK; сторонние приложения шлют запросы и получают результаты из его всегда актуального индекса. | Почему: Целый домен (индекс всех файлов + инкрементальная актуальность + язык запросов) закрывается зрелым чужим кодом за ~50 МБ RAM вместо тысяч строк своих; соответствует цели «сопровождает один человек». | Применимость: high — тул file_search в Jarvis становится тонким адаптером к Everything (named pipe или ES.exe); свой индекс не нужен вовсе. Риск: внешняя зависимость, но продукт бесплатный, стабильный 15+ лет, с фоллбеком на собственный MFT/USN-ридер.
- **Heartbeat-слияние событий при записи** [ActivityWatch (docs: buckets-and-events, aw-watcher-window main.py)]: Watcher шлёт события нулевой длительности; хранилище продлевает последнее событие, если data идентична и timestamp в окне pulsetime, иначе создаёт новое. Pulsetime чуть больше интервала опроса. | Почему: Компактирование на этапе записи: часы одинаковой активности схлопываются в одну строку, база растёт от числа переключений, а не от времени. Дешёвая и проверенная альтернатива пост-обработке. | Применимость: high — применять для журнала активности world model (активное окно, текущий документ, активное приложение) в SQLite. Учесть документированную ловушку: слишком большой pulsetime ложно склеивает события через сон машины.
- **Событийный захват с idle-fallback вместо интервального** [screenpipe (docs.screenpipe.com/architecture)]: Захват состояния происходит по осмысленным событиям ОС (смена фокуса, клик, пауза в наборе, clipboard), с редким фоллбек-таймером (~5 с) на случай, когда события не приходят; дубликаты отбрасываются. | Почему: Стоимость пропорциональна активности пользователя, а не времени работы: ~300 МБ/8ч против ~2 ГБ при непрерывной записи; при простое системы нагрузка стремится к нулю. | Применимость: high — общий принцип для всего awareness-слоя Jarvis: любые обновления world model триггерятся событиями (WinEvents, USN), а редкий таймер служит только реконсиляцией и страховкой от пропущенных событий.
- **SetWinEventHook(EVENT_SYSTEM_FOREGROUND, OUTOFCONTEXT) для активного окна** [Raymond Chen, The Old New Thing (devblogs.microsoft.com)]: Подписка на системное событие смены переднего окна с асинхронной доставкой в собственный процесс (без внедрения в чужие), далее GetWindowThreadProcessId → OpenProcess(QUERY_LIMITED_INFORMATION) → QueryFullProcessImageName. | Почему: Событийно, без поллинга и без вмешательства в другие процессы; канонический паттерн от Microsoft именно для «monitor what applications users spend time in». Нужен message loop и обработка уже уничтоженного окна — известные, дешёвые издержки. | Применимость: high — заменить любой опрос активного окна в awareness-слое; событие кормит шину и heartbeat-журнал. На Python доступно через comtypes/pywin32 с собственным message loop в потоке watcher-процесса.
- **Watcher-процессы → локальный API → bucket per watcher** [ActivityWatch (docs: architecture)]: Каждый наблюдатель — отдельный процесс, пишущий через локальный REST в своё изолированное хранилище-bucket; сервер ничего не собирает сам; клиентская библиотека буферизует данные при недоступности сервера. | Почему: Отказ одного watcher не трогает остальных и не портит чужие данные; новые наблюдатели добавляются без изменения ядра (расширяемость = просто новый процесс + новый bucket); естественная точка для шины событий. | Применимость: high — прямой шаблон декомпозиции монолитного main.py: awareness-компоненты (окна, файлы, приложения) как отдельные процессы/подпроцессы, ядро — брокер+хранилище; одновременно решает задачу вынести tkinter UI из процесса движка.
- **Бюджет диска + oldest-first eviction + retention-окна** [Windows Recall (Microsoft Learn: Manage Recall)]: Хранилищу истории явно выделяется квота, зависящая от размера диска (25/75/150 ГБ), при достижении — вытеснение старейших записей; отдельно настраивается срок хранения (30–180 дней). | Почему: Хранилище истории по построению не может съесть диск; поведение при переполнении определено заранее, а не обнаруживается аварийно (ср. screenpipe issue #696 о неограниченном росте). | Применимость: high — заложить в новую подсистему истории Jarvis с первого дня: квота в конфиге, фоновая компактация/eviction, retention по типам данных (сырые данные — недели, производные — годы).
- **Двухуровневое хранение: сырое vs производное** [Windows Recall, Rewind.ai, screenpipe]: Дорогие сырые данные (снимки, медиа) хранятся отдельно с коротким retention, а извлечённые из них компактные производные (текст, метаданные, интервалы активности, векторный индекс) — долго; поиск работает по производным. | Почему: Производный текст на порядки меньше сырья (метаданные ActivityWatch — мегабайты в год; JPEG-кадры screenpipe — гигабайты в месяц), при этом закрывает 95% запросов «что я делал/где этот документ». | Применимость: high — world model и история активности Jarvis должны хранить только производные (имена окон, пути, извлечённый текст, интервалы) в SQLite+FTS5; сырых снимков экрана в v1 не делать вообще — это отдельный тяжёлый домен.
- **История активности как изолированная подсистема со шлюзом доступа** [Windows Recall (blogs.windows.com: Update on Recall security and privacy architecture)]: Хранилище истории — отдельная подсистема: данные зашифрованы, обрабатываются в изолированном компоненте, а UI и прочие модули считаются недоверенными потребителями и получают данные только через шлюз после явного согласия пользователя, сессии доступа ограничены по времени; настройки самого механизма нельзя изменить незаметно. | Почему: После публичного провала первой версии (открытая SQLite, читаемая чем угодно) Microsoft перепроектировала систему вокруг принципа единственной точки доступа — это и есть анти-дрейф-паттерн, который у MARK XXXV уже есть для разрешений (core/security.py), перенесённый на данные. | Применимость: medium — в single-user настольном приложении энклавы не нужны, но принцип применим напрямую: один модуль-шлюз владеет БД истории, все обращения (включая LLM-контур и плагины) идут через него с policy-проверкой; шифрование файла БД и явная кнопка паузы/индикатор записи — вопрос UX-доверия.
- **В LLM уходит только производный текст** [Rewind.ai (Ask Rewind)]: При обращении к облачной модели отправляется только извлечённый текст из релевантных фрагментов истории; сырые записи и медиа никогда не покидают машину. | Почему: Чёткая архитектурная граница: capture/index-слой полностью локален и не знает о LLM, LLM-слой видит только текстовый контекст — это одновременно бережное отношение к данным и точка LLM-независимости. | Применимость: high — оформить в Jarvis контракт «awareness отдаёт текстовые срезы world model», одинаковый для Gemini, локальной модели или любой будущей; решает и задачу отвязки от Gemini Live.
- **Accessibility-текст прежде OCR, UIA только с CacheRequest** [screenpipe (architecture docs), Microsoft Learn (UI Automation caching)]: Структурный текст окна берётся из accessibility/UIA-дерева (быстрее и точнее OCR); свойства элементов запрашиваются bulk-запросом CacheRequest одним cross-process вызовом, обход строится от конкретного окна, не от корня рабочего стола. | Почему: Поэлементные UIA-вызовы — это cross-process round-trip каждый; документированная ловушка — обход от корня занимал ~70 секунд. Кэширование и узкий scope делают чтение структуры окна практичным по латентности. | Применимость: medium — для тулов Jarvis «прочитай, что на экране/в окне»: читать UIA по требованию или по событию смены фокуса, с CacheRequest и ограниченным TreeScope; не делать фонового краулинга деревьев.
- **Плагины с декларативными правами, проверяемыми в ядре** [screenpipe pipes]: Плагин описывает в манифесте (frontmatter), к каким приложениям/типам данных/эндпоинтам ему нужен доступ; ядро выдаёт per-plugin токен и enforce'ит ограничения в middleware сервера, а не полагается на дисциплину плагина. | Почему: Расширяемость без потери контроля: та же идея единственного источника правды о правах, что в policy-таблице MARK XXXV, распространённая на сторонний код. | Применимость: medium — при проектировании плагинной системы Jarvis: манифест возможностей плагина + проверка в том же центральном гейте core/security.py, через который обязан ходить и agent/executor (закрывает известную дыру аудита).

## Анти-паттерны

- **Непрерывный тяжёлый захват внутри основного процесса** [screenpipe issues #183, #278, #2571]: Реальные измерения расходятся с заявленными 5–10% CPU: CPU >100%, RAM до 25,7 ГБ с OOM-kill, утечки 1,5–2,7 ГБ/час, запись на диск сотни КБ/с. Медиазахват/OCR — отдельный инженерный домен; встроенный в ядро ассистента, он утащит за собой весь процесс. Для Jarvis: не тянуть запись экрана в v1, а если делать — только изолированным процессом с супервизором и лимитами.
- **Поллинг как базовый механизм наблюдения** [aw-watcher-window (1 с), screenpipe issue #2571 (recovery-loop каждые 2,25 с)
]: Фоновая нагрузка постоянна независимо от активности пользователя и складывается из десятка «дешёвых» циклов в заметный tail-CPU; в screenpipe один вспомогательный poll-цикл дал 56% всех строк логов и участвовал в утечке. ОС предоставляет событийные механизмы (WinEvents, USN, время последнего ввода) почти для всего; таймер допустим только как редкая реконсиляция.
- **Рекурсивный watcher на большие деревья вместо журнала ФС** [python-watchdog docs, Microsoft Docs: Change Journals]: Directory notifications требуют постоянно работающего приложения, теряют историю между перезапусками (нужен полный rescan), дороги на больших деревьях, а в watchdog документированы искажения семантики (директория как файл при удалении, неполные сканы перемещённых каталогов). MARK XXXV сейчас именно так следит за файлами — это и хрупко, и дорого; USN-журнал решает задачу durable и бесплатно.
- **World model только в памяти + плоский JSON без индекса** [прототип MARK XXXV; контраст — SQLite+FTS5 у screenpipe/Recall/ActivityWatch]: Состояние теряется при перезапуске и не допускает поиска; все изученные системы сошлись на локальном SQLite (метаданные+FTS5, медиа отдельно на диске) как на минимально достаточном хранилище. Текущее состояние должно быть восстановимой производной от журнала событий (как индекс Everything из USN), а не единственной копией истины в RAM.
- **Хранилище истории без квоты и политики вытеснения** [screenpipe issue #696; контраст — квоты Recall]: История активности растёт монотонно; без явного бюджета и oldest-first eviction проблема обнаруживается аварийно — заполненным диском и ручными cron-чистками. Recall показывает правильную форму: квота от размера диска + retention-окна, заданные до запуска, а не после инцидента.
- **Хранить сырые данные там, где достаточно производных** [screenpipe (~300 МБ/8ч JPEG) vs ActivityWatch (мегабайты метаданных)]: Сырьё дороже производных на 2–3 порядка и превращает проект в систему управления медиахранилищем; для задач ассистента («что я делал», «где документ», «какое окно было активно») достаточно текста, путей и интервалов. Сырые снимки — опция с коротким retention, не фундамент.
- **БД истории, открытая для прямого чтения любым модулем** [Windows Recall v1 (2024) и его публичный редизайн]: Первая версия Recall хранила снапшоты и OCR-текст в обычной SQLite, доступной любому коду, — это вызвало публичный провал и полное перепроектирование вокруг шлюза доступа. Урок архитектуры данных: у самой чувствительной БД в системе должен быть один модуль-владелец и одна точка доступа с политиками; «каждый модуль дергает SQLite сам» — тот же дрейф, что и обход центрального permission-гейта агентным executor'ом в MARK XXXV.
- **Произвольно большой pulsetime / агрессивное слияние событий** [ActivityWatch (PR #68 aw-watcher-window, PR #64 aw-watcher-afk)]: Слишком широкое окно слияния ложно склеивает идентичные события через разрыв (сон, выключение), искажая длительности; мейнтейнер прямо предписывает pulsetime = ожидаемый интервал между событиями + малый запас. Похожие миллисекундные краевые случаи уже ловили как баги (события, не сливавшиеся из-за 1 мс).
- **Ядро продукта на проприетарной внешней системе наблюдения** [Rewind.ai → Limitless → Meta (локальный захват отключён 19.12.2025)]: Rewind был технически образцовым (1–5% CPU, локальное сжатие «3750x»), но после покупки Meta локальная запись экрана была отключена у всех пользователей. Для проекта на 5+ лет внешние компоненты допустимы как заменяемые адаптеры (Everything — за ним стоит открытый механизм MFT/USN, воспроизводимый самостоятельно), но не как невоспроизводимое ядро.
