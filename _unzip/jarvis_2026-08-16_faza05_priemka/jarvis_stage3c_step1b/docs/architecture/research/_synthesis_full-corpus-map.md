## 1. Карта корпуса: документы и pipeline принятия решений

### 1.2. Слой дизайнов (`research/design_[ABC]-*.md`)

Три независимых полных архитектуры под одну и ту же задачу, каждая со своей «линзой»:

- **A «Эволюция»** (`design_A-evolution.md`) — максимум переиспользования, гейт первым, миграция серией самоценных этапов. ⚠️ Называет целевую систему **MARK XL**, тогда как корпус — MARK XXXVI.
- **B «Чистое ядро»** (`design_B-clean-kernel.md`) — микроядро <2000 строк, всё — плагины, 4 процесса, per-domain БД. ⚠️ Кодовое имя **MARK L** — третья версия нумерации в корпусе.
- **C «Прагматичный минимализм»** (`design_C-pragmatic.md`) — 2 процесса, 2 файла БД, «абстракция оплачивает существование».

### 1.3. Мета-слой: судьи и критик (`judgments.md`, `critic.md`)

- **judgments.md** — три судьи с разными линзами (longevity / performance-solo / data-safety-ux) оценивают A/B/C по 6 критериям × шкала 1–10, каждый даёт раздел **Graft** («что пересадить в победителя»). Итог: **C=150, A=138, B=124** (суммы сходятся с покритериальными оценками), счёт 2:1 за C.
- **critic.md** — оценивает всё исследование: архитектура готова к миграции, но фиксирует **4 блокирующих пробела** (тестирование, наблюдаемость, Windows-факты, жизненный цикл) с готовыми ТЗ на дорасследование.

### 1.4. Слой gapfill (`research/gapfill_*.md`) — ответы на пробелы критика

- `gapfill_0` — стратегия тестирования (пирамида «инфраструктура снизу, LLM сверху»).
- `gapfill_1` — наблюдаемость (своя SQLite + Datasette вместо серверных стеков).
- `gapfill_2` — Windows-развязки и жизненный цикл (uv, Task Scheduler, слоты обновлений, миграции, бэкап).

### 1.5. Внешний research-контур (`DEEP-RESEARCH-PROMPT.md`, `external_*.md`, `_verify_workflow.js`)

Замкнутый цикл «после принятия архитектуры»: самодостаточный промпт для внешних deep-research AI (задача — улучшать/опровергать отдельные решения, НЕ перепроектировать) → два внешних отчёта (Claude — высокое доверие; Manus — смешанное, с галлюцинациями) → workflow адверсарной верификации (7 параллельных фактчекеров по кластерам: sqlite-encryption, usn-everything, gemini-live-limits, russian-streaming-stt, ufo-context-eng, windows-daemon, incidents, + uia-ocr). ⚠️ В скрипте 8 тематических кластеров при логе «/7» — мелкое внутреннее расхождение. ⚠️ Итоговые вердикты верификации лежат в `external_verification-verdicts.md`, которого в конспектах **нет** — при работе с корпусом его нужно учитывать отдельно.

### 1.6. Вершина: `ARCHITECTURE-RESEARCH-2026-07.md`

Центральный синтезирующий документ: конденсирует всё вышеперечисленное в целевую архитектуру MARK XXXVI и план миграции. Это единственный документ, где зафиксирован финальный, пересобранный план этапов (⚠️ судьи/критик отмечали, что в самих judgments.md единого плана нет — он появился только в синтезе).

**Итоговый pipeline**: `code-assets` (что есть) + `research_*` (что известно миру) → `design A/B/C` (три варианта) → `judgments` (гибрид C+A+B) → `critic` (пробелы) → `gapfill 0–2` (закрытие пробелов) → `ARCHITECTURE-RESEARCH` (синтез) → `DEEP-RESEARCH-PROMPT` → внешние отчёты → верификация → точечные поправки.

## 2. Целевая архитектура MARK XXXVI с высоты птичьего полёта

### 2.1. Философия

Три **неторгуемых требования**, реализуемых структурно (кодом границ), а не дисциплиной:

- **Р1** — единый гейт разрешений: ВСЕ пути исполнения (live-голос, чат, шаг плана, плагин) через одну функцию `dispatch()`.
- **Р2** — независимость от LLM-провайдера: смена модели = 1 строка конфига, смена провайдера = адаптер ~200–500 строк.
- **Р3** — откат файловых операций: preview + журнал + обратная операция; «отмени последнее» голосом.

Рамки: один сопровождающий, горизонт 5+ лет, «каждая сущность оплачивает существование»; целевой объём ядра **8–12k строк** (против 23–26k прототипа); idle ≤150 МБ RSS, <1% CPU, ≤1 пробуждение/мин; движок **никогда не работает от администратора**; ассистент работает каждый день миграции.

### 2.2. Процессная топология

```
┌─────────────────────────────────────────────────────────────┐
│  jarvis-engine (asyncio-демон, всегда живой)                │
│  ┌──────────┐ ┌────────┐ ┌───────────┐ ┌────────┐          │

│  │voice │ │memory  │ │worldmodel│ │journal│ │bus (~15  │   │
│  │(Voice│ │(hot/   │ │gateway   │ │(saga+ │ │ frozen-  │   │
```

Два долгоживущих процесса + ленивый ingest-воркер + MCP-хосты + эфемерные воркеры. IPC — **ID строк SQLite, не блобы**. Отвергнуты: процесс-на-плагин, брокеры сообщений, 4 постоянных процесса варианта B.

### 2.3. Потоки данных (путь запроса)

wake word (локальный, бесплатный) → открытие Live-сессии / текст из UI → **steering-очередь** (реплики вклиниваются на границе итерации) → **трёхуровневый роутер** (0: прямой ответ / 1: лёгкий цикл ≤2–3 хода, ~90% трафика / 2: Plan-and-Execute) → каждый tool call через **dispatch()** (preview → подтверждение по уровню риска → saga-intent → исполнение → completion → undo-стек) → план в `execution_log` (intent ДО, результат ПОСЛЕ — рестарт продолжает с последнего COMPLETE-шага) → события в шину → UI и голос — независимые проекции (голосу — только вехи) → ответ (sentence-chunked TTS + кэш частых фраз). Бюджет лёгкого пути **≤500 мс** от конца речи до действия.

Awareness-поток: USN/WinEvents → ingest-воркер (коалесценция, heartbeat-слияние, батч-транзакции) → history.db → агрегированные `file.changed` в шину движка → sleep-time консолидация в простое извлекает факты в память jarvis.db.

### 2.4. Хранение

- **jarvis.db** (вечное; писатель — движок): память, world-снапшот, execution_log, action_journal, гранты, метрики, llm_calls, конфиг-KV.
- **history.db** (вытесняемое; писатель — ingest-воркер): наблюдения с квотой, oldest-first eviction, retention по типам.
- Принцип «**один писатель на файл БД**»; ссылки между файлами — soft (атомарного снапшота двух WAL не существует — слабая связность принята как ADR-контракт); всё состояние в БД, не в RAM (рестарт дёшев); конфиги — temp + ReplaceFile.
- Технология одна: SQLite (WAL, synchronous=NORMAL, busy_timeout) + FTS5 + sqlite-vec (именно **asg017/sqlite-vec**, MIT) + RRF-слияние.

## 3. Ключевые принятые решения (что, где, почему)

| Решение | Документ-источник | Почему |
|---|---|---|

| **4 уровня риска** (read/reversible+Undo/external-ask/irreversible-блокирующий) | `action-layer-undo` (AWS Agentic Lens) | «Подтверждать всё» ломает надзор — рефлекторное «да»; авто+Undo лечит confirm-усталость |

## 4. Отвергнутые подходы и почему

**Фреймворки и оркестрация:**
- **LangChain / CrewAI / OpenManus / планировщики Semantic Kernel** — цепочечная модель не ложится на stateful-цикл; SK сам удалил планировщики; CrewAI manager-worker «не работает как задокументировано»; отладка через 5 слоёв абстракций.
- **LiteLLM как зависимость** — мультитенантный прокси на 100+ провайдеров при потребности в 3–5; supply-chain компрометация версий 1.82.7–1.82.8 (март 2026), CVE CVSS 9.9, попадание в CISA KEV — неприемлемо для программы с доступом ко всем личным файлам. ⚠️ **Противоречие внутри корпуса**: `research_agent-frameworks` ещё рекомендовал LiteLLM как библиотеку; `research_llm-abstraction` и все последующие документы его отвергли — побеждает поздняя позиция.
- **Мультиагентность с правом записи** — Cognition: работают только однопоточные записи; субагенты допустимы только read-only.
- **Code-as-action** (произвольный Python) — гейт не может классифицировать риск произвольного кода, аудит и откат разваливаются; это тот же класс дыры, что сырой `command` в cmd_control.
- **Temporal / полный event sourcing / DAG-параллелизм (LLMCompiler)** — оверинжиниринг для одного ПК; event sourcing — паттерн уровня одного модуля (action_journal).

**Хранение:**
- **Векторные/графовые СУБД** (Neo4j/Graphiti ~2 ГБ RAM, LLM-вызовы на каждую запись) — идея би-темпоральности берётся 4 колонками в SQLite, стек нет.
- **Плоский JSON** — текущий анти-паттерн прототипа (перезапись целиком, нет индексов/поиска/забывания).
- **Единый SQLite-файл (A)** и **4 per-domain БД (B)** — первый внутренне противоречив (риски A сами требуют отдельного файла индексатора), вторые «не оплатили существование» (4 трека миграций, ATTACH-запросы).
- **Litestream** — always-on процесс, долгая читающая транзакция, инцидент молчаливой потери репликации (#1083).

**Windows-механика:**
- **watchdog как основной механизм** — нет durability между перезапусками; остаётся только на 1–2 горячих папках.
- **TxF** — деприкейтнут самим Microsoft; **System Restore** — не покрывает документы; **снапшот-rollback** — стирает параллельные изменения.
- **Windows-служба** — session 0 не видит окна/аудио; **PyInstaller onefile** — %TEMP% чистится ОС.
- **«DPAPI шифрует файл БД»** — ⚠️ фигурировало в дизайнах A и B, судьи опровергли: нереализуемо для живого WAL; DPAPI — только для секретов.
- **«Everything через named pipe»** — ⚠️ ошибка research-слоя и дизайнов, исправлена судьями: в 1.4 это WM_COPYDATA/SDK DLL/ES.exe, named pipe только в 1.5 alpha.
- **Собственный USN-ридер как основной путь** — требует elevation (ни один из трёх дизайнов не заметил); демотирован до последнего резерва с крошечным elevated-хелпером.
- **Работа ассистента под администратором** — запрещённое состояние.

**Наблюдаемость и голос:**
- **Langfuse / Phoenix always-on / Logfire self-hosted / OTel Collector / LiteLLM-proxy / Prometheus** — не проходят бюджет RAM либо избыточны для single-user.
- **DeepEval** (всё LLM-judged), **promptfoo** (Node-стек, куплен OpenAI), **живые LLM в CI-гейте**, **VCR-кассеты как основная сетка** — отвергнуты gapfill_0.
- **Porcupine** (нет русского, вендор-лок), **XTTS v2** (CPML, мёртвый апстрим), **Kokoro/Moonshine** (нет русского), **cloud-ASR вместо локального wake word** (дорого, убивает приватность).
- **Скриншоты/медиазахват в v1** — урок screenpipe (CPU >100%, OOM 25,7 ГБ; один poll-цикл дал 56% строк логов); производные на 2–3 порядка дешевле и закрывают 95% запросов.

**Отвергнутые галлюцинации внешнего research (Manus):** «always-on тариф Gemini с дисконтом на idle», «EFS на Windows 11 Home», «AF_UNIX в CPython на Windows», tus-протокол, «Everything SDK — MIT» без текста лицензии.

### 5.2. Вердикты судей

- **longevity → C**: единственный вариант со структурным анти-оверинжинирингом («абстракция оплачивает существование»); 8–10k строк — единственный объём, который один человек удержит в голове; все швы долгоживучести на месте.
- **performance-solo → C**: минимальный always-on footprint, минимум движущихся частей при сохранении всех трёх неторгуемых требований.
- **data-safety-ux → A** (единственный несогласный): гейт закрывается в рабочей системе через 3–5 недель против 8–12 у C; самый проверяемый план миграции. **Ключевая оговорка**: «по нейтральной сумме критериев C выиграл бы» — выбор A обусловлен строго линзой судьи, поэтому его graft из C — максимальный. Расхождение формально не снято, но содержательно закрыто взаимной пересадкой.

### 5.3. Что взято из проигравших (grafts)

**Из A (миграционная механика):**
- «Этап 0.5»: тонкий `dispatch()` ПОВЕРХ существующей policy-таблицы **раньше манифестов** — снимает главный дефект C (гейт после манифестов, дыра живёт дольше без необходимости);
- golden-сценарии (20–30 запросов, включая interruption/steering) как merge-гейт каждого этапа;
- feature-flag на новый цикл (сначала текст, голос последним) + журнал расхождений 2 недели;
- критерий «старый путь **УДАЛЁН**, не выключен» + календарный лимит двойных механизмов 2 недели.

**Из B (контрактная гигиена):**
- frozen-каталог событий в одном модуле, одно api_version, строгая аддитивность, генерируемый EVENTS.md, консоль-подписчик шины;
- lifecycle плагинов loaded/not_ready(retry+backoff, кап 1 час)/auth_required/error (паттерн HA ConfigEntry);
- perf-бюджеты как CI-тестируемые артефакты;
- скаффолд-генератор тула (manifest + каркас одной командой);
- MCP-совместимая форма ActionRegistry с этапа 1 (а не 7) — срезает ~5-месячный shim-налог;
- **local-first memory-extractor как ДЕФОЛТ** (⚠️ в A он был лишь «кандидатом» — судья data-safety поднял до дефолта: экстракция личных фактов не уходит в облако без явного opt-in);
- дизайн Observer как готовый чертёж выноса ingest.

**Дефекты C, закрытые судьями:** песочница Playwright-MCP (дыру «downloads/профиль мимо гейта» не заметил ни один дизайн — нашёл только longevity-судья); честный CI-контракт вместо overclaim «физически нет доступа к os/shutil»; ingest — не в движке (GIL-джиттер аудио при USN-штормах), а в ленивом воркере-владельце history.db; IFileOperation в выделенном STA-потоке; мост WebSocket↔tkinter mainloop; шифрование history.db — явное решение, не молчание.

**Общие фактические ошибки, найденные судьями:** Everything IPC (named pipe → WM_COPYDATA), «DPAPI шифрует БД», elevation MFT/USN, бэкап WAL копированием, бюджет отклика ужесточён до ≤500 мс.

## 6. Тематические разделы

### 6.1. Безопасность

- **Единый гейт**: пайплайн hooks → deny → circuit-breaker-пол → allow → ask → профиль сессии (observe/normal/trusted); deny непереопределяем. Неотключаемый пол: корни дисков, %USERPROFILE%, каталог самого Jarvis — confirm в любом профиле.
- **Честность про «единственный путь»**: для in-process Python это **CI-контракт**, не физика — import-linter (запрет os/shutil/subprocess в tools/ и plugins/) + ruff TID251 + юнит-тест «хендлер недоступен вне dispatch()» как merge-гейт. ⚠️ Формулировка B «модули физически не имеют доступа к os/shutil» признана судьями преувеличением.
- **Confirm-UX**: 4 уровня риска; «авто+Undo» включается только после стартовой самопроверки «журнал+staging работоспособны» (иначе деградация до ask); консервативный профиль первых недель → перевод в авто по статистике confirm/undo-rate; правка параметров прямо в диалоге; changeset-превью с чекбоксами («одобрить 18 из 20»); панель standing-grants (видимые, отзываемые, с TTL).
- **Durable-подтверждения** с хэш-пиннингом payload, расширенным (по внешнему research) на **содержимое** целевых файлов (mtime+размер+хэш на preview, перепроверка на apply).
- **Уроки инцидентов** (Replit — агент стёр prod-БД и соврал; PocketOS — удаление Railway volume за 9 секунд; Cursor Plan Mode): system prompt — advisory, hard boundaries — вне reasoning-петли; **бэкапы — вне blast radius агента** (отдельный ScopedRoot без прав записи/удаления).
- **Данные в покое**: матрица угроз — кража диска → BitLocker/Device Encryption + ACL; другой пользователь → ACL; чужой процесс в сессии → вне модели угроз (SQLCipher/apsw-sqlite3mc — опция с обязательным smoke-тестом связки с sqlite-vec/FTS5/WAL; порог отката: vec0 не работает или KNN-overhead >20% → EFS (только Pro) или частичное шифрование). Секреты — DPAPI/keyring.
- **Поведенческие авторитеты** (сколько спрашивать) — только явная настройка, никогда LLM-выведенная personality (урок прототипа: «JUST DO IT» из речи ослаблял confirm).
- **Фенсинг недоверенного текста** (санитизация из _world_model.py) — стандарт для всех инжектируемых секций промпта.

### 6.2. Память и world model

**Память** — слоистая, на jarvis.db:
- Горячий слой: 3–5 капированных core-блоков (~1–2k токенов) в промпте, **генерируемых из БД** тем же анти-дрейф-паттерном, что capability truth.
- Холодный слой: append-only эпизоды + би-темпоральные факты (valid_from/valid_to/recorded_at/invalidated_at — идея Zep без стека) + процедурные сценарии (CoALA-типы с разными политиками).
- Поиск: FTS5 (BM25) + sqlite-vec (384d, брутфорс достаточен до ~100k векторов) + RRF ~70/30; ~30% запросов содержат точные якоря — BM25 обязателен; ретривал детерминированный, **без LLM на чтении**.
- Консолидация: sleep-time процесс в простое (Letta + OpenAI dreaming); запись дёшево — ADD-only + entity linking (урок mem0 v3); забывание = decay + саммари + evergreen, жёсткое удаление только по команде.
- Экстрактор — **локальная модель по умолчанию** (GBNF-гарантия структуры), облако — opt-in.
- Память видима, редактируема, скоупируема; пользовательский слой — markdown как источник истины (OpenClaw).
- ⚠️ **Противоречие по эмбеддеру**: `research_memory-systems` рекомендует **nomic-embed-text** (137M, ~274 МБ), все остальные документы и итог — **all-MiniLM-L6-v2** (22M, 384d) через fastembed/ONNX. Итоговая архитектура зафиксировала MiniLM; расхождение в корпусе не оговорено явно.

**World model** — «данные, а не магия»:
- Схема всех зрелых систем: bootstrap-снапшот (MFT/Everything) + инкрементальный поток (USN, ведёт сам драйвер NTFS — catch-up после простоя) + компактирование при записи (heartbeat-слияние ActivityWatch, pulsetime = интервал + запас) + бюджет хранения (квоты, oldest-first eviction, retention по типам).
- Окна — событийно `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)`, AFK — GetLastInputInfo; никакого поллинга.
- Состояние — материализованная проекция append-only журнала диффов + периодическая реконсиляция; в RAM — только горячий срез с лимитом.
- Хранятся **только производные** (пути, заголовки, интервалы, текст); сырых скриншотов в v1 нет.
- Доступ — **только через world_gateway** с policy-проверкой (урок редизайна Recall: изолированное хранилище, шлюз, квоты, индикатор наблюдения, opt-in, «забудь X»). История активности — самые чувствительные данные системы.
- В облако — только производный текст (граница Rewind).

### 6.3. LLM-абстракция

- **Двухуровневая граница**: batch абстрагируется полностью; realtime — только семантические события + capability-флаги (wire-протокол/VAD/форматы/lifecycle — в драйверах).
- Batch: два адаптера над **официальными SDK** — google-genai (новый; старый google.generativeai удаляется) + openai-совместимый (OpenAI/Ollama/LM Studio/OpenRouter/llama.cpp/vLLM); ~700–1200 строк. ⚠️ Внутри дизайна A объём роутера оценён и ~200–500, и ~500–1000 строк — вилка не сведена.
- Паттерны LiteLLM копируются: fallback ПОВЕРХ retry, классы fallback по таксономии ошибок, CooldownCache; поле raw рядом с нормализованным (OpenRouter native_finish_reason).
- **registry.yaml**: роли live-voice/chat/planner/memory-extractor/classifier/embedder → provider:model + fallback-цепочка + требуемые capabilities с валидацией на старте. Убивает 14 загрузок ключа и 36 хардкодов.
- Structured output: общий плоский поднабор JSON Schema (без union, вложенность ≤2) + клиентская валидация + одна repair-итерация (Gemini responseSchema отказывает **тихо**); локально — GBNF llama.cpp (валидный JSON даже на 4B).
- Local-first альтернатива на каждую облачную роль: голос → каскад; chat/planner → Ollama (нативный /api/chat, не /v1); memory-extractor → локальный по умолчанию.
- Gemini Live-специфика (внешний research): resumption 2 ч (Dev API) / 24 ч (Vertex), contextWindowCompression, GoAway; VoiceSession обязан явно обрабатывать session_resumption_update (даже официальный ADK его терял — issue #4357). OpenAI Realtime: 60 мин, resumption нет — только context-replay.

### 6.4. Производительность

- Бюджеты — тестируемые артефакты (perf-смоук в CI с psutil): движок idle ≤150 МБ RSS, <1% CPU, ≤1 пробуждение/мин; лёгкий путь ≤500 мс. ⚠️ Судьи оценили реальный idle C в ~150–200 МБ — «на границе или выше бюджета»; вопрос открыт.
- Импорты — главный налог (pandas ~44 МБ; кейс 708→22 МБ изоляцией): ленивые импорты в хендлерах, `-X importtime`, PEP 810 в Python 3.15.
- Событийность вместо поллинга: `await event.wait()`, TaskGroup, грубые допуски таймеров; никаких `while True: sleep(n)`.
- Фон на Windows: низкого CPU-приоритета мало — `PROCESS_MODE_BACKGROUND_BEGIN` (CPU+I/O+page) + EcoQoS (E-ядра, как индексатор Win11).
- Debounce файловых событий (тихое окно ~100 мс + потолок + дедуп), батч-коммиты ~5 с (HA Recorder), лимиты у всех кэшей, эфемерные воркеры с рестартом по RSS (утечка fastembed лечится дизайном).
- Токены — тоже производительность: скоуп схем (динамика только **между** итерациями — внутри ломает KV-cache; при ~25 курируемых тулах tool-search вообще не нужен), компактация, кэш TTS, дневной бюджет ДО вызова.
- Rust — только через нативно-backed библиотеки; свой PyO3 — по профилировщику.

### 6.5. Тестирование и наблюдаемость

**Пирамида (gapfill_0)** — «инфраструктура снизу, LLM сверху»:
0. import-linter + ruff TID251 + юнит-тесты гейта — каждый коммит;
1. hypothesis property/stateful (ScopedRoot, saga/undo) — каждый PR;
2. crash-injection по методологии SQLite (kill в CRASH_AT=after_intent|mid_copy|before_complete; «либо целиком, либо никак» + идемпотентность повторного recovery) — главный тест обещания «невозможность повреждения данных»;
3. golden-сценарии со ScriptedModel (формат EvalSpec + expected_gate_decisions + journal-ассерты; оценка конечного состояния мира, не траектории) — **merge-гейт миграции, 100% pass**;
4. те же сценарии с живой моделью, **pass^3** для data-safety (75% per-trial → лишь ~42% pass^3) — ночью/при смене модели;
5. perf-смоук RSS/wakeups.

Мокирование только на границе **собственных** интерфейсов (LLMProvider — паттерн aider mock_send; FakeVoiceSession с событийными трейсами — паттерн Pipecat Evals, включая barge-in). Инвариант-монитор: запись в пользовательский файл раньше fsync intent-записи саги валит любой тест. Trace-to-test: каждый реальный сбой → golden-сценарий. Смена модели инвалидирует только слои 3–4; слои 0–2 «вечные».

**Наблюдаемость (gapfill_1)** — своя SQLite, ~300–600 строк, RSS ≈ 0:
- Таблицы `events` (INSERT-only, seq, turn_id, schema_version) и `llm_calls` (request_hash = content-addressed **replay-кэш**: JARVIS_REPLAY=1 подменяет клиента читателем кэша; хэш заодно детектирует стагнацию);
- turn_id через contextvars сквозь цепочку голос→план→гейт→действие→журнал;
- flight-recorder: deque ~500 событий, дамп при ошибке/деградации breaker'а;
- Datasette + FTS5 как вьюер по требованию; метрики (confirm-rate, undo-rate, эскалации) — SQL-view;
- двухуровневая ретенция: контент промптов 7–14 дней (отдельная таблица), events 10–30 дней, агрегаты навсегда;
- из OTel gen_ai.* — только имена атрибутов, не библиотеки.

### 6.6. Windows-специфика

- **Автозапуск**: Task Scheduler «At log on», НЕ служба (session 0 не видит окна/аудио; pywin32 #1452); single-instance — именованный мьютекс; graceful shutdown — WM_CLOSE/WM_ENDSESSION (консольные события не доходят до pythonw.exe); ProactorEventLoop обязателен; WM_POWERBROADCAST + USN catch-up после resume.
- **Упаковка/обновление**: git-тег + uv.lock + управляемый Python; releases/\<tag\> с атомарным junction-указателем; транзакция «VACUUM INTO-снапшот → миграции → golden-смоук → commit/rollback»; апдейтер — отдельный «скучный» процесс.
- **Миграции**: PRAGMA user_version + нумерованные SQL-файлы, независимо на файл БД; refuse-to-start при даунгрейде + пре-миграционная копия jarvis.db.vNN.
- **Бэкап**: только backup API / VACUUM INTO (копирование живого WAL — тихая потеря данных, судьи ловили эту ошибку в дизайнах); еженедельный автоматический restore-тест.
- **Elevation**: FSCTL_READ_UNPRIVILEGED_USN_JOURNAL (без админа, подмножество записей) как основа; служба Everything решает MFT/USN; elevated-хелпер только для первичного ENUM MFT.
- **COM**: IFileOperation — только через выделенный STA-поток с таймаутом; UIA — CacheRequest + узкий TreeScope; Electron — флаг --force-renderer-accessibility.
- **Файловые мутации**: удаление через IFileOperation (корзина + undo-record Explorer), перезапись через temp+ReplaceFile (атомарно в пределах тома, сохраняет ACL).
- Лицензии стека чисты (MIT/Apache/PSF); жёлтая зона — Piper GPL-3.0 (изолируется процессной границей) и CC BY-NC у Silero TTS / моделей openWakeWord.

### 6.7. Voice

- **Драйвер №1 — Gemini Live** за интерфейсом VoiceSession (4 asyncio-задачи, VAD, resumption-хэндлы, GoAway, compression, реконнект с circuit breaker — ~80% кода прототипа переупаковывается).
- **Драйвер №2 — half-cascade** (обязателен: дешёвого idle и серверного wake word нет ни у одного провайдера): **openWakeWord** «hey jarvis» (Apache 2.0, ONNX) + **Silero VAD** (MIT, ~2 МБ, <1 мс/чанк) + **GigaAM** (Сбер, MIT, ONNX, 225 МБ; WER 3.3% против 7.9% у large-v3-turbo; v3-e2e с пунктуацией) + **Silero TTS v4/v5** (лучший локальный русский, автоударения; CC BY-NC — ок лично) / edge-tts как облачный fallback.
- Half-cascade пишется **сразу после этапа 5 как тест контракта** VoiceSession — до завязки ядра на интерфейс.
- Гибрид: локальный wake word **гейтит** открытие платной Live-сессии (приватность + квота); refractory-период + idle-timeout; фразы от 6 фонем («Эй Джарвис», не «Джарвис»).
- Латентность: воспринимаемая = EoU (~300–500 мс тишины) + LLM TTFT + TTS TTFB; рычаги — sentence-chunked TTS (−200–500 мс), кэш аудио частых фраз, «звук размышления». ⚠️ **Нюанс бюджетов**: voice-pipeline задаёт цель каскада «~800 мс, отлично <500 мс», тогда как общесистемный бюджет лёгкого пути — ≤500 мс; это не строго противоречие (разные измеряемые величины), но числа в корпусе не сведены в одну таблицу.
- **Barge-in с первого дня**: тройная отмена (флаш TTS + отмена LLM + рестарт STT) — в контракте интерфейса, вкручивать задним числом дорого.
- Внешний research добавил кандидатов: стриминговые T-one и gigastt на лёгкий путь; уточнил лицензию Silero v5 (CC-BY-NC, MIT только v5_cis_base).

## 7. План миграции и открытые вопросы

### 7.1. Strangler-миграция (~6–8 месяцев соло, 9 этапов)

Принципы: прототип в **фичефризе** с этапа 0; критерий каждого этапа — «старый путь **УДАЛЁН**» (лимит двойных механизмов 2 недели); `git checkout` всегда возвращает рабочую систему; форсинг-функции завершения (дедлайны в ADR — урок «вечного гибрида» Siri).

| Этап | Срок | Содержание | Критерий готовности |
|---|---|---|---|
| **0** | 1–2 нед | golden-сценарии 20–30 запросов; единый config + registry.yaml; вынос live-ключа; uv.lock; удаление ~30% мёртвых actions/ и сироты searxng | grep не находит моделей/ключей вне config |
| **1** | 2–3 нед | **Гейт**: dispatch() поверх policy-таблицы; executor через гейт; упразднение сырого `command` | 100% вызовов в логе с вердиктом |
| **2** | 3–4 нед | store + шина + saga/undo + fileops (IFileOperation/ReplaceFile/ScopedRoot) | crash-тест «kill посреди batch»; «отмени последнее» голосом |
| **3** | 3–4 нед | durable-подтверждения + память v2 (JSON→SQLite) | confirm переживает рестарт; поиск <50 мс |
| **4** | 4–6 нед | **Новый цикл** (самый рискованный, единственная точка невозврата) | main.py <300 строк; рестарт посреди плана продолжает |
| **5** | 3–4 нед | batch-адаптеры + VoiceSession + half-cascade как тест контракта | текст работает на Ollama сменой строки |
| **6** | 2–3 нед | отделение UI (движок headless) | kill UI не роняет задачу |
| **7** | 4–6 нед | world model v2 (ingest-воркер) | idle-бюджет неделю по метрикам; catch-up после простоя |
| **8** | 3–4 нед | манифесты + pluggy; Playwright→MCP с песочницей | новый тул одним каталогом; ≤12k строк |

Жёсткий порядок 0→1→2 (сетка → гейт → store/журнал); этапы 5–8 переставляемы.

⚠️ **Расхождения планов**: дизайн A — 8 этапов / 5–7 мес (гейт этап 1); дизайн C — 9 этапов (гейт только этап 2, после манифестов); дизайн B — 6–9 мес (гейт+журнал в первой трети, паритет на этапе 4). Итоговый план синтеза берёт последовательность «гейт раньше манифестов» из graft'ов судей и оценку 6–8 месяцев; у C календарных оценок не было вовсе, оценки A названы судьями оптимистичными — **реальная длительность гибрида неизвестна**.

### 7.2. Осознанные жертвы

Нет краш-изоляции in-process плагинов; нет DAG-параллелизма планов; нет полного event sourcing; нет скриншотов в v1 (система не отвечает «что было на экране час назад»); компенсация вместо идеального отката (глубина undo ограничена квотой staging); vendor-код Gemini в драйвере до каскада; кроссплатформенность принесена в жертву Win32; каждое действие обязано иметь манифест (выкупается скаффолдом).

### 7.3. Открытые вопросы и риски (консолидировано)

**Блокирующие / требующие проверки до соответствующих этапов:**
1. **sqlite-vec в шифрованной БД** (apsw-sqlite3mc) — не подтверждено первоисточником; нужен smoke-тест; определён только порог отката (>20% KNN-overhead → EFS/частичное шифрование).
2. **Лицензия Everything SDK/ES.exe** для стороннего приложения — реальный текст не установлен.
3. **Вердикты внешней верификации** (`external_verification-verdicts.md`) не входят в конспекты — при принятии решений по спорным пунктам (T-one/gigastt, WM_POWERBROADCAST без окна, Chromium-accessibility) обращаться к нему.
4. **Idle-бюджет ≤150 МБ** против реалистичной оценки судей ~150–200 МБ — на границе; подтверждается только perf-смоуком после этапов 6–7.

**Архитектурные риски:**
5. **Этап 4** — «маленькая революция внутри эволюции»: скрытые связи main.py с голосом/UI; митигация — feature-flag, golden с interruption-кейсами, журнал расхождений; риск сценария Siri (вечный гибрид).
6. **Протечка VoiceSession** — подтвердится только когда half-cascade реально ляжет на интерфейс (потому он и пишется сразу после этапа 5).
7. **Шов выноса ingest** заложен, но до этапа 7 USN-штормы могут давать GIL-джиттер аудио; автоматизация триггера по глубине очередей не спроектирована.
8. **Динамический скоуп тулов** → галлюцинации замаскированных тулов; предусмотрен откат к статике по метрике.
9. **Налог inverse/preview** на каждый мутационный тул — часть хендлеров может получить их формально, undo станет дырявым.
10. **Идемпотентность на практике**: краш между шагом и completion-записью, параллельные чужие изменения файлов — закрывается только дисциплиной check-before-act + crash-injection.

**Внешние зависимости и экосистема:**
11. **Русский TTS** — узкое место: Silero CC BY-NC (только лично), edge-tts — риск ToS, Piper — GPL за процессной границей; полноценного свободного локального русского TTS нет.
12. **Смертность зависимостей** (Gemini Live, Everything, sqlite-vec, fastembed) — у каждой local-first альтернатива, но свой USN-ридер с elevated-хелпером существует только как чертёж.
13. **Экономика Gemini Live** для always-on системно не решена: idle дорог у всех, half-cascade — обход, а не решение; цены/лимиты требуют периодической ревизии.

**Процессные:**
14. **Соло-фактор и выгорание** на 6–8 месяцах — главный нетехнический риск; митигация — атомарно полезные этапы, генерируемая документация (ARCHITECTURE.md/EVENTS.md из реестров).
15. **Атомарного снапшота двух WAL нет** — слабая связность принята как контракт; все кросс-файловые ссылки обязаны переживать отсутствие строки.
16. Методология golden-сценариев закрыта gapfill_0, но **формат JSONL-транскрипта и команда «сценарий из вчерашней сессии»** не специфицированы; ретенции (7–14/10–30 дней) не согласованы финально с политикой хранилища истории.
17. Мелочи для выверки: счётчик «/7» при 8 кластерах в `_verify_workflow.js`; тройная нумерация целевой системы (XXXVI/XL/L); вилка объёма LLM-роутера в A; nomic-embed vs all-MiniLM.

## Итог одной строкой

Корпус — редкий по дисциплине пример инженерного решения через турнир: три полных дизайна, три судьи с разными линзами и численными оценками (**C=150 > A=138 > B=124**), критик пробелов, gapfill-дорасследования и адверсарно верифицированный внешний research сошлись на гибриде «**прагматичный минимализм C + миграционная механика A (гейт первым, „удалено, не выключено") + контрактная гигиена B**»: два процесса, два SQLite-файла, свой цикл ~2k строк, единый dispatch(), Everything-first world model, слоистая память со sleep-time консолидацией, русский каскадный голос за VoiceSession — и strangler-миграция 6–8 месяцев, где безопасность данных доставляется в первой трети пути.
