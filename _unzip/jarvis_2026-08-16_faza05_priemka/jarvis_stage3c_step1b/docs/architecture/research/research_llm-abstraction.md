Изучены четыре пласта первоисточников: внутренности LiteLLM (официальные доки router_architecture) и OpenRouter (их блог о роутинге); «тонкие» библиотеки абстракции (any-llm от Mozilla.ai, aisuite Эндрю Ына, pydantic-ai); различия tool calling и structured output у OpenAI/Anthropic/Gemini/локальных рантаймов (Ollama, llama.cpp, LM Studio); и главное — как два боевых фреймворка голосовых агентов (Pipecat, LiveKit Agents) реально абстрагируют Gemini Live и OpenAI Realtime, включая их GitHub-issues о том, где абстракция ломается.

Вывод 1: batch-слой (request/response) — решённая задача, и решать её надо своим тонким слоем. Формат Chat Completions стал lingua franca: его нативно говорят Ollama, LM Studio, llama.cpp server, vLLM, OpenRouter. Различия tool calling (tools/function у OpenAI, input_schema + tool_use-блоки у Anthropic, functionDeclarations у Gemini, разные стриминговые дельты) — механические, транслируются адаптером в один внутренний тип сообщения/вызова/результата. Философия any-llm подтверждена как правильная для долгоживущего проекта: оборачивать официальные SDK провайдеров и нормализовать ответы к одной форме, а не реимплементировать HTTP-интерфейсы самому (главная претензия any-llm к LiteLLM — реимплементация ведёт к дрейфу совместимости). Для проекта это буквально означает: один адаптер google-genai (новый SDK), один openai-совместимый адаптер (закрывает сразу OpenAI, Ollama, LM Studio, OpenRouter, llama.cpp), опционально anthropic — и проблема «двух SDK Gemini» с 36 хардкодами имён исчезает за границей адаптера.

Вывод 2: LiteLLM как зависимость — нет; LiteLLM как источник паттернов — да. Против: он спроектирован под мультитенантный прокси и 100+ провайдеров (нужно 3–5); репутация качества кода в сообществе плохая (тред HN «worst code I have ever read»); огромная поверхность зависимостей; и, по данным поиска 2026 года, серия инцидентов: supply-chain компрометация версий 1.82.7–1.82.8 на PyPI с кражей учётных данных (март 2026), цепочка уязвимостей прокси CVSS 9.9 и command injection в каталоге CISA KEV. Для программы, работающей с полным доступом к файлам личного ПК, вес зависимости — прямая инженерная цена. За: его архитектура роутера отлична и копируема в ~500–1000 строк: fallback-обёртка ПОВЕРХ retry-обёртки (function_with_fallbacks → function_with_retries); три класса fallback по типу ошибки (общие, context-window-exceeded, content-policy) на основе единой таксономии исключений, в которую маппятся ошибки всех провайдеров; CooldownCache — временное исключение «остывающих» деплойментов. OpenRouter добавляет два приёма: деприоритизация провайдера при сбое за последние 30 секунд и поле native_finish_reason — рядом с нормализованным полем всегда сохраняется сырое провайдерское (нормализация без потери информации). OpenRouter стоит держать как один из адаптеров (один ключ — 500 моделей), но не как несущую абстракцию: облачная точка отказа и не покрывает realtime-голос.

Вывод 3: structured output кросс-провайдерно — минное поле поднаборов JSON Schema. OpenAI strict — constrained decoding на уровне токенов, но требует additionalProperties:false и падает 400-й на некомпилируемых схемах; Gemini responseSchema — более узкий OpenAPI-поднабор, union-типы и вложенность 3+ уровней отказывают, иногда тихо; Anthropic исторически — принуждение через tool с input_schema, зато без additionalProperties-ограничений. Схемные режимы дают 99,7–99,9% соблюдения, «JSON mode» без схемы — 8–15% брака. Портируемая стратегия: держать внутренние схемы в общем поднаборе (плоские, без union), всегда валидировать на клиенте и иметь одну repair-итерацию. Отдельная находка для локального контура: llama.cpp конвертирует JSON Schema в GBNF-грамматику и гарантирует структуру даже на 4B-модели (нюансы: схема не попадает в промпт — её надо описать словами; обрыв по лимиту токенов ломает гарантию, нужен maxTokens + валидация). Это делает роли memory-extractor и cheap-classifier идеальными кандидатами на локальную модель.

Вывод 4 — центральный для проекта: realtime-голос полностью не абстрагируется, и это подтверждено опытом обоих фреймворков, которые пытались. LiveKit Agents сделал RealtimeModel как ABC + структуру RealtimeCapabilities (флаги возможностей), но issue #6002 фиксирует разлом: Gemini Live не умеет tool_choice="none" и пер-ответное управление инструментами, а динамическое обновление списка тулов требует рестарта сессии — общие workflow, предполагающие GPT-семантику, молча ломаются. Pipecat документирует, что GeminiLive не эмитит события начала/конца речи пользователя (только interrupted), из-за чего отваливается целый слой даунстрим-логики, и что стратегия стриминга аудио зависит от режима VAD. Жизненный цикл сессий различается фундаментально: у Gemini соединение живёт ~10 минут, сессия — 15 минут (неограниченно при sliding-window compression), есть resumption-хэндлы (валидны 2 часа) и сигнал GoAway с timeLeft; у OpenAI Realtime — жёсткий потолок 60 минут, resumption НЕТ вовсе — контекст пересобирается вручную заливкой текстовой истории в новую сессию. Отсюда граница абстракции: абстрагировать семантические события сессии (user-speech-start/stop, транскрипты входа/выхода, tool-call с id, interruption со списком отменённых вызовов, audio-chunk, session-expiring) плюс явные capability-флаги; а wire-протокол, конфиг VAD, аудиоформаты (у Gemini вход 16 кГц / выход 24 кГц PCM) и стратегию продления жизни сессии (resumption-хэндлы против context-replay) оставить в непереносимых «драйверах» провайдеров. Критично для известной дыры проекта: tool-вызовы из live-сессии обязаны проходить через тот же центральный гейт разрешений core/security.py, что и batch-путь — диспетчер тулов один, транспортов много.

Вывод 5: реестр «роль→модель» — зрелый паттерн с готовым образцом. Continue.dev в config.yaml назначает моделям роли (chat, autocomplete, embed, rerank, apply) с пер-ролевыми опциями и полем capabilities, перекрывающим автодетект; pydantic-ai разделяет Model / Provider / ModelProfile (паспорт возможностей и ограничений модели). Для проекта: registry.yaml с ролями live-voice, planner, memory-extractor, cheap-classifier, embedder; каждая запись — provider:model, параметры, fallback-цепочка, требуемые capabilities; на старте валидация «модель покрывает требования роли». Это одновременно убивает 14 дублей загрузки ключа и 36 хардкодов.

Практический план: свой слой из трёх частей — (1) batch-адаптеры над официальными SDK с единой таксономией ошибок, fallback-поверх-retry и cooldown (у проекта уже есть circuit breakers — они переезжают сюда); (2) realtime-драйверы за событийным интерфейсом с capability-флагами, Gemini Live первым, OpenAI Realtime вторым; (3) каскадный путь STT→LLM→TTS как провайдер-независимый резерв голоса (паттерн half-cascade из LiveKit): если realtime-провайдер недоступен или сменился — голос деградирует, но не умирает, и работает с любой batch-моделью, включая локальную. Оценка объёма: batch-слой + реестр + fallback — реально уложиться в 700–1200 строк; realtime-драйвер на провайдера — ещё ~500–800, но один из них у проекта фактически уже написан.

## Идеи

- **Реестр «роль→модель» с capability-валидацией** [Continue.dev config.yaml (docs.continue.dev/reference, model-roles) + pydantic-ai ModelProfile]: Конфиг, где каждой роли (live-voice, planner, memory-extractor, cheap-classifier, embedder) назначается provider:model с параметрами, fallback-цепочкой и списком требуемых возможностей; поле capabilities может перекрывать автодетект. На старте система проверяет, что модель покрывает требования роли. | Почему: Убирает хардкод имён моделей из кода полностью; смена модели = правка одной строки конфига; Continue.dev доказал масштабируемость паттерна на пяти+ ролях в реальном продукте. | Применимость: high — прямо решает 36 хардкодов имён моделей и 14 дублей загрузки ключа в MARK XXXV; registry.yaml + один модуль-резолвер.
- **Двухуровневая граница абстракции: batch отдельно от realtime** [Синтез из Pipecat docs и LiveKit Agents realtime overview]: Request/response-вызовы абстрагируются полностью (единые типы сообщений/тулов/ошибок), а realtime-голос — только на уровне семантических событий сессии; wire-протоколы, VAD, аудиоформаты и продление сессий остаются в провайдер-специфичных драйверах. | Почему: Оба фреймворка, попытавшихся сделать единый realtime-интерфейс, пришли к этой же структуре через боль (issue #6002 у LiveKit, отсутствующие speech-события у Pipecat); честная граница дешевле протекающей универсальности. | Применимость: high — определяет структуру пакетов нового ядра: core/llm (полная абстракция) и core/voice/drivers/* (изолированное неабстрагируемое).
- **RealtimeCapabilities: явные флаги возможностей realtime-модели** [LiveKit Agents (livekit-agents/llm/realtime.py, RealtimeModel ABC + RealtimeCapabilities)]: Базовый класс realtime-сессии сопровождается структурой флагов: поддержка per-response tool_choice, динамического обновления тулов, text-модальности, resumption, видео. Общая логика ветвится по флагам, а не предполагает поведение. | Почему: Превращает молчаливые поломки (Gemini игнорирует tool_choice=none) в явные ветки кода; новый провайдер описывает себя декларативно. | Применимость: high — тот же приём стоит применить и к batch-моделям (parallel tool calls, strict schema, streaming tool args).
- **Провайдер-специфичный session-lifecycle manager** [Gemini Live docs (ai.google.dev/gemini-api/docs/live-session) + OpenAI community threads о reconnect]: Для Gemini: хранить свежий resumption-хэндл из SessionResumptionUpdate (валиден 2 ч), реагировать на GoAway.timeLeft переподключением (~10-мин соединения), включать contextWindowCompression со sliding window для «вечных» сессий. Для OpenAI: до истечения 60-мин потолка пересоздавать сессию с заливкой текстовой истории (context-replay), т.к. resumption отсутствует. | Почему: Это два принципиально разных механизма непрерывности — их нельзя унифицировать, но можно спрятать за одним контрактом «сессия живёт, пока драйвер жив», что и требуется ассистенту, работающему часами. | Применимость: high — у MARK XXXV уже есть реконнект с circuit breaker; его нужно оформить как lifecycle-manager внутри драйвера Gemini Live.
- **Fallback-обёртка поверх retry + классы ошибок** [LiteLLM router architecture (docs.litellm.ai/docs/router_architecture)]: Запрос сначала проходит retry в пределах той же модели (экспоненциальный backoff), и только исчерпав их — fallback на другую модель; fallback-цепочки различаются по классу ошибки: общие сбои, превышение контекста, content-policy. Все ошибки провайдеров маппятся в единую таксономию исключений. | Почему: Разделение «повторить то же» и «сменить модель» по типу ошибки — то, что наивные реализации смешивают; таксономия исключений — предпосылка любого умного роутинга. | Применимость: high — копируется в свой слой в ~200 строк; квотные circuit breakers проекта становятся частным случаем.
- **CooldownCache и деприоритизация нездоровых провайдеров** [LiteLLM CooldownCache + OpenRouter model routing blog (деприоритизация при сбое за 30 сек)]: Провайдер/модель после серии ошибок помещается в cooldown и исключается из выбора на время; роутер выбирает из оставшихся, возвращая «остывшего» после таймаута. | Почему: Дешёвая форма health-tracking без отдельного мониторинга; предотвращает молотьбу по лежащему провайдеру и каскадные задержки. | Применимость: medium — у проекта уже есть circuit breakers на здоровье поисковых провайдеров; тот же механизм обобщается на LLM-провайдеров в реестре.
- **Обёртка официальных SDK вместо реимплементации HTTP-интерфейсов** [any-llm (blog.mozilla.ai/introducing-any-llm), aisuite (github.com/andrewyng/aisuite)]: Адаптер вызывает официальный SDK провайдера (или его OpenAI-совместимый эндпоинт) и нормализует ответ к одной внутренней форме (any-llm нормализует к OpenAI ChatCompletion-объектам). | Почему: Совместимость с изменениями API поддерживает сам провайдер, а не ты; один OpenAI-совместимый адаптер бесплатно покрывает Ollama, LM Studio, llama.cpp, OpenRouter, vLLM. | Применимость: high — сводит задачу к 2–3 адаптерам (google-genai, openai-compatible, опц. anthropic) и закрывает проблему двух параллельных SDK Gemini.
- **Общий поднабор JSON Schema + валидация + repair-петля** [Requesty «compatibility mess» (244 модели), logic.inc structured outputs guide, Rost Glukhov comparison]: Все внутренние схемы держатся в пересечении возможностей провайдеров (плоские структуры, без union-типов, вложенность ≤2), выход всегда валидируется клиентски, при браке — одна повторная попытка с текстом ошибки. | Почему: Схемные режимы дают 99,7–99,9% соблюдения против 8–15% брака у «JSON mode» без схемы, но поднаборы схем у провайдеров разные, и Gemini отказывает тихо — клиентская валидация обязательна для переносимости. | Применимость: high — для планировщика, экстракции памяти и любых машиночитаемых ответов; правило «schema lowest common denominator» должно попасть в style-гайд проекта.
- **GBNF-грамматики для локальной экстракции памяти и классификации** [llama.cpp grammars README (JSON Schema→GBNF конвертер), LM Studio structured response docs]: llama.cpp/LM Studio конвертируют JSON Schema в грамматику и ограничивают генерацию на уровне токенов — структурно валидный JSON гарантирован даже у малых моделей. Нюансы: схему нужно продублировать словами в промпте (в грамматике модель её «не видит»), обрыв по maxTokens ломает гарантию. | Почему: Снимает главный барьер применения локальных 4–8B моделей для дешёвых ролей — ненадёжность JSON; экстракция памяти перестаёт стоить денег и уходить в облако. | Применимость: high — роли memory-extractor и cheap-classifier переводятся на локальную модель через тот же openai-совместимый адаптер (response_format: json_schema).
- **Нормализованное поле + сырое native_* рядом** [OpenRouter (native_finish_reason в ответах)]: Слой нормализации всегда сохраняет исходное провайдерское значение (finish_reason, код ошибки, usage) рядом с нормализованным, вместо замещения. | Почему: Нормализация без потери информации: отладка и провайдер-специфичная логика не упираются в «усреднённый» ответ; дешёвый приём, спасающий часы диагностики. | Применимость: medium — одно поле raw в внутреннем типе ответа адаптера.
- **Half-cascade: каскадный STT→LLM→TTS как резервный голосовой путь** [LiveKit realtime models overview (half-cascade), Pipecat (единый pipeline для cascaded и S2S)]: Голосовой контур умеет работать в двух режимах: нативный speech-to-speech (Gemini Live/OpenAI Realtime) и каскад из отдельных STT, batch-LLM и TTS за тем же событийным интерфейсом. | Почему: Каскад работает с ЛЮБОЙ batch-моделью, включая локальную — это настоящая провайдер-независимость голоса; production-агенты в 2026 часто выбирают каскад ради надёжности tool calling и наблюдаемости. | Применимость: medium — не для первой итерации, но интерфейс событий стоит спроектировать так, чтобы каскадный драйвер вставал в тот же слот.
- **Единый диспетчер тулов для всех транспортов** [Экспертная оценка на базе Pipecat/LiveKit (function calling внутри live-сессии) и известной дыры agent/executor в MARK XXXV]: Tool-вызовы из live-сессии, из batch-запросов и из агентного executor сходятся в один диспетчер, который проходит центральный гейт разрешений core/security.py; драйверы транспортов только доставляют вызов и результат (включая отмену pending-вызовов при interruption у Gemini). | Почему: Policy-таблица остаётся единственным источником правды независимо от того, каким путём модель попросила действие; закрывает класс ошибок «новый транспорт забыл про гейт». | Применимость: high — одновременно чинит незакрытый обход гейта в executor и структурирует realtime-драйверы.

## Анти-паттерны

- **LiteLLM как несущая зависимость single-user desktop-проекта** [HN-треды о качестве кода; TheHackerNews: компрометация версий 1.82.7–1.82.8 (март 2026), цепочка уязвимостей прокси CVSS 9.9, command injection в CISA KEV]: Инструмент спроектирован под мультитенантный прокси и 100+ провайдеров — проекту нужно 3–5; тысячи транзитивных зависимостей и история supply-chain-инцидентов 2026 года — неприемлемая цена для программы с полным доступом к личным файлам; Python-прокси даёт и потолок производительности. Ценность LiteLLM для этого проекта — его паттерны, а не пакет.
- **Реимплементация провайдерских HTTP-интерфейсов вместо официальных SDK** [Критика LiteLLM в блоге any-llm (Mozilla.ai)]: Каждое изменение API провайдера требует правки твоего слоя; накапливается дрейф совместимости и неожиданные отличия поведения — ровно то, что нельзя себе позволить проекту, сопровождаемому одним человеком 5+ лет.
- **Единый realtime-интерфейс, предполагающий GPT-семантику tool control** [LiveKit Agents issue #6002]: Общие workflow LiveKit предполагали tool_choice=none и динамическое обновление тулов — Gemini Live этого не умеет (нужен рестарт сессии), и сценарии молча ломались. Абстракция без capability-флагов превращает различия протоколов в плавающие баги.
- **JSON mode без схемного enforcement** [Сравнения structured output (TokenMix, Future AGI): 8–15% брака против 99,7–99,9% у схемных режимов]: «Просто попроси JSON в промпте» стабильно даёт процентную долю мусора, которая в長ном агентном цикле означает регулярные тихие сбои планировщика и памяти; для машиночитаемых ответов допустимы только режимы с constrained decoding/schema плюс клиентская валидация.
- **Предположение о переносимости JSON Schema между провайдерами** [Requesty «Structured Outputs Across LLM Providers: the compatibility mess», tianpan.co о схеме, которую две модели трактуют по-разному]: Схема, работающая на OpenAI strict, может быть невыразима на Gemini responseSchema (union-типы, глубокая вложенность падают тихо) и вести себя иначе на Anthropic; миграция провайдера без пер-режимного прогона схем превращается в недели незапланированной работы.
- **Абстракция моделей, вшитая в agent-фреймворк** [Критика framework-embedded подходов в блоге any-llm (на примере связанности pydantic-ai)]: Слой моделей, сцепленный с чужим агентным контуром, нельзя вынуть и использовать в своём planner/executor; для проекта с собственным агентным контуром это означало бы переписывание ядра под чужую архитектуру ради адаптеров.
- **Хардкод имён моделей и дублирование конфигурации по кодовой базе** [Собственный прототип MARK XXXV (36 хардкодов, 14 загрузок ключа, два SDK параллельно)]: Каждая смена модели/провайдера превращается в грепанье по 23k строк; параллельные SDK тянут конфликтующие зависимости; это главный механизм, из-за которого «смена провайдера» становится переписыванием, а не заменой адаптера.
- **Ollama через /v1 (OpenAI-compat) для агентных задач** [Ollama docs/issues (#4386, #13374), OpenClaw provider docs]: OpenAI-совместимый эндпоинт Ollama не поддерживает tool_choice и num_ctx, исторически ломал сочетание streaming+tools, и модели могут выдавать сырой tool-JSON текстом; для тулов надёжнее нативный /api/chat — т.е. адаптер должен уметь оба пути, а не слепо считать /v1 эквивалентом OpenAI.
