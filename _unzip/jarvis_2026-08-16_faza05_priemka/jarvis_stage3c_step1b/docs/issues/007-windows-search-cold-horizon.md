## Agent Brief

**Category:** bug/enhancement
**Summary:** Быстрый поиск файлов через индекс Everything (`es.exe`), с ограниченным по времени фолбэком, когда индекса нет — чтобы «найди файл» больше не висело минутами на обходе всего диска.

**Current behavior:**
`file_controller.find_files`/`largest` делают `search_path.rglob(...)` по всему дереву
без индекса → «найди по всему ПК» = 3-4 минуты/зависание. Windows Search на машине
отключён, Everything не установлен (см. triage findings).

**Desired behavior:**
- Новый модуль поиска `core/awareness/_search.py` с функцией
  `search(name="", ext="", scope=None, limit=50, timeout_s=…) -> list[dict]`
  (каждый: path, mtime, size), **слоями**:
  1. **Everything `es.exe`** если доступен (на PATH / рядом) — мгновенно, весь диск.
     Запуск через шов `_run_es(args) -> str` (тесты подменяют, реальный процесс не
     дёргается). Формирование запроса Everything из name/ext.
  2. **Bounded-фолбэк** если es нет: обход ТОЛЬКО пользовательских папок
     (`_known_folders.watch_roots()`) [+ project roots позже] со СТРОГИМ лимитом по
     времени (секунды) и количеству; пропуск системных/шумных каталогов. НИКОГДА не
     обходит весь `C:`.
- `find_files` и `largest` в `file_controller` переведены на этот модуль (или на
  bounded-обход) → безлимитный `rglob` удалён. Формат/сигнатуры функций и их результат
  (текст) сохранить, существующие файловые тесты не ломать.
- Когда результатов нет и бэкенд ограниченный — честное сообщение («искал в основных
  папках; для поиска по всему ПК установите Everything / включите индекс»).
- Резолвер (004): по желанию — холодная ветка `by_extension`/`recent_file` падает в
  `search`, если журнал пуст (вторично; не ломать существующие тесты резолвера).

**Key interfaces:**
- `core.awareness._search.search(...)` + `_run_es` (шов) + `_es_available()`.
- `_known_folders.watch_roots()` — источник границ фолбэка (переиспользование).
- `file_controller.find_files/largest` вызывают `_search` вместо `rglob`.

**Acceptance criteria:**
- [ ] Есть `es.exe` (шов подменён) → `search` возвращает распарсенные пути из вывода Everything; запрос строится из name/ext.
- [ ] Нет `es.exe` → bounded-фолбэк находит файлы во временном дереве, уважает лимит количества и НЕ выходит за заданные корни (тест).
- [ ] Фолбэк не висит: жёсткий дедлайн по времени (тест: дерево больше лимита → возврат за доли секунды с частичным результатом).
- [ ] `find_files`/`largest` больше не используют безлимитный `rglob`; существующие файловые тесты зелёные.
- [ ] Полный `pytest` зелёный (сейчас 104 passed).
- [ ] Отсутствие Everything не роняет ничего (мягкая деградация).

**Out of scope:**
- Установка Everything (делает мейнтейнер), включение Windows Search, проектные корни
  в конфиге (позже), действия 008–010.

## What to build

Холодный горизонт поиска. `_search` внутри пакета `awareness`: адаптер Windows Search
Index через ADODB `Search.CollatorDSO` (первый COM в проекте):

- только метаданные (`System.ItemPathDisplay`, `System.DateModified`, размер, имя),
  `SCOPE` строго по пользовательским папкам из `_known_folders`;
- чистый конструктор SQL-запросов (имя/расширение/диапазон дат) отделён от COM-вызова —
  тестируется без COM;
- `pythoncom.CoInitialize()` на каждом вызывающем потоке (пул `run_in_executor`
  переиспользует потоки — инициализация на вызов, с защитой), таймаут на запрос;
- никаких COM-вызовов в event-loop потоке и в фоновом демоне — только по команде.

Резолвер (срез 004) получает холодную ветку: «файл/проект, который я вчера добавил»,
«тот JSON-файл, с которым мы работали» (расширение + недавность, объединяя горячий
журнал и индекс; горячий приоритетнее — индекс отстаёт на свежих файлах). При
недоступном Windows Search — честная деградация на горячий журнал.

Демо: «найди тот JSON-файл, с которым мы работали» → путь; «найди проект, который я
вчера добавил» → путь папки.

## Acceptance criteria

- [ ] Оба демо-запроса возвращают корректные пути при включённом Windows Search (ручная проверка).
- [ ] Юнит-тесты конструктора запросов (скоуп по known folders, фильтры расширения/дат) — без COM; COM-адаптер за узким интерфейсом.
- [ ] Повторные вызовы из пула потоков не дают «CoInitialize has not been called» (инициализация на потоке вызова).
- [ ] COM не вызывается в event-loop потоке и в фоновом демоне.
- [ ] При выключенной службе Windows Search Jarvis отвечает деградированно (горячий журнал) и не падает.
